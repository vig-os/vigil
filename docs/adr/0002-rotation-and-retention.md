## Context

Several fleet tools run one process per agent session, all appending to the same `<signal>.jsonl`. The rotation in [gerchowl/s1-mcp#6](https://github.com/gerchowl/s1-mcp/pull/6) works for that (8 concurrent writers × 50 records, no loss) and is the starting point, but the pre-mortem on [#4](https://github.com/vig-os/vigil/issues/4) (probed 2026-10-09, all confirmed by tests) found six defects in the naive port. The numbers below are those probes.

No existing crate fits. `file-rotate`, `logroller`, `log2`, `flexi_logger`, `rolling-file` and `tracing-appender` keep in-process size counters and rename without cross-process coordination: they are thread-safe, not multi-process safe ([g-fleet#355](https://github.com/gerchowl/g-fleet/issues/355), ecosystem table).

## Decision

Rotation lives in the crate, using std (`File::lock`, stable since Rust 1.89) and safe `rustix` filesystem wrappers, Unix targets (Linux, macOS), `#![forbid(unsafe_code)]`.

1. **Size rotation, default 50 MiB.** Rotate when `len + line + 1 > max_bytes`. A single line larger than the limit is still written, alone in a fresh file. Size arithmetic is checked or saturating, because crane runs every Nix check with `--release` where overflow checks are off.
2. **Age retention, default 90 days; `None` keeps everything.** A rotated segment is deleted when its mtime is older than the retention. The live file is never deleted. (Amendment 3, Proposed: age is one of three retention limits; a segment-count cap and a total-bytes cap are added by decisions 16 to 23, and age runs first among them (decision 19). With none of the new caps set, behaviour is exactly the one in this decision.)
3. **Lock the state directory.** All writers take an exclusive `flock` (std `File::lock`) on the state directory itself. After locking, its device and inode are checked against the path; a replaced or missing directory is reopened (recreated 0700 if needed) with bounded retries, updating the shared lock handle. Critical-section operations are relative to the locked descriptor, so an in-flight append remains in that directory even if its path is swapped. A separate lock file was the first design and is superseded: the re-verification of [PR #22](https://github.com/vig-os/vigil/pull/22) showed that a lock file deleted under load (tmpfiles, cleaners) lets two writers into the critical section (a check-then-act race: 2 `NotFound` errors in 48 000 appends, misordered records), while a non-empty directory cannot be unlinked. Locking the data file itself is also wrong: a waiter can lock the inode that was just renamed away and write under a lock nobody else holds. All signals in one directory share the one lock; the critical section is one write plus an occasional rotation, so contention is acceptable.
4. **Inode recheck before every write.** With the lock held, compare the live path's `(dev, ino)` with the cached handle and reopen if they differ; then size-check, rotate if needed, write. Without it, a process holding an `O_APPEND` handle from before another process rotated keeps writing into the renamed segment. Probe: 8 processes × 500 records, 2000 B limit, **428–2529 of 4000 records landed in rotated segments** and segments grew to 64 688 B. Fixed variant: 0 lost, 0 misplaced, 0 over the limit.
5. **Collision-free, chronologically sortable segment names.** `<signal>-<UTC stamp with nanoseconds>.jsonl`, and if that name already exists a zero-padded counter is appended, so the lexicographic order is the chronological order. Format, as implemented in [PR #22](https://github.com/vig-os/vigil/pull/22) (`stamp_at`, `unique_target` in `src/rotate.rs`): `<signal>-YYYYMMDDTHHMMSS.<9-digit nanos>Z.jsonl`, and on collision `<signal>-<stamp>_NNNNNN.jsonl` with a zero-padded counter of at least 6 digits. Ordering is by (stamp, integer counter), so a counter wider than 6 digits still sorts correctly. Rotation never replaces an existing file: the live file is atomically renamed with no-replace semantics; directory-relative link/unlink is used only when the platform or filesystem lacks that operation. Example: `logs-20261009T141245.123456789Z.jsonl`, then `logs-20261009T141245.123456789Z_000001.jsonl`. The separator is `_` because it sorts after `.`, so the bare name comes first. The naive scheme was wrong twice: `rename` replaces, so two rotations in the same second overwrote each other (the reason for no-replace semantics) (**3960–3979 of 4000 records lost**); and s1-mcp's `-N` suffix sorts wrongly (`…Z-1.jsonl` < `…Z.jsonl`, `-10` < `-2`).
6. **Repair and rollback of partial writes.** Under the lock, record the length before writing; if the write fails part-way (for example `EFBIG`), `set_len` back to it and return the error. Otherwise the next record is glued onto a half line and both are unreadable. Each line is written as one `write(2)` of `line + '\n'`. Under the directory lock, an unterminated tail left by a killed writer is detected and a leading newline is included in that same write. The damaged record remains invalid, but subsequent records remain intact; the repair byte counts toward the rotation limit.
7. **One lock handle per directory per process.** `flock` locks belong to the open file description, so a second handle in the same process blocks on the first. The handle lives inside the shared writer (`Arc`); a second `open` of the same directory in the same process shares it or fails clearly, and never deadlocks.
8. **Pruning** runs after a rotation and once per process at open. Prune errors are ignored and never fail an append. (Amendment 3, Proposed: pruning also runs at open when only a count cap or a total cap is set, not only when an age is set, and it applies all configured limits in the order of decision 19. A prune error still never fails an append, but an unmet cap is reported once per process, decision 20.)
9. **Local filesystems only.** `flock` and `O_APPEND` atomicity are not reliable over NFS; a state directory on NFS is unsupported and documented as such.
10. **Files and directories** are created `0600` and `0700`.
11. **Signal names** are restricted to `[a-z0-9_]+`, so a signal can never contain the `-` or `.` separators the segment names rely on.
12. **Lock-free reader retries.** `read_since` and `find_newest` take no lock. They list segments, copy records, and re-list; changed segment paths or a changed live device/inode trigger a retry. After eight attempts, `read_since` returns only the final copy's rotated-file prefix, excluding the live tail so it cannot skip intervening segments. This best-effort prefix may omit recent records, and pruning may remove retained records during copying. `find_newest` returns its final best-effort candidate on exhaustion. `find_newest` searches newest-first and stops reading files at the first match; its callback may run again on the same line after a retry. `segments` and `segments_since` return listing snapshots whose paths may change after return. A stopped reader cannot hold up a writer.
13. **Blocking writer locks.** Writers use blocking `File::lock` (a kernel wait, without polling or a timeout) so healthy contenders are not starved by polling. After a wait over ten seconds, one stderr warning per process names the directory. A stopped or hung lock holder can block writers; the batch queue filling is already reported on stderr. Warnings do not abort writes, and failed stderr writes are ignored.
14. **Separate file boundaries.** A rotated segment may end with an unterminated fragment from a killed writer. Readers and shippers must process each file separately; naive `cat seg1 seg2` can glue that tail to the next segment's first record. The Collector processes files separately.
15. **Reader helpers** shipped with the writer (#4): `segments` (oldest to newest, live file last), `segments_since` (mtime window), `read_since`, and `find_newest` (newest-first search).

### Amendment 3 (Proposed): bounded disk use ([#163](https://github.com/vig-os/vigil/issues/163))

**Why.** A long-running multi-process consumer needs a firm upper bound on disk use. Decisions 1 and 2 bound each file and the *age* of a segment, not their number, so a busy fleet writes many GiB inside 90 days (OWASP Logging Cheat Sheet, Verification: logging must not be able to fill the disk; NIST SP 800-92 §5.1.2: define what happens when storage is full). Consumers that delete segments themselves race with rotation in other processes, because they do not hold the directory lock. The consumer's contract in #163 is the design input:

| Signal | Size per file | Rotated files | Age |
|---|---|---|---|
| logs | 16 MiB | 4 | 14 d |
| traces | 32 MiB | 4 | 7 d |
| metrics | 8 MiB | 2 | 30 d |

plus a total cap of 512 MiB that deletes the oldest rotated files first.

**Binding constraints** (architect rulings on #163; each decision below keeps them, and the tests of "Acceptance evidence" check them):

1. Additive and non-breaking: new methods on `RotationConfig` and `Config`, one new type, no changed default (decision 16).
2. Enforced only at the existing prune points (after a rotation, once per process at open), under the directory lock, oldest rotated segments first, never the live file (decisions 19 and 20).
3. Audit-trail files are never deleted by these caps (decision 21).
4. Environment equivalents follow the existing `VIGIL_*` grammar, and an invalid value warns once (decision 23).
5. The worst-case disk-use formula is decision 22; the README states it verbatim.
6. The test strategy includes a multi-process bound check at every prune point (Acceptance evidence, "Amendment 3").

16. **Two optional caps, both off by default.** `max_segments(Option<usize>)` limits the number of *rotated* segments of one signal (the live file is not counted). `max_total_bytes(Option<u64>)` limits the bytes of all telemetry files in the directory (decision 17). Both default to `None`, so behaviour with no new setting is exactly decisions 1 to 15 (OQ1). When both are set, **both apply**: the stricter one deletes more. They combine with age (decision 19), not instead of it. **Zero is honoured, never clamped** (ruling 163-d1, OQ4): `max_segments(Some(0))` and `VIGIL_MAX_SEGMENTS=0` mean "keep no rotated segments" (every rotated segment is pruned at each prune point; the live file is never deleted); `max_total_bytes(Some(0))` and `VIGIL_MAX_TOTAL_BYTES=0` mean "the total is always over the cap", so every rotated segment is pruned at each prune point. `None` or an unset variable means unlimited. This is the opposite of `VIGIL_RETENTION_DAYS=0` (keeps everything), the pair of zeros ADR-0004 decision 6 warns about, so the rustdoc of every method and the README table state both side by side. `retention(Some(Duration::ZERO))` is **not** an equivalent of `max_segments(Some(0))`: the age test keeps a segment whose mtime is in the future (`src/rotate.rs:843-844`, `duration_since(..).ok()` is `None`), the count cap does not look at mtime. `max_bytes` still clamps 0 to 1 (a file must hold a line). Both caps count bytes and segments **as listed** at the prune point, so a segment that an external cleaner removed is simply absent.
17. **The total cap is one budget over all telemetry signals, deleting oldest first by a cross-signal order.** It covers every signal in the directory that matches decision 11's grammar (`logs`, `metrics`, `traces`, and any other `RotatingFile` signal opened there) except the reserved `audit` (decision 21) (OQ2). Segments of all those signals are ordered by `(stamp, signal, counter)`, where `stamp` is the fixed-width UTC stamp of decision 5, compared as a string, and `counter` as an integer (OQ6). **The order is weaker than it looks, and the amendment says so** (ruling 163-d1, OQ6). Within one signal the name stamp is monotonic: the stamp and counter logic never produce a name that sorts before an existing one of the signal (`src/rotate.rs:636-641`, `763-766`; decision 5). Across signals the stamp is the rotating process's wall clock, so it is chronological only while clocks do not step back, and a signal whose whole rotated history was pruned has lost its monotonic baseline (its next stamp is whatever the clock says). Ties break by the key above: equal stamps by signal name, then counter. **The order decides only *which* segment is pruned, never *whether* the bound holds:** the total step deletes until the byte condition is met, in whatever order, so a clock step can make vigil delete a newer segment before an older one but cannot make the disk use exceed decision 22. The budget **reserves the live files at their limit**: the counted size is `rotated bytes + Σ over signals with a live file of V_s`. For the signal being pruned, `V_s = max(M_s, live_len + pending_len)`, where `pending_len` is the length of the write that triggered the prune (the line plus its newline and a repair byte, if any; `0` at open) and `live_len` is the live file's length after a rotation (`0`) or before the write when none happened. For every other signal, `V_s = max(M_s, current length of its live file)`. `M_s` is the signal's `max_bytes` as the pruning process resolves it (decision 18). The pending length is what makes the cap hold for **any line length** (ruling 163-d1, blocker 2): a line larger than `M_s` is written alone into a fresh file (decision 1) *after* the prune, so a reservation without it would let the live file exceed its reservation by the whole line (probe: `M = 1 MiB`, `T = 10 MiB`, repeated 4 MiB records). **The prune point must therefore see the pending length and must run whenever `live_len + pending_len > M_s`, not only after a rotation.** Today `append_with` prunes only inside the rotation branch (`src/rotate.rs:445-448`) and calls `prune_at(&dir, &self.signal, keep)` without the pending length, although `buf.len()` is in scope there; and when the live file is empty and the line is oversized there is no rotation and so no prune at all (`src/rotate.rs:443`, `len > 0`). The implementing slice moves the prune call to after the rotation decision and before the write, passes `buf.len()` (plus the repair byte), and runs it also in the empty-live-file case when `pending_len > M_s`. Without the reservation the live files would grow past the cap between prune points and `max_total_bytes` would not be a bound at all (OQ3). A signal whose live file does not exist is not reserved until `open` creates it (`open` prunes, decision 8).
18. **Per-signal overrides are an additive type plus builder methods.** All signatures, with the derives and auto traits the rules of ADR-0004 decision 5 require (private fields; `Debug + Clone + PartialEq + Eq + Default`; **not `Copy`**; `Send + Sync`; every method `#[must_use]`):

    ```rust
    // vigil::rotate
    impl RotationConfig {
        /// Cap on rotated segments per signal; None = unlimited (default). Some(0) keeps no rotated segment.
        pub fn max_segments(self, segments: Option<usize>) -> Self;
        /// Cap on the bytes of all telemetry files in the directory; None = unlimited (default).
        /// Some(0) prunes every rotated segment at each prune point.
        pub fn max_total_bytes(self, bytes: Option<u64>) -> Self;
        /// Override size, count and age for one signal; replaces an earlier override of that signal.
        pub fn signal(self, signal: crate::Signal, rotation: SignalRotation) -> Self;
    }

    /// Per-signal overrides of the three per-signal limits. Each field is "not set" (inherit the
    /// RotationConfig value) or an explicit value, and an explicit `None` is not "not set".
    #[derive(Debug, Clone, PartialEq, Eq, Default)]
    pub struct SignalRotation { /* private: Option<u64>, Option<Option<usize>>, Option<Option<Duration>> */ }
    impl SignalRotation {
        pub fn new() -> Self;                                   // all inherited
        pub fn max_bytes(self, bytes: u64) -> Self;             // clamps 0 to 1
        pub fn max_segments(self, segments: Option<usize>) -> Self; // Some(0) keeps none
        pub fn retention(self, retention: Option<Duration>) -> Self;
    }

    // vigil::Config (src/init.rs), same names and zero rules as RotationConfig, stored "not set" apart from "set to None"
    impl Config {
        pub fn max_segments(self, segments: Option<usize>) -> Self;
        pub fn max_total_bytes(self, bytes: Option<u64>) -> Self;
        pub fn signal_rotation(self, signal: crate::Signal, rotation: SignalRotation) -> Self;
    }
    ```

    `RotationConfig` keeps private fields, so new fields are not breaking; it keeps `Eq` by storing the overrides as a fixed array indexed by a private `Signal` match (one slot per variant, no map keyed by the non-`Ord` `Signal`, so equality does not depend on call order, and a new `Signal` variant fails to compile there until it gets a slot). `Signal` is `#[non_exhaustive]` and has only the three vigil signals, so `RotationConfig::signal` covers them; a custom `RotatingFile` signal uses the `RotationConfig` values. A string-keyed override for custom signals is not offered: no consumer has one, and it can be added later as a new method without breaking anything. `RotatingFile::open(dir, "logs", cfg)` resolves `cfg` for its own signal name at open: the effective `(M, K, retention)` is the override if set, else the `RotationConfig` value, else the default. The resolution function is also what the total cap uses for `M_s` of the other signals (decision 17). `Config` hands one `RotationConfig` (with the overrides) to all three signals, as it hands one clone today (ADR-0003 decision 1, whose "`max_bytes` and retention apply to each file separately" stays true: each file now resolves its own). The `Config` and `RotationConfig` rustdoc state the zero rules of decision 16 and the order of decision 19. ADR-0004's API table gets these rows when the slice lands.
19. **Order and algorithm of a prune pass.** One pass runs after a rotation and at open (decision 8), always with the directory lock held, by the handle of one signal `s` with its resolved limits. Steps, in this order, all deleting with the locked directory descriptor (`unlinkat`), none touching `<signal>.jsonl` or any name outside decision 11's grammar:
    1. **Age** (existing): delete the rotated segments of `s` whose mtime is older than `retention_s`.
    2. **Count**: if `K_s` is set, delete the oldest rotated segments of `s` (by `(stamp, counter)`) until at most `K_s` remain.
    3. **Total**: if the total cap `T` is set, list the rotated segments of all telemetry signals once, `stat` each for its size, and delete the oldest by decision 17's order until `rotated bytes + Σ V_s ≤ T` or none is left (`V_s` with the pending length, decision 17).

    Age runs first because it is the cheapest, already tested and the policy a human reasons about ("nothing older than 14 d"); count and total only remove what age left. The order is fixed so that the surviving set is deterministic and a test can pin it. Each pass lists the directory once per step that needs it; the total step needs one `stat` per telemetry segment, so a pass is linear in the number of segments (Consequences).
20. **A prune that fails partway, and a cap that cannot be met.** Prune errors never fail an append (decision 8), and no step stops at the first error. `unlinkat` returning `ENOENT` counts as deleted (someone else removed it); any other error leaves the segment counted and the pass continues with the **next oldest**, so the bound is met by deleting what can be deleted, oldest first among those. When a pass ends with a cap unmet (`> K_s` rotated segments of `s`, or `rotated bytes + Σ V_s > T`), the process writes **one stderr warning per cap kind per process**, `vigil: cannot meet max_segments=<K> in <dir>: <n> rotated segments remain` or `vigil: cannot meet max_total_bytes=<T> in <dir>: <R> rotated bytes remain and the live files reserve <V> bytes`, and keeps going; the next pass tries again. A cap that is *met by deleting* is the configured policy and prints nothing, even at every rotation. **The live file is never deleted, so a total cap below `Σ V_s` cannot be met:** every rotated segment is deleted at each pass (the segment just rotated included) and the disk bound is `Σ V_s`, which is why decision 22 states `max(T, Σ V_s)`. The warning is the documented signal of that misconfiguration; there is no error, because the caps may come from the environment (decision 23). A crash or kill between a rotation and its prune, or a failed `unlinkat`, leaves the excess until the next pass that covers it: the same signal's next rotation or any process's open of that signal for age and count, any signal's pass for the total. The bound of decision 22 holds at every moment at which every prune that started has deleted what the caps require.
21. **Audit data never counts and is never deleted.** The audit trail is a separate lifecycle (ADR-0005 decision 2 and amendment 10: sealed segments are archived by the operator, and deleting one is a prefix deletion the verifier reports). By default it lives in `<state dir>/audit/`, a different directory with its own lock, which these caps never open. If `AuditConfig::dir` points an audit trail at the telemetry directory, its files `audit.jsonl` and `audit-<stamp>[_NNNNNN].jsonl` match decision 11's grammar, so the rule is explicit: the signal name `audit` is excluded from the listing of every step of decision 19, exactly as `validate_signal` already reserves it, and so are dot-files (`.audit-next.jsonl`, `.audit-resume.jsonl`, ADR-0005 decision 8). Audit bytes are **not counted** in the total cap and **not reserved**: the disk bound of decision 22 is for telemetry and the audit trail's size is added by the operator who shares the directory (its growth is bounded only by the operator's archiving). A caller who needs one budget for both puts the audit trail in its own directory on its own quota. Foreign files in the directory are not vigil's and are neither counted nor touched.
22. **Worst-case disk use** (the README states this, with the numbers of the consumer's contract as its example). The bound is on **logical bytes**: the sum of `st_size` over the live files, the rotated segments and the unlinked-but-open segments (rulings 163-d1 and 163-d2); see the retained-handle term and the paragraph on filesystem allocation below. It is not a bound on blocks allocated. Write `F_s = max(M_s, l_s)`, where `l_s` is the longest line (with its newline) ever written to signal `s` in this directory (`l_s ≤ 1 048 576` for vigil's own exporters, which bound a line to `max_line_bytes ≤ 1 048 575`, ADR-0003; a `RotatingFile::append` caller counts its own), and `S` for the telemetry signals with a live file in the directory. At every moment at which no prune is unfinished (decision 20), the **visible** telemetry bytes `D` (live files and rotated segments) are at most (a) with **no new cap**: unbounded, limited only by the write rate times the retention age (decision 2), plus `Σ_S F_s` for the live files; this is today's behaviour and is stated as such; (b) with a **count cap `K_s` for every signal in `S`**: `D_count = Σ_S (K_s + 1) · F_s` (`K_s` rotated segments plus the live file; `K_s = 0` gives `F_s`); (c) with a **total cap `T`**: `D_total = max(T, Σ_S V_s)` with `V_s` as in decision 17, hence `≤ max(T, Σ_S F_s)` (the live files cannot be deleted; `T` already includes their reservation, and the pending-length rule of decision 17 is what makes this hold for any line length); (d) with both: `min(D_count, D_total)`; if some signal in `S` has no `K_s`, `D_count` is not a bound and `D_total` applies alone.

    **Retained-handle term** (rulings 163-d1 and 163-d2). A writer caches its live-file handle until its next append (`src/rotate.rs:152-176`, `336-342`, `435`: `refresh` compares `(dev, ino)` only under the lock of the next write). When another process rotates and prunes, a segment that the cached handle still refers to is unlinked but stays open, and its bytes stay on disk until the handle closes. **The unit is the writer instance, not the process:** `RotatingFile::open` (`src/rotate.rs:388-399`) creates an independent writer with its own handle every time, so one process can hold many idle writers on one signal. Let `W_s` be the number of open writers on signal `s`, summed over every process that shares the directory, whether opened by `init` (through its `Guard`) or by `RotatingFile::open`. Each writer retains **at most one unlinked segment**, of at most `max(M_s, l_s)` bytes (`F_s`, above; `l_s` is the longest line, `L_max,s`). The **logical bytes** of unlinked-but-open segments are therefore at most `R = Σ_s W_s · max(M_s, l_s)`, and the total is `D_logical ≤ D + R`. **Release points:** the writer's next append (the inode check reopens the live file), the drop of that `RotatingFile` (for `init` writers, the drop or shutdown of the `Guard`), or process exit. A writer that never appends again retains until then. `init` opens exactly one writer per enabled signal per process, so for `init` users `W_s` equals the number of processes with that signal enabled and `R = W · Σ_S F_s` for `W` processes. No writer change hides this: closing handles on a timer would race with the inode recheck of decision 4, and the cost is bounded and documented.

    **Filesystem allocation is not bounded.** The contract counts file lengths. A file can use up to one filesystem block more than its length (a 2-byte file occupies one 4096-byte block), plus filesystem metadata and any preallocation or delayed allocation the filesystem does. vigil does not bound that and does not claim to. An operator sizing a volume adds `F · B` to the formula, where `F` is the file count it implies (live files + rotated segments + retained segments: `|S| + Σ_S K_s + Σ_s W_s` with count caps) and `B` is the block size, and leaves the metadata margin the filesystem needs.

    Rotation in flight costs no extra *visible* bytes: the rename moves bytes from the live file to a rotated segment and the new live file is empty, so the bytes are unchanged until the prune that follows in the same critical section deletes some (`K_s + 1` rotated *files* exist for that moment, which matters for inode limits, not bytes). The formula assumes (a) every writer of the directory runs the same limits; with differing limits each process prunes to its own and the bound is the largest of them (the directory then depends on who pruned last, which vigil does not support), (b) `M_s` held when the segments were written (after `max_bytes` is lowered, older segments are larger until they age out or are deleted by a cap), (c) the filesystem keeps only the bytes it is told to (sparse files, block rounding and the directory entries are not counted), (d) local filesystems (decision 9). Example, the consumer's table (every `M_s` exceeds a 1 MiB line, so `F_s = M_s`): visible `16·5 + 32·5 + 8·3 = 80 + 160 + 24 = 264 MiB` by count, `max(512, 56) = 512 MiB` by total, so `D = 264 MiB` and the total cap never deletes anything. **Counting unlinked-but-open segments** for an `init`-only consumer (one writer per signal per process, so `W_s = W` processes), each process adds up to `16 + 32 + 8 = 56 MiB`, so `D_logical ≤ 264 + 56·W` MiB: 376 MiB for 2 processes, 712 MiB for 8; the README states the formula and tells the consumer to insert their process count (the #163 text gives none). A consumer that also opens `RotatingFile`s itself counts each as one more writer of its signal. With vigil's defaults and a 512 MiB total cap, `Σ F_s = 150 MiB` of live reservation leaves 362 MiB for rotated segments, about seven 50 MiB segments across all three signals (plus `150·W` MiB of unlinked-but-open segments, worst case).
23. **Environment variables follow the existing grammar** (`VIGIL_*`, whole numbers, an empty value is unset, an explicit builder value beats the environment, an invalid value warns once on stderr naming the variable and value and uses the default; `number(key, minimum)` in `src/init.rs`, the same helper that warns for `VIGIL_MAX_BYTES`). The warning is printed when the configuration is built, so once per variable per `init` or `layer`:

    | Variable | Meaning | Minimum |
    |---|---|---|
    | `VIGIL_MAX_SEGMENTS` | `max_segments` for every signal; `0` keeps no rotated segment | 0 |
    | `VIGIL_MAX_TOTAL_BYTES` | `max_total_bytes`; `0` prunes every rotated segment at each prune point | 0 |
    | `VIGIL_LOGS_MAX_BYTES`, `VIGIL_METRICS_MAX_BYTES`, `VIGIL_TRACES_MAX_BYTES` | that signal's `max_bytes` | 1 |
    | `VIGIL_LOGS_MAX_SEGMENTS`, `VIGIL_METRICS_MAX_SEGMENTS`, `VIGIL_TRACES_MAX_SEGMENTS` | that signal's `max_segments`; `0` keeps none | 0 |
    | `VIGIL_LOGS_RETENTION_DAYS`, `VIGIL_METRICS_RETENTION_DAYS`, `VIGIL_TRACES_RETENTION_DAYS` | that signal's retention in whole days; `0` keeps everything, as `VIGIL_RETENTION_DAYS` | 0 |

    Unset means unlimited and there is no "unlimited" spelling, because unlimited is the default; one is needed if a default cap is ever set ([#168](https://github.com/vig-os/vigil/issues/168)). Beware the zeros: `VIGIL_RETENTION_DAYS=0` keeps everything, `VIGIL_MAX_SEGMENTS=0` keeps no rotated segment (decision 16). The names do not collide with `VIGIL_METRICS`, `VIGIL_TRACES` and `VIGIL_METRICS_INTERVAL`, which are exact names. **Precedence, per option, most specific first within a source, builder before environment** (OQ5): `Config::signal_rotation` value, then `Config::max_*`/`retention`, then `VIGIL_<SIGNAL>_*`, then `VIGIL_*`, then the default. So a builder value for the whole `Config` still beats an operator's per-signal variable, as every builder value beats the environment today (ADR-0004 decision 6). The rustdoc of each builder method names its variables, and the README table lists them.

**Open questions**, each with the option applied above. The architect ruled on them in ruling 163-d1 (PR #169); the text states each ruling. The implementing slice flips the amendment to Accepted.

- **OQ1, defaults.** Accepted (ruling 163-d1): both caps stay `None`. Options were (a) keep unbounded (**applied**), (b) a default total cap, (c) a default count per signal. A default cap deletes telemetry a Collector may not have shipped yet (ADR-0006); the pre-1.0 default is [#168](https://github.com/vig-os/vigil/issues/168). The README says the default is unbounded within the age.
- **OQ2, scope of the total cap.** Accepted without an isolation claim (ruling 163-d1): (a) one global budget, ordered across signals (**applied**). **A count cap is a per-signal ceiling, not a floor, and nothing isolates a quiet signal:** under total-cap pressure the global pass can prune a quiet signal's rotated history completely (its live file never). A per-signal floor is out of scope; a consumer that needs isolation uses a separate directory per signal, or per-signal total budgets in a later amendment (no consumer in #163 asks for it, so no issue is filed). Rejected: (b) per-signal byte budgets (no single quota knob), (c) a floor (makes the cap unmeetable in more cases, decision 20).
- **OQ3, do live files count in the total?** Accepted, corrected (ruling 163-d1): (a) yes, reserved at their limit, and for the writing signal at `max(M_s, live_len + pending_len)` (decision 17), plus the retained-handle term `R` for logical bytes (decision 22) (**applied**). Rejected: (b) rotated segments only (the bound would be `T + Σ F_s` by hand), (c) current length (not a bound, files grow after the prune).
- **OQ4, zero values.** The first draft's rule (clamp) was **rejected** (ruling 163-d1): zero is honoured (decision 16). Applied: `Some(0)` and `0` mean "keep none"/"always over the cap"; `None`/unset is unlimited; the README states the opposite zero of `VIGIL_RETENTION_DAYS`.
- **OQ5, precedence.** Accepted: (a) specificity within a source, and a builder value beats the environment (**applied**): `signal_rotation`, `Config::max_*`, `VIGIL_<SIGNAL>_*`, `VIGIL_*`, default. Rejected: (b) specificity across sources, which gives "a builder value beats the environment" an exception that ADR-0004 decision 6 does not have.
- **OQ6, order key across signals.** Rejected as written (ruling 163-d1) and replaced by the weaker, explicit order of decision 17: stamp, then signal name, then counter; monotonic within a signal, wall-clock across signals; it decides only which segment is pruned, never whether the bound holds. Rejected: mtime across signals (a `stat` more and many ties on coarse filesystems, and no better under a clock step).

### Acceptance evidence

The acceptance test is a **multi-process** test, not a thread test: the test binary re-executes itself as N ≥ 4 children, each writing M records with a tiny `max_bytes` that forces many rotations. It asserts every record appears exactly once across all segments, every line is whole, no segment exceeds the limit except single oversize lines, and no segment name collides. It sits beside targeted tests for each probe above (same-second rotation, name order, stale-inode reopen, retention with set mtimes, `None` keeps, partial-write rollback via a test seam, second `open` not deadlocking). Tests write only under `std::env::temp_dir()`, since `HOME` is unwritable in the Nix sandbox.

**Amendment 3 (Proposed): evidence the implementing slice must deliver.** One test per rule; none asserts on wall-clock time, and a test of new API fails before the change as a compile error. Segment ages are set with explicit mtimes, as the retention tests already do.

1. **Multi-process bound (constraint 6).** The test binary re-executes itself as N ≥ 4 children writing M records to the three signals with a tiny `max_bytes`, a count cap and a total cap, so rotations overlap. A crate-private seam, `prune_at_observed(..., observe)` (the pattern of `append_with`, which injects the write step), calls `observe` at the end of every prune pass **while the lock is still held**, and each child asserts there: per signal at most `K_s` rotated segments, `rotated bytes + Σ V_s ≤ T` or no rotated segment left, no live file missing, the seeded audit files are byte-identical, and **logical bytes** (item 9) are within decision 22's `D + R`. **Ordering is asserted per deletion policy, not globally** (ruling 163-d1, blocker 3): age and count pruning delete oldest first **within the signal** (by `(stamp, counter)`); the total step deletes oldest first by decision 17's cross-signal key, as far as the key is monotonic. The bound itself is asserted at every prune point regardless of order, so a clock-step fixture (a segment of another signal seeded with an earlier stamp) can change which segment goes but never fails the bound. Holding the lock makes the check race-free, so it is deterministic: it needs no sleep and no observer thread. The parent then asserts the end state, that every child exited 0 (an assertion in a child is exit 101), and that every record that is still on disk is whole and appears once (decision 1 to 6 evidence, unchanged).
2. **Oldest first per policy, never the live file:** a cross-signal test for the total step with segments of three signals interleaved by stamp, equal stamps (signal then counter tie-break) and a counter wider than 6 digits; the live files of all signals survive a cap of 1.
3. **Order of limits:** a fixture where age, count and total each delete a different segment, and the surviving set is asserted; then each cap alone.
4. **Reservation:** a live file at its limit plus rotated segments exactly at `T` keeps them; one byte less deletes the oldest; a live file longer than `M_s` raises `V_s`.
5. **Unmet caps:** `T` below `Σ V_s` deletes every rotated segment, keeps every live file and warns exactly once per process (child process, stderr, checked for `"1 passed;"` through the shared helper); an injected `unlinkat` failure (a seam, as for the partial write) on the oldest segment leaves it counted, deletes the next oldest, warns once, and the next pass deletes it once the failure is gone.
6. **Audit:** `audit.jsonl`, `audit-<stamp>.jsonl`, `.audit-next.jsonl` and a foreign file in the directory are neither counted nor deleted under a cap of 1 byte.
7. **Open:** a process that only opens, with only a count cap or only a total cap set, prunes (today only an age prunes at open).
8. **Configuration:** `max_bytes(0)` clamps to 1 while `max_segments(Some(0))` and `max_total_bytes(Some(0))` are honoured (and `retention(Some(Duration::ZERO))` keeps a future-mtime segment that `max_segments(Some(0))` deletes), `SignalRotation` "not set" versus explicit `None`, override replacement, `PartialEq` independent of call order, the five-level precedence of decision 23, each of the eleven variables (valid, empty, invalid warns once and uses the default, below the minimum), and per-signal `max_bytes` actually rotating at that size.
9. **Retained handles and long lines (rulings 163-d1 and 163-d2):** (i) a deterministic fixture with **several writer instances in one process** (for example 16 `RotatingFile::open` writers on one signal, all idle after one append) **and several processes**, while another writer rotates and prunes under a cap that deletes their segments. The test measures **logical bytes only**: `st_size` of every visible file, plus `fstat` `st_size` of each handle held through the open writers (a test seam that reports the cached handle's `fstat`, or a fixture that holds the fd), and asserts `D + R` with `R = Σ_s W_s · max(M_s, l_s)` counted over writer instances. It asserts that the count is exactly `W_s`-per-instance, not per process (a per-process term fails), and that one append per writer releases its retained segment. No test asserts on `st_blocks`. (ii) the reviewer's case: `M = 1 MiB`, `T = 10 MiB`, repeated 4 MiB records from two processes, including into an empty live file: the visible bytes never exceed `max(T, Σ V_s)` at any prune point, which fails if the prune runs only inside the rotation branch or ignores the pending length. (iii) a clock-step fixture as in item 1.
10. **Public API:** `scripts/check_public_api.py` and cargo-semver-checks pass as a minor change; the new items appear in `api/public-api.txt`; `RotationConfig` and `SignalRotation` are `Send + Sync`, not `Copy`.
11. **Mutants** (each fails at runtime with exit 101, never a compile error; each is shown once, then reverted): delete the newest instead of the oldest; skip the reservation; let the total step delete a live file; count `audit-*` segments; run the total step before age; stop at the first failed `unlinkat`; skip the prune at open for caps; reserve without the pending length; prune only in the rotation branch; clamp `Some(0)` to 1; count retained handles per process instead of per writer instance; order by signal name before stamp; read `VIGIL_LOGS_MAX_SEGMENTS` into the metrics signal.

## Consequences

- Rotation uses atomic no-replace rename relative to the locked directory descriptor (`RENAME_NOREPLACE` on Linux, `RENAME_EXCL` on macOS); all critical-section file operations use that descriptor, so directory swaps cannot redirect an in-flight append. Only `EINVAL`, `ENOSYS`, `EOPNOTSUPP` or `ENOTSUP` enables the directory-relative link/unlink fallback, which requires hard-link support. A failed link preserves the live file; if unlink and undo both fail, the returned error names both failures. On the next lock acquisition, a multiply linked live file is unlinked and recreated only if a segment of the same signal in the locked directory shares its device and inode, preserving the data under that segment name. External backup links alone never trigger healing.
- Any number of local processes may share a state directory safely; the cost is one `flock` plus directory and live-file inode checks per write, serialised across all signals in the directory.
- Every rotation lists and sorts the directory, so rotation cost is linear in the segment count (amendment 3, Proposed: with a total cap a pass also `stat`s every telemetry segment of the directory, so the cost is linear in the segments of all signals; a count cap bounds that number, which is why the README recommends both). That is fine at the 50 MiB default; a tiny `max_bytes` with tens of thousands of segments is slow (a 48 000-segment stress run took about 10 minutes). Readers and shipping agents match only `<signal>.jsonl` and `<signal>-*.jsonl`.
- Timestamps in names are from the rotating process's clock; ordering by name is only as good as host clock monotonicity, and counters cover same-instant collisions.
- Retention is by file mtime, so a segment survives 90 days after its *last* write, not its first.
- Windows is out of scope.
- (Amendment 3, Proposed.) With a cap set, vigil deletes unshipped telemetry when it must: a Collector that is down while a cap is reached loses the oldest segments, silently, since a met cap is policy and not an error (decision 20). That is the answer to "what happens when storage is full" (NIST SP 800-92): the newest data survives, the live file is never deleted, and the audit trail is never touched. Operators who cannot lose telemetry size the cap above what they ship in an outage, or leave it off.
- (Amendment 3, Proposed.) Under a total cap a noisy signal can evict all of a quiet signal's rotated history (its live file is never deleted); the count cap is a ceiling, not a floor, and nothing isolates a quiet signal (OQ2). A consumer that needs isolation uses a directory per signal.
- (Amendment 3, Proposed.) The logical-bytes bound includes segments that another process unlinked while a writer still holds the handle, per writer instance (decision 22); filesystem block rounding and metadata are not bounded (decision 22).
- (Amendment 3, Proposed.) Differing limits across the processes of one directory are unsupported (decision 22, assumption a).

## Alternatives considered

- **An existing rotating-file crate:** not multi-process safe (see Context).
- **A logging daemon or single writer process:** adds a service every tool must find and survive.
- **A separate lock file:** the first design; a cleaner deleting it breaks mutual exclusion (decision 3).
- **Per-process files** (`logs-<pid>.jsonl`): avoids locking but multiplies files, breaks "one live file per signal" and the shipping story.
- **Lock the data file:** races with rename (decision 3).
- **`logrotate`/`newsyslog` externally:** per-host configuration, no guarantee against a writer holding the old inode, and no portable story for the fleet.
- **Trust `O_APPEND` alone:** atomic appends do not protect against writing into a renamed file (decision 4).
- **Consumers delete segments themselves** (amendment 3): runs outside the directory lock and races with rotation in other processes (#163).
- **Per-signal byte budgets instead of one total cap** (amendment 3): no single knob for the disk quota (OQ2).
- **A cap on rotated bytes only, live files unreserved** (amendment 3): not a bound without adding `Σ F_s` by hand (OQ3).
- **Deleting by mtime across signals** (amendment 3): one `stat` more per segment and many ties on coarse filesystems (OQ6).
- **A default cap now** (amendment 3): changes what existing users keep (OQ1, [#168](https://github.com/vig-os/vigil/issues/168)).
- **Reporting each cap-driven deletion on stderr or as a metric** (amendment 3): at a cap that is reached on every rotation it is noise, and a metric would make rotation depend on the metrics pipeline it feeds (ADR-0003). Only an unmet cap is reported (decision 20).
- **A new crate for disk quotas or `statvfs`-based free-space checks** (amendment 3): a free-space rule is about the host, not about vigil's footprint, and needs `unsafe` or a new dependency (`#![forbid(unsafe_code)]`).
