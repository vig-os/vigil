# ADR-0003: Metrics and traces

- **Status:** Accepted (2026-10-11)
- **Date:** 2026-10-11 (round 2: reconciled with the accepted ADR-0004, metric identity conflicts decided; round 3: Prometheus name collisions, instrument validation, cross-ADR loss rule)
- **Issues:** [#38](https://github.com/vig-os/vigil/issues/38) (this decision), [#7](https://github.com/vig-os/vigil/issues/7) (metrics), [#8](https://github.com/vig-os/vigil/issues/8) (traces), [#26](https://github.com/vig-os/vigil/issues/26) (log/span correlation), [#9](https://github.com/vig-os/vigil/issues/9) (`schemaUrl`), [#64](https://github.com/vig-os/vigil/issues/64) (key order); consistent with the accepted [ADR-0004](0004-public-api-and-stability.md) ([#37](https://github.com/vig-os/vigil/issues/37))

## Context

vigil 0.1 writes one signal: logs, through the `tracing` bridge, into `logs.jsonl` ([ADR-0001](0001-on-disk-format.md), [ADR-0002](0002-rotation-and-retention.md)). The 0.2.0 milestone adds `metrics.jsonl` and `traces.jsonl`. The path-to-1.0 pre-mortem (2026-10-10, risks R5, R6, R7) probed the upstream stack and found that it works end to end, with edges that must be decided before #7 and #8 are written.

The load-bearing claims were re-probed for this ADR on 2026-10-11 in a scratch crate (Rust 1.95, `opentelemetry`/`opentelemetry_sdk`/`opentelemetry-proto`/`opentelemetry-appender-tracing` 0.33, `tracing-opentelemetry` 0.34.0, otelcol-contrib 0.151.0 and Prometheus 3.12.0 from the flake's pinned nixpkgs). The probe wrote OTLP/JSON lines with `opentelemetry-proto`'s own transforms (as vigil's exporter does), fed them through the Collector's `otlpjsonfile` receiver and its `otlp_http` exporter into Prometheus' OTLP endpoint (`--web.enable-otlp-receiver`), and queried the result. Findings:

**Metrics.**

- **P1, cumulative works.** One producer, 20 adds over 11 periodic exports: Prometheus returned `vigil_requests_total{route="/x"} 20`, `vigil_latency_milliseconds_{sum,count} 285 / 20`, `vigil_inflight 0`, `vigil_memory_bytes 19456`, and `target_info`. The Collector logged no error. The final value arrived through the export on `shutdown()`.
- **P2, delta is rejected whole.** The same producer with `Temporality::Delta`: 10 of 11 lines failed with `HTTP Status Code 500 … "rejected_items": 4`, which is every metric in the batch, including the gauge and the up-down counter, which are not delta. `vigil_memory_bytes` never arrived. The pre-mortem saw the reason text `invalid temporality and type combination` and that `--enable-feature=otlp-deltatocumulative` accepts delta but loses samples (15/20).
- **P3, missing `service.instance.id` corrupts silently.** Two concurrent processes of one service, with no instance id, appending to one file (ADR-0002's premise): Prometheus kept **one** series and no error was logged anywhere. The samples interleave (`3, 3, 5, 5, 6, 7, …, 12, 12, 14, …, 20`), so the second process's 12 requests disappear from the total and `rate()` is meaningless. The pre-mortem saw a 400 plus 5 out-of-order samples for the same cause when the timestamps interleave the other way. With distinct `service.instance.id` values, the same run gave two exact series (20 and 12), labelled `instance="<id>"`. Prometheus maps `service.name` to `job` and `service.instance.id` to `instance`; other resource attributes (`process.pid`) appear only on `target_info`.
- **P4, a non-finite double drops every metric in the line, silently.** An `f64` gauge recording `NaN` serialized as `"asDouble":null`. The Collector dropped all 4 lines (counter and histogram included) and logged nothing at its default level. The same file with `"asDouble":"NaN"` (the proto3 JSON spelling) arrived complete: `vigil_memory_bytes NaN` and every other series correct. This is ADR-0001 decision 6 again, now for metrics.
- **P5, no runtime.** `PushMetricExporter::export(&self, &ResourceMetrics)` returns a `Send` future; `PeriodicReader` runs on its own thread (`OpenTelemetry.Metrics.PeriodicReader`), as do the batch span processor (`OpenTelemetry.Traces.BatchProcessor`) and the batch log processor. `From<&ResourceMetrics> for ExportMetricsServiceRequest` is public; its JSON is the `{"resourceMetrics":…}` shape of `MetricsData`. The largest line in P1 was 1 743 bytes for 4 instruments.
- **P6, test fixtures.** `ResourceMetrics` fields are `pub(crate)`. The sdk's `testing` feature exposes them but pulls in `tokio`, which `tests/deps.rs` forbids in `Cargo.lock`. The probe built real `ResourceMetrics` without it: a `SdkMeterProvider` with a `PeriodicReader` over the exporter under test, flushed by `shutdown()`.

**Traces.**

- **P7, the pin.** `tracing-opentelemetry` 0.34.0 (MSRV 1.75) is the only release on `opentelemetry` 0.33; `cargo tree -i opentelemetry` shows one copy. With `tracing-opentelemetry`'s `default-features = false` and the sdk features `logs`, `metrics`, `trace` (sdk default features kept), the only new crate in the tree is `tracing-opentelemetry` itself: no `tokio`, `tonic`, `hyper`, `tower`, `h2` or `reqwest`.
- **P8, correlation.** Log records emitted inside an entered span carry that span's `traceId`/`spanId`, which match the exported span. The appender reads `Context::current()`, which `tracing-opentelemetry` activates on span entry. Edge (a): `info!(parent: &span, …)` on a span that was never entered gets no trace context (probe: `span=None`).
- **P9, every event is also a span event.** With the layer unfiltered, each `info!`/`warn!`/`error!` inside a span is written twice: as a log record and as a span event (`inner: events=['inside inner', 'warn inner', 'error inner']`).
- **P10, dedup options, measured.**
  - A per-layer filter that lets only spans reach the OpenTelemetry layer removes all span events, but an `error!` inside a span no longer sets the span status: `status.code` stays `0` (Unset). `tracing-opentelemetry` sets `Error` only from ERROR-level events it sees.
  - Letting spans **and ERROR-level events** through keeps `status.code = 2`, but each error is still duplicated as a span event.
  - Spans and ERROR-level events through, **plus** the SDK span limit `max_events_per_span = 0`: no span events at all, `status.code = 2` on the failing span, and `droppedEventsCount = 1` on it, which honestly records that an error event existed.
  - Upstream's own mechanism, `OpenTelemetryLayer::with_counting_event_filter`, **prints `evaluating event with level INFO` to stdout for every event** in the released 0.34.0 (leftover `println!` calls in `FilteredOpenTelemetryLayer::on_event`; probe: 8 stdout lines for 6 events and 2 diagnostics). A library must never write to stdout: it is the protocol channel of an MCP stdio server such as s1-mcp, and the data channel of a CLI.
- **P11, span fields on log records.** With the appender's `experimental_span_attributes` feature and `with_tracing_span_attributes(TracingSpanAttributes::all())`, records inside `info_span!("outer", a = 1, session = "s-1")` and its child `inner` (`b = "x"`) carried `a`, `session` and `b`. It works without the traces signal (it reads the `tracing` registry, not OpenTelemetry). But an event field with the same name as a span field produced **duplicate keys** on one record (`[('a','1'), ('session','s-1'), ('a','2')]`), and the OTLP spec requires attribute keys to be unique. Upstream marks the feature experimental: "the API may change without a major version bump until it is stabilized" (appender CHANGELOG, 0.32.0).
- **P12, open spans at shutdown.** A span still entered when the providers shut down is never exported; `shutdown()` returns `Ok(())`. Its log record (`inside left_open`) points to a `spanId` that does not exist in `traces.jsonl`.
- **P13, default span attributes.** With default settings each span carries `code.file.path`, `code.module.name`, `code.line.number`, `thread.id`, `thread.name`, `target` and the non-semconv `busy_ns`/`idle_ns`. `OpenTelemetryLayer<S, _>` is generic over its subscriber position, so it has to be built for the exact position it is installed in (pre-mortem R7: E0277 when reused elsewhere).

- **P14, span extensions need direct installation.** `tracing_opentelemetry::OpenTelemetrySpanExt` finds the layer through `downcast_raw`. Probe (`src/bin/ext.rs`): with the layer installed as `Filtered` + `Box`, `span.context()` inside an entered span is valid; with the same layer in a `tracing_subscriber::reload` slot (the pattern `src/init.rs` uses for logs), it is invalid, because `reload::Layer` does not forward `downcast_raw` (tracing-subscriber 0.3.23 `reload.rs`). `vigil::propagation` uses those extensions internally (ADR-0004 decision 9), so the same holds for it.

**Metric identity (round 2).**

- **P15, SDK 0.33 does not handle identity conflicts, and vigil can.** Probe `src/bin/conflict.rs`: two `static`-style declarations named `app.x`, each bound on its own thread with a forced order (A then B, and B then A), each recording its own fixed values, then a flush. Each case ran on the raw SDK and through a stand-in of decision 21's mechanism.
  - Raw SDK, **same scope, different boundaries:** one stream, with the boundaries of whichever bound first (`bounds=[1.0, 10.0]` vs `[5.0, 50.0]` by order). Both declarations' values are merged into it.
  - Raw SDK, **same scope, names differing only in case** (`app.x` vs `App.X`): one stream, named after whichever bound first, so the bytes on disk depend on thread order.
  - Raw SDK, **same scope, descriptions differing only:** **two** streams with the same name in the same scope, each carrying its own description and its own values, the same in both orders. That is deterministic, but the two streams have the same name, scope and attributes, so a Prometheus backend sees one series: the description is metric metadata (`HELP`), never a label. Their samples would collide as in P3 (interleaved, or rejected as duplicates when they share a timestamp); this backend effect is inferred from the mapping, not probed. (A first version of the probe keyed its snapshot without the description and showed one stream; review caught it, and the corrected probe asserts that no two exported streams share a key.)
  - Raw SDK, **conflicts across scopes** (different boundaries, or different units) and **a counter and a histogram in one scope:** both streams are exported, every time, with no warning. That is two incompatible metrics of one name reaching Prometheus.
  - Raw SDK, **staged** (A bound and exported, then B bound): the first export has A; the second export has A *and* B. The SDK cannot unbind A; its cumulative stream keeps exporting (as ADR-0004's final review found).
  - Raw SDK, **across scopes, only the description or only the spelling differs:** two separate streams, the same in both orders (`crate-a:app.x` and `crate-b:App.X`), so nothing depends on order there.
  - Mechanism (decision 21's rule): in every conflict case above, the export after both bindings contained **no** `app.x` stream in either order, and exactly one diagnostic was produced, with identical text in both orders (for example, for the two-scope boundaries case, verbatim from the probe, which formats scope, name, kind, unit, description and boundaries: `vigil: conflicting metric instruments named "app.x": crate-a::app.x (histogram "ms" "" Some([1.0, 10.0])) vs crate-b::app.x (histogram "ms" "" Some([5.0, 50.0])); both dropped`; #7 chooses the final wording). Staged: the first export had A, the second had nothing of `app.x`, although the SDK still exported A's stream to vigil's exporter. Two declarations in different scopes that agree on kind, unit and boundaries stayed two streams in both orders, including when only their descriptions or spellings differ (ADR-0004 decision 8: not a conflict).
  - The number of measurements dropped varied with the order (2 or 3), because it counts the records that actually happened after the conflict was detected. It is exact for each run, not order-invariant.
  - The probe runs the two orders one after the other, held apart by a barrier. It shows that the outcome does not depend on order; it is not a race test. Races are excluded by construction in decision 21: binding and poisoning happen under one mutex, and the export filter removes a stream whose handle bound before the poisoning.
  - When only one of two conflicting declarations ever records, only that one is bound and it exports normally; which one depends on which one the program uses, not on thread order.
- **P16, key order depends on the consumer's build (#64).** Confirmed in the ADR-0006 review ([#64](https://github.com/vig-os/vigil/issues/64)): vigil builds lines through `serde_json::to_value`, whose maps are sorted by default and insertion-ordered when *any* crate in the build graph enables `serde_json/preserve_order` (Cargo unifies the feature). The same input then gives `{"description":"d","name":"n","sum":1}` or `{"name":"n","description":"d","sum":1}`. ADR-0001 decision 5's "equal input gives equal bytes" holds only by accident of the consumer's graph.

**Prometheus name collisions (round 3).**

- **P17, Prometheus collapses distinct OTLP streams silently.** Probe `src/bin/promcol.rs`: one process (`service.name=svc`, `service.instance.id=i-1`) recorded each scenario in two rounds one second apart (three exports: one per round and the final one at shutdown), through otelcol-contrib 0.151.0 (`otlpjsonfile` → `otlp_http`) into Prometheus 3.12.0 with default settings. In every case, the Collector and Prometheus logged 0 errors, and Prometheus kept one series per colliding pair:
  - **S1, two scopes, identical identity** (`crate-a` counter `app.x` +5 per round, `crate-b` counter `app.x` +7 per round): `app_x_total {} ['5', '10', '10']`. crate-b's 7/14 is gone. Prometheus' `otlp.promote_scope_metadata` defaults to `false`, so the scope is not a label and the two streams have one series identity.
  - **S1 with `otlp.promote_scope_metadata: true`:** two series, `app_x_total{otel_scope_name="crate-a"} ['5', '10', '10']` and `{otel_scope_name="crate-b"} ['7', '14', '14']`.
  - **S2, one scope, `app.x` vs `app_x`** (two SDK streams; +1 and +10 per round): `app_x_total {} ['1', '2', '2']`. The 10s vanish.
  - **S3, one scope, `app.x` in `ms` vs `app.x.milliseconds` without a unit** (+3 and +30): both translate to `app_x_milliseconds_total`; `['3', '6', '6']`, the 30s vanish.
  - **S4, one scope, histogram `app.y` vs gauge `app.y.count`** (gauge 42, then 84): `app_y_count {} ['1', '2', '2']` is the histogram's count; the gauge vanishes.
  - **S5, translation details, one scope:** counter `app.total.x` (+2) and counter `app.x` (+20): `app_x_total {} ['2', '4', '4']`, so the translator drops a `total` word and the 20s vanish; counter `app__y` → `app_y_total` (runs of underscores collapse); a gauge `app.r` with unit `1` → `app_r_ratio`.
  - So the OTLP names that decision 21 compares are not the names Prometheus stores. Its default translation (underscore escaping with unit and type suffixes) maps distinct OTLP names onto one series name, and a histogram expands into three (`_bucket`, `_sum`, `_count`).
- **P18, instrument validation can be compile-time.** OpenTelemetry's instrument-name rule (`[A-Za-z][A-Za-z0-9_.\-/]{0,254}`), the unit rule (ASCII, at most 63 characters) and histogram boundaries (finite, strictly increasing) can all be checked in a `const fn` on Rust 1.95, including `f64::is_finite` and `<`. Probe (scratch crate): `static GOOD: Histogram = Histogram::new("app.latency").with_unit("ms").with_boundaries(&[5.0, 10.0, 50.0])` builds; `Histogram::new("1app")`, `.with_boundaries(&[10.0, 5.0])` and `.with_boundaries(&[f64::NAN])` in a `static` each fail to compile, `error[E0080]: evaluation panicked: vigil::metrics: …` (exit 101). Without such a check, the SDK accepts the declaration and turns the instrument into a no-op, so its records are dropped with no count.

**Loki.** Loki's OTLP ingestion promotes `service.instance.id` to an index label by default, and Grafana's own documentation says it is "no longer recommended as a default label" because of cardinality, recommending structured metadata instead ([Loki OTel docs](https://grafana.com/docs/loki/latest/send-data/otel/)).

### Reconciliation with ADR-0004 (Accepted)

The first round of this ADR was written against assumptions A1–A5 about ADR-0004. ADR-0004 is now accepted, and its "Reconciliation with ADR-0003" list is applied throughout this revision:

- **A1, feature names:** confirmed. Features `metrics` and `traces`, both on by default; logs are always compiled (ADR-0004 decision 7).
- **A2, exporter visibility:** confirmed for stable builds. The metrics and span exporters and the shared line-bounding code are crate-private; only with the compiler cfg `--cfg vigil_unstable` (not a cargo feature) do they become public, next to `OtlpJsonLogExporter` (ADR-0004 decision 4).
- **A3, how code records metrics:** replaced. Applications record through the vigil-owned `vigil::metrics` facade (`Counter`, `CounterF64`, `UpDownCounter`, `Histogram`, `Gauge`), each instrument a `static` whose scope is its declaring crate (`vigil::scope!()`). Nothing from `opentelemetry` is in the stable API. Libraries record through `tracing` only, until an API-only crate exists ([#61](https://github.com/vig-os/vigil/issues/61)) (ADR-0004 decision 8). Identity conflicts between declarations are decision 21 below.
- **A4, configuration shape:** builder methods on `Config` with private fields, plus `VIGIL_*` variables (ADR-0004 decisions 5 and 6): `Config::metrics_interval(Duration)` / `VIGIL_METRICS_INTERVAL`, and the per-signal switches of decision 5.
- **A5, composition:** yes. `Config::layer()` builds the same three-signal pipeline as `init`, and its box contains the OpenTelemetry tracing layer whenever `traces` is compiled in, as `Filtered`, never in a `reload` slot (ADR-0004 decision 2).
- **No OpenTelemetry globals by default.** vigil installs no global meter or tracer provider, from `init` or `layer`. The only way is `Config::install_opentelemetry_globals` under `--cfg vigil_unstable` (ADR-0004 decisions 1 and 4).
- **Context propagation** is `vigil::propagation` (`inject`, `set_parent`, `trace_id`), with the nearest-recorded-ancestor rule as stable behaviour (ADR-0004 decision 9). No user-facing guidance names `OpenTelemetrySpanExt`.
- **"vigil's configured filter"** below (the first round said `RUST_LOG`) means `Config::filter_env` (default `RUST_LOG`) with `Config::default_filter` (default `info`) (ADR-0004 decision 2).

## Decision

### Shared

1. **One pipeline, three signals.** `vigil::init`, `Config::init` and `Config::layer` build the same pipeline: logs, plus metrics and traces when their features are compiled in and their switches are on (decision 5). There is one pipeline per process; a second `init` or `layer` returns `InitErrorKind::AlreadyRunning` before it creates any provider, file or thread, and `init` refused because another crate owns the global subscriber returns `ForeignSubscriber`, after shutting down the providers it built (ADR-0004 decisions 2 and 3). The signals share one state directory, one resource and one `RotationConfig`: `logs.jsonl`, `metrics.jsonl` and `traces.jsonl` are separate `RotatingFile`s under the one directory lock (ADR-0002 decisions 3 and 7; a second signal shares the process's lock). `max_bytes` and retention apply to each file separately.
2. **The exporter seam is the logs seam.** Each signal has an exporter, crate-private without `--cfg vigil_unstable` (ADR-0004 decision 4), that converts the SDK batch with `opentelemetry-proto`'s public transforms (`From<&ResourceMetrics>`, `group_spans_by_resource_and_scope`), then goes through the same pipeline as logs: deterministic ordering with a key order independent of the build graph (ADR-0001 decision 5, decision 22 here), non-finite sanitizing (decision 6), line bounding (decision 10), and `LineSink::write_line` into the signal's `RotatingFile`. The logs-specific bounding code in `src/logs.rs` is generalized over the three envelopes (`resource{Logs,Metrics,Spans}` → `scope…` → `logRecords` / `metrics` / `spans`). Signal-specific code is limited to: the shrink and drop rules (decisions 11 and 17); the fields that are sanitized for non-finite values (`doubleValue` in log bodies and attributes; `asDouble` and histogram `sum`/`min`/`max` in metrics; double attributes in spans); the log-record key dedup (decision 20); and the metric identity filter (decision 21).
3. **Losses are reported, never silent: as a value, and on stderr when nobody asks.** Losses are returned per signal by `Guard::flush` and `Guard::shutdown`/`shutdown_with_timeout` as `FlushError::lost(Signal)` (ADR-0004 decision 3), each in decision 23's unit. While the process runs, each signal's exporter wrapper (like `ReportingExporter` in `src/init.rs` today) also writes the first failure to stderr and then cumulative summaries at most once a minute, naming the signal and the unit (`vigil: runtime span export losses; dropped spans: N`). At the end, the final summary of not-yet-reported losses depends on how the pipeline stops. On **`Drop`**, it prints every signal's countable losses in that signal's `lost` unit (records, spans, measurements), plus the metrics data points of decision 23. An explicit **`shutdown`** returns the countable losses to its caller and does not print them again, so a loss is never reported twice at the same moment. It **still prints** the part that `FlushError` carries only as a kind, the dropped metric data points, because their number would otherwise appear nowhere. `flush` returns its counts and leaves the rate-limited runtime summaries as they are, since they serve operators of programs that never call `flush`.
4. **Shutdown: concurrent, one 5-second budget.** Dropping the `Guard`, or `Guard::shutdown`/`shutdown_with_timeout` (with its own budget instead of 5 s), first sets the existing `stopped` flag, so events, new spans and `vigil::metrics` records after that point are dropped with one stderr warning each kind (metric records are not counted, ADR-0004 decision 8). It then shuts down the three providers **concurrently**, each on its own scoped thread (`std::thread::scope`) with the same 5-second deadline, and waits for all of them. A sequential order cannot keep one budget: `SdkMeterProvider::shutdown_with_timeout` ignores its argument, and `PeriodicReader::shutdown` waits a fixed 5 s (`opentelemetry_sdk` 0.33 `metrics/meter_provider.rs`, `metrics/periodic_reader.rs`, "TODO: Make this timeout configurable"), so a metrics export blocked on the directory lock (ADR-0002 decision 13) would consume the budget of the signals after it. Concurrently, the worst case stays about 5 s for all three. A signal that misses the deadline gets its own stderr warning naming the signal. The three exporters serialize on the one directory lock, shared in-process through one handle (ADR-0002 decisions 3 and 7), so concurrency costs no correctness. **Each shutdown thread captures its own queue-overflow count:** `with_default` is thread-local, so the thread that calls `SdkLoggerProvider::shutdown_with_timeout` installs the capture for `BatchLogProcessor.LogsDropped` (`dropped_logs_count`), and the thread that calls `SdkTracerProvider::shutdown_with_timeout` installs one for `BatchSpanProcessor.SpansDropped` (`dropped_span_count`, emitted synchronously on that thread before the shutdown message, `opentelemetry_sdk` 0.33 `trace/span_processor.rs`). Both forward every other event to the dispatcher that was current on the calling thread (ADR-0004 decision 3). Both events exist only with the SDK's default `internal-logs` feature (`otel_warn!` compiles to nothing without it), which vigil keeps on. A unit test per signal pins the event name and field, so losing either fails CI. The metrics provider has no queue. With the `push` feature (ADR-0006, [PR #63](https://github.com/vig-os/vigil/pull/63), proposed), the push worker gets what remains of the same budget after this concurrent flush. The SDK's own shutdown diagnostics are `opentelemetry*` events, which go to stderr through the diagnostics layer, not into `logs.jsonl`.
5. **Per-signal switches and storage failure.** `Config::metrics(bool)` and `Config::traces(bool)` (default `true` when compiled in; environment `VIGIL_METRICS` / `VIGIL_TRACES`, `0` or `1`, explicit builder values win as for every option) turn a compiled-in signal off at runtime. If `metrics.jsonl` or `traces.jsonl` cannot be opened, that signal is disabled with one stderr warning, and the other signals continue. A disabled or switched-off metrics signal binds no instruments: `vigil::metrics` records are dropped without further reports (ADR-0004 decision 8). For traces, the layer stays installed (it is built before storage opens, decision 15), so propagation keeps working, and the exporter discards batches without further reports or counts. There is no stderr fallback for metrics or spans (unlike logs, they are not human-readable on a console).
6. **No OpenTelemetry environment configuration.** vigil sets every SDK parameter it relies on explicitly (export interval, batch sizes, queue sizes, span limits, sampler), so `OTEL_METRIC_EXPORT_INTERVAL`, `OTEL_BSP_*`, `OTEL_SPAN_*_LIMIT` and `OTEL_TRACES_SAMPLER` have no effect. vigil's configuration surface is `Config` plus `VIGIL_*` variables (ADR-0004 decisions 5 and 6), as for logs today. One source of truth per knob, and a test can pin the effective values.

### Resource

7. **`service.instance.id` on every signal.** When the pipeline is built (`init` or `layer`), vigil generates a random UUID v4 (lowercase, hyphenated, RFC 9562 version and variant bits) and adds it as `service.instance.id` to the one resource shared by logs, metrics and traces. The randomness comes from `getrandom` 0.3, which is already in `Cargo.lock` through `rand_core` (no new crate). The id is not configurable in 0.2.0. Existing attributes (`service.name`, `process.pid`, `host.name`, `service.version`, `vcs.ref.head.revision`) are unchanged. This changes the logs resource, so the logs golden files change with it, in #7.

### Metrics

8. **Cumulative only, and not configurable.** The exporter's `temporality()` always returns `Temporality::Cumulative`. There is no API, environment variable or feature that selects delta or low-memory temporality. A test asserts the temporality on every exported sum and histogram (`aggregationTemporality: 2`).
9. **Periodic reader.** One `PeriodicReader` on the SDK's own thread, export interval **60 s** by default (the OTel default), configurable with `Config::metrics_interval(Duration)` and `VIGIL_METRICS_INTERVAL` in whole seconds (minimum 1 s; a shorter builder value clamps to 1 s). The final export happens on shutdown; `Guard::flush` triggers a collect-and-export. The `SdkMeterProvider` is held by vigil's process-wide pipeline slot, which `vigil::metrics` instruments bind to (ADR-0004 decisions 2 and 8). It is **not** installed as the OpenTelemetry global, except under `--cfg vigil_unstable` with `install_opentelemetry_globals`.
10. **Aggregation defaults are upstream's and not exposed.** Explicit-bucket histograms with the SDK default boundaries unless the declaration sets its own with `Histogram::with_boundaries` (ADR-0004 decision 8); no views; no exponential histograms; the SDK's cardinality limit of 2 000 series per instrument, beyond which measurements go to one overflow series with `otel.metric.overflow = true`. Exemplars are not produced (the 0.33 SDK emits empty `exemplars` arrays).
11. **Bounding.** A line is split at metric boundaries, and a metric with more data points than fit is split at data-point boundaries, repeating the resource, scope and metric metadata (name, unit, description, temporality, monotonicity). An oversized single data point has its longest attribute string shortened, as for logs. If it still does not fit, the data point is dropped, reported on stderr in data points and flagged in `FlushError` without a count (decision 23). There is no stub data point, because a fabricated value would be wrong data. Non-finite doubles (`asDouble`, histogram `sum`/`min`/`max`) are written in the spelling the log exporter uses for non-finite values (ADR-0001 decision 6), which P4 shows the Collector and Prometheus accept.
12. **Prometheus name mapping, documented.** The README documents the mapping as observed with Prometheus 3.12's default OTLP translation (and confirmed by the pre-mortem on 3.15): `.` → `_`; monotonic counters get `_total` (`vigil.requests` → `vigil_requests_total`); units become suffixes (`ms` → `_milliseconds`, `By` → `_bytes`, so `vigil.latency` → `vigil_latency_milliseconds_{bucket,sum,count}`), and a gauge with unit `1` gets `_ratio`; runs of non-alphanumeric characters (including `_`) collapse into one `_`, and a counter's inner `total` word is dropped (P17, S5; decision 21 relies on these); up-down counters and gauges get no `_total`; `service.name` → `job`, `service.instance.id` → `instance`; every other resource attribute is on `target_info` only. **Prometheus must run with `otlp.promote_scope_metadata: true`**, so that each series carries `otel_scope_name` and `otel_scope_version` (and the scope's other promoted metadata) as labels. Without it, same-named instruments of two crates, which ADR-0004 decision 8 and decision 21 keep as two streams, collapse into one series and one crate's data is dropped silently (P17, S1). The README's Prometheus section and the shipping reference (ADR-0006, [PR #63](https://github.com/vig-os/vigil/pull/63)) state the setting as required, and #7's conformance test runs Prometheus with it and asserts two series for S1. The cost: a crate's version is a label, so a dependency upgrade starts new series (query with `sum without (otel_scope_version)`). Other Prometheus-compatible backends need their equivalent setting; the README says so. Collector configs in docs use the `otlp_http` exporter name (the `otlphttp` alias is deprecated in 0.151.0). #7's conformance test asserts these series names and values through the Collector and Prometheus.

### Traces

13. **Pin and upgrade policy.** `tracing-opentelemetry = { version = "0.34", default-features = false }` (no `metrics` layer, no `tracing-log` normalization). The `opentelemetry` crate family (`opentelemetry`, `opentelemetry_sdk`, `opentelemetry-proto`, `opentelemetry-appender-tracing`) and `tracing-opentelemetry` move together, in one PR, only once a `tracing-opentelemetry` release on the new `opentelemetry` minor exists. That PR passes the Collector conformance tests for all three signals and the stdout test (decision 15). Renovate groups them. Because no opentelemetry type is in vigil's stable API, such a bump is a vigil **minor** unless it changes bytes on disk, which ADR-0001's versioning stance then decides (ADR-0004 decision 1). Behaviour users write code against stays pinned across the bump by vigil's tests (decisions 14, 15, 20 and `vigil::propagation`): vigil translates an upstream change in its own code, or the bump waits for a vigil major.
14. **Layer configuration.** `OpenTelemetryLayer` with: location on (`code.*`) and threads on (`thread.*`), both semconv; `target` kept; tracked inactivity **off** (no `busy_ns`/`idle_ns`, which are not semconv); context activation on (required for P8); the error-mapping options at their defaults. Consequence of decision 15's span limit: `error_records_to_exceptions` puts `exception.*` on the **span** only for fields recorded as `&dyn Error`; the common `#[instrument(err)]` and `error = %e` forms are mapped by `error_events_to_exceptions` onto the span **event**, which the limit drops, so for them the span keeps `status.code = 2` (and, for a message-less `error = %e` or `#[instrument(err)]`, the status description), while the full error text is in the log record. For `error!(error = %e, "msg")` the field is an ordinary event attribute and the status description is empty. The special fields `otel.name`, `otel.kind`, `otel.status_code` and `otel.status_description` are documented as the way to set them. This field and error-status mapping is **stable behaviour**, pinned by vigil's tests across upstream bumps (ADR-0004 decision 1).
15. **Span-event dedup: logs are the only event stream.** The OpenTelemetry layer gets the same gates as the logs layer, plus one of its own: vigil's configured filter (so `debug_span!`/`trace_span!` from dependencies are not created as OTel spans at the default `info`), the `opentelemetry*` target exclusion, and the shutdown gate (sharing the logs gate's `stopped` and `warned` flags, so there is still one "event after shutdown" warning); then a filter that passes spans and ERROR-level events only. The tracer provider sets `max_events_per_span = 0`. Result (P10): `traces.jsonl` contains no span events; a span with an `error!` inside has `status.code = 2` (Error) and `droppedEventsCount` equal to the number of error events; every event is in `logs.jsonl` exactly once, with that span's ids. **Placement: installed directly, not through a `reload` slot.** `init` installs the subscriber before storage opens and fills the logs layer's `reload` slot afterwards (`src/init.rs`). The OpenTelemetry layer must not use that pattern: `reload::Layer` does not forward `downcast_raw`, so the layer's span extensions cannot be found, and `vigil::propagation`, which uses them internally, would silently produce no `traceparent` (P14). Instead, `init` and `layer` build the `SdkTracerProvider` before the subscriber exists (after the pipeline slot is reserved and, for `init`, after the `has_been_set` check; if `set_global_default` still fails, the providers are shut down and `init` returns `ForeignSubscriber`, ADR-0004 decision 3). The span exporter writes to a sink slot with three explicit states: **pending** (set when the provider is built), **ready** (`Arc<RotatingFile>`, shared as in ADR-0002 decision 7) or **disabled** (storage failed). `init` and `layer` both open storage synchronously and resolve the slot before they return; `layer` behaves exactly as `init` here, it only does not install the subscriber. Opening storage takes the directory lock (`RotatingFile::open`, ADR-0002 decision 3), so if another process holds the lock, `init`/`layer` blocks with it, as logs already do today, with ADR-0002 decision 13's stderr warning after 10 s. The wait is unbounded, like every writer's lock wait; while it lasts, the span batch thread waits on the pending slot, the span queue fills, and overflow is counted at shutdown (decision 4). A batch exported while the slot is pending (spans from other threads during `init`) waits on the slot (a `Mutex` plus `Condvar`) on the batch processor's own thread, so it is neither lost nor confused with a failure. In the disabled state the exporter discards batches without counting them as losses: decision 5's single warning covers the whole signal, and decision 3's summaries and decision 18's open-span report are suppressed. The layer is wrapped by the filters above as `Filtered` (which forwards `downcast_raw`), directly in `init`'s subscriber and inside the box `layer()` returns. #8 tests that `vigil::propagation::inject` writes a `traceparent` inside a recorded span after both `init` and `layer`, the nearest-recorded-ancestor cases of ADR-0004 decision 9, and that the parent span id `inject` writes equals the exported `parentSpanId` of a recorded child span. Span events, links and `add_event` are not in 1.0; the README says span events are not recorded (under `--cfg vigil_unstable`, events added through the re-exported `OpenTelemetrySpanExt::add_event` are dropped by the same limit). `with_counting_event_filter` is not used (P10). A test runs `init` plus events at every level and asserts that **nothing** is written to stdout, so a future upstream stdout leak fails CI.
16. **Sampling and limits.** Sampler `ParentBased(AlwaysOn)`, set explicitly: every span is recorded locally, and shipping decides volume (#8). Batch span processor with the same queue size as logs (`queue_size`, default 65 536), batch size 512, scheduled delay 1 s, and the SDK's other span limits (128 attributes, 128 links). The `SdkTracerProvider` is **not** installed as the OpenTelemetry global. Only under `--cfg vigil_unstable` with `install_opentelemetry_globals` (installed after `set_global_default` succeeds) do crates that use the `opentelemetry` tracing API directly write to `traces.jsonl`, and only if they are on vigil's opentelemetry minor; those spans bypass `tracing` and therefore vigil's filter, and get the same sampler, limits and loss reporting.
17. **Bounding.** As for logs: split at span boundaries; an oversized span has its longest attribute string shortened (with `vigil.truncated` and `vigil.original_size`); if it still does not fit, the span becomes a stub that keeps `traceId`, `spanId`, `parentSpanId`, `name`, `kind`, timestamps and `status`, with `vigil.dropped = true`. The stub is kept rather than dropped so log records that reference the span still resolve, and it counts as one lost span (decision 23).
18. **Open spans at shutdown are reported.** vigil cannot export a span that has not closed: the OpenTelemetry span only ends in `on_close`, and the `tracing` registry has no way to enumerate live spans. vigil counts spans that pass decision 15's filters and have not closed (a vigil layer behind the same filters, with one atomic counter, incremented on new span and decremented on close). Unless traces are disabled (decision 5), it reads the count when the shutdown of decision 4 begins (after the `stopped` gate, so no new spans start). If the count is non-zero it writes `vigil: N spans were still open at shutdown; spans that had not closed before the trace pipeline stopped were not exported, and log records may reference them`. N is exact at that instant. Some of those spans may still close and be exported while shutdown runs, so N is an upper bound on the spans lost; reading the count later instead would miss spans that closed after the trace pipeline stopped. This report goes to **stderr only**, also when `shutdown` is called explicitly; N is not added to `lost(Signal::Traces)`, because `lost` is a lower bound of spans certainly lost and N an upper bound of spans possibly lost, and adding them would make `lost` neither (decision 23). The rustdoc of `Guard::shutdown` says so. The README documents that root spans should end before the `Guard` is shut down.
19. **Explicit parents (edge a) are a documented limitation.** `info!(parent: &span, …)` on a span that is not entered gets no trace context, because the appender uses the current OpenTelemetry context, which only entering sets. vigil documents "enter the span (`in_scope`, `instrument`, `entered`) for correlation" and has a test pinning today's behaviour, so an upstream change becomes visible at the next bump. Propagation has its own, stable rule for such spans (nearest recorded ancestor, ADR-0004 decision 9).

### Logs and spans

20. **Span fields on log records: on, with vigil-owned semantics.** vigil enables the appender's `experimental_span_attributes` feature with `TracingSpanAttributes::all()`, so a log record carries the fields of every enclosing `tracing` span, whether or not `traces` is enabled (#26). Upstream's behaviour is not vigil's contract; vigil's is. It is **stable behaviour** pinned by vigil's tests across upstream bumps (ADR-0004 decision 1): vigil translates an upstream change in its own code, or the bump waits for a major:
    - Fields are collected root to leaf. On a key conflict, the event's own field wins over span fields, and an inner span wins over an outer one. The exporter enforces this on the record, so keys are unique on every record (P11 showed duplicates without it).
    - Values recorded later with `Span::record` are included.
    - Span fields come only from spans that pass vigil's configured filter: at the default `info`, a `debug_span!(session = ..)` contributes nothing.
    - The dedup relies on the appender adding span fields root to leaf before the event's own fields (`opentelemetry-appender-tracing` 0.33 `layer.rs`, `on_event`). Upstream does not promise that order, so vigil's test asserts the outcome (event wins, inner span wins), not the order.
    - If upstream changes or removes the experimental API, vigil keeps this contract, implementing the span-field visitor itself if needed (the upstream feature is a span-extension visitor of about a hundred lines, with no SDK internals). A bump that changes it fails vigil's tests and is handled in the bump PR (decision 13), never by changing the contract in a minor.
    - There is no allowlist knob in 0.2.0. Adding one later is additive.

### Metric identity, key order and loss units (round 2)

21. **Metric identity conflicts poison the name.** vigil's metrics binding keeps a process-wide registry, owned by the pipeline slot, of every distinct declaration bound under each case-folded instrument name. Identity follows ADR-0004 decision 8, made precise where the SDK merges streams:
    - **Across scopes,** two declarations of one case-folded name conflict if their **kind** (which includes the value type, so `Counter` and `CounterF64` differ), **unit** or **histogram boundaries** differ. If those agree, they are two streams told apart by `otel_scope_name`, even when their descriptions or spellings differ (ADR-0004 decision 8; P15: deterministic separate streams).
    - **Within one scope,** they also conflict if their **exact spelling** or **description** differs. A spelling difference is merged by the SDK into one stream under the first-bound spelling, so the bytes depend on order; a description difference gives two streams of the same name in one scope, which a backend cannot tell apart, because the description is not a label (P15). This and the series-name rule below refine ADR-0004 decision 8: within one scope fully, across scopes only for incompatible pairs whose Prometheus names overlap. ADR-0004 decision 8 carries an amendment note pointing here (added in this PR), like decision 3 (decision 23).
    - **Within one scope, Prometheus series names are part of identity (P17, S2–S5).** For each declaration vigil also computes the series names Prometheus 3's default OTLP translation gives it, and two declarations **in the same scope** conflict if those sets intersect. The translation, as P1 and P17 observed it: the name is split on every character that is not a letter or digit (`_` included) and rejoined with single `_`s, so runs collapse (`app__y` → `app_y`); the unit's suffix is appended as a whole word unless the name already has it (`ms` → `_milliseconds`, `By` → `_bytes`, S3); a gauge with unit `1` gets `_ratio`; a monotonic counter gets `_total` at the end and loses a `total` word inside the name (observed for one in the middle: `app.total.x` → `app_x_total`, S5; the general rule is copied from the translator); a histogram yields `_bucket`, `_sum` and `_count` of its base (S4). The rest of the unit table, and the `_` prefix for a leading digit (which decision 24 already excludes), are copied from Prometheus' `otlptranslator` at the pinned version. The translation function lives in vigil, and #7's conformance test asserts against the real Prometheus that its output is exactly the series created, for every unit, kind and name shape vigil's tests declare. If a later Prometheus changes its default translation, vigil follows in a minor with a changelog entry naming the pairs that become (or stop being) conflicts. Backends configured with another translation strategy (for example no escaping) may see a pair poisoned that would not have collided there; that is the safe direction.
    - **Across scopes, the series-name check applies only to incompatible pairs.** With decision 12's required `promote_scope_metadata`, series of different scopes carry different `otel_scope_name` labels, so two compatible declarations (same kind and unit) whose series names overlap, such as counter `app.x` in crate-a and counter `app_x` in crate-b, are two series of one Prometheus metric, as S1 is; poisoning them would drop both crates' data for no collision. Two declarations whose series names overlap but whose kind or unit differ, such as histogram `app.y` in crate-a and gauge `app.y.count` in crate-b (both `app_y_count`), would put two incompatible metrics under one Prometheus name, which ADR-0004 decision 8 rejects; they poison the name, across scopes too. Together with ADR-0004's rule (the same case-folded name with a different kind, unit or boundaries), that is the whole cross-scope rule.
    - **Shared names across scopes are reported, not dropped.** When a second scope binds a case-folded name already bound in another scope with equal kind, unit and boundaries (S1, whatever the spelling or description), vigil writes one informational stderr line per name (`vigil: metric "app.x" is recorded by crate-a and crate-b; Prometheus needs otlp.promote_scope_metadata: true to keep them apart`), because the backend setting is the one thing vigil cannot check.
    - **On bind** (an instrument's first record after the pipeline exists, ADR-0004 decision 8): a declaration that conflicts with any registered declaration of the name marks the name **poisoned**; otherwise it is registered and bound. A poisoned name never gets another SDK instrument, and every handle already bound under it sees the poison flag (one atomic load per record) and drops its records from then on. Binding and poisoning happen under one mutex.
    - **On export:** the metrics exporter removes every metric whose case-folded name is poisoned, in every scope, from every export. This is what makes poisoning work on SDK 0.33, where a cumulative stream cannot be unbound and keeps exporting (P15, staged case). It also covers instruments created through `opentelemetry::global` under `--cfg vigil_unstable` (`install_opentelemetry_globals`): they bypass the registry, so they cannot cause a poisoning, but their streams of a poisoned name are removed too. The rustdoc of `install_opentelemetry_globals` says so.
    - **Loud, once per name:** the first poisoning of a name writes one stderr diagnostic naming the two declarations that disagreed (scope, spelling, kind, unit, description, boundaries), in sorted order. For two declarations its text does not depend on which bound first (P15). With three or more declarations of one name, which pair it names can depend on order; the outcome (the name is dropped) cannot. No further diagnostics follow for that name.
    - **Deterministic outcome:** what is exported after a set of declarations has bound depends only on that set, never on the order or the threads they bound on (P15: identical exports in both orders for boundaries, units, kinds, same-scope spelling and same-scope description). There is no winner to choose, so there is no order to depend on. Poisoning cannot see a declaration that never records: it never binds, so it cannot conflict, and the declaration that is used exports normally (P15). Before the second declaration of a conflicting pair binds, the first exports normally; those exports stay in the files. Both follow from instruments being lazily bound `static`s (ADR-0004 decision 8).
    - **Counts are not order-independent, and say so.** Records dropped at a poisoned handle are counted under `lost(Signal::Metrics)` (decision 23); how many there are depends on when the poisoning happened (P15: 2 or 3). Measurements the first declaration recorded into the SDK before the poisoning are later removed by the export filter and counted nowhere. So a poisoning in the period also sets `FlushErrorKind::DataLost`, and the rustdoc of `lost` says the metrics count excludes measurements already aggregated under a name that was poisoned later.
    - **Tests (#7):** each P15 case and each P17 case (S2–S5 poisoned within one scope; S1 and a cross-scope counter `app.x`/`app_x` pair kept, S1 with the informational line; a cross-scope histogram `app.y`/gauge `app.y.count` pair poisoned) in both orders, the staged case, the single diagnostic, and the drop count and `DataLost` kind.
    - **A conflict that only some runs reach.** Binding is lazy, so a conflicting declaration used only on an error path poisons the name only in runs that take that path: `app.x` then disappears from exactly the failing runs, with the diagnostic in their stderr. The README's metrics section says this, and recommends a test that records every instrument once (which binds them all and surfaces any conflict in CI).
    - **Bounded registry.** Instruments exist only as `static`s (ADR-0004 decision 8 has no dynamic constructor), so the registry and the set of SDK instruments are bounded by the number of declarations compiled into the program; attribute cardinality is bounded separately by decision 10.
    - **Why both lose, not one:** any rule that keeps one side either depends on order (the first bound wins, which is what the SDK does) or cannot be enforced in one scope, where the SDK has already merged both declarations into the first-bound stream (P15, boundaries and spelling). A conflict is a programming error in one of two declarations; dropping the name with one diagnostic makes it visible at once, without putting wrong data into Prometheus.
22. **Key order is vigil's, not the build graph's (#64).** The line writer must produce the same bytes whether or not `serde_json/preserve_order` is enabled anywhere in the consumer's dependency graph (P16). It builds lines from an explicitly ordered representation (a fixed field order per OTLP message, or ordered maps that vigil sorts itself), never from `serde_json::Map`'s default ordering. This holds for all three signals and for anything derived from the line bytes (the time-first key order and the byte-for-byte `push` body proposed in ADR-0006, PR #63). The determinism, golden-file and fingerprint tests of #7 and #8 also run in a build with `serde_json/preserve_order` enabled (a dev-dependency feature or a dedicated test crate), and the fix in #64 shows them failing before the change. If ADR-0006 is accepted, its time-first key order is that fixed order.
23. **Loss units: one unit per signal, never mixed.** `FlushError::lost(Signal)` counts:
    - `Logs`: **log records** (export failures, diagnostic stubs, queue overflow at shutdown), as ADR-0004 decision 3 defines.
    - `Traces`: **spans** certainly lost: export failures, stubbed spans (decision 17), and queue overflow captured at shutdown (decision 4). Spans open at shutdown are not counted (decision 18).
    - `Metrics`: **measurements**, meaning `vigil::metrics` record calls that never reached the SDK: dropped before the pipeline existed (reported once when it starts, ADR-0004 decision 8) and dropped because their name was poisoned (decision 21). This supersedes ADR-0004 decision 3's "metric data points" for `lost`, which ADR-0004's reconciliation list handed to this ADR: measurements are the unit the application produces, as records and spans are. ADR-0004 decision 3 carries an amendment note pointing here (added in this PR), as ADR-0006 does for ADR-0001.
    - Problems at the **data-point** level (a failed metrics export, a data point too large to bound, decision 11) are not added to `lost(Signal::Metrics)`. They are reported on stderr in data points (`vigil: runtime metric export losses; dropped data points: N`), always including at shutdown (decision 3), and set the `FlushError` kind: `Failed` for a failed export, `DataLost` for a dropped data point. The rustdoc of `lost` says so. A failed periodic export of cumulative data loses resolution, not totals, because the next export carries the full sums again; only a failed final export at shutdown loses measurements, and it shows as `Failed`.
    - **A failed write of a line to its file** follows the same rule, with or without the `push` tee of ADR-0006: a lost log line counts its records in `lost(Signal::Logs)` and a lost span line its spans in `lost(Signal::Traces)`, even if the push copy was delivered, because the durable copy is missing. A lost metrics line is a data-point-level problem: it sets `Failed`, is reported on stderr in data points, and is **not** added to `lost(Signal::Metrics)`, because the next cumulative export carries the totals again. ADR-0006's tee text is aligned to this rule (comment on PR #63).
    - Records dropped after shutdown began are reported once on stderr and not counted (ADR-0004 decision 8), as are metric records while the signal is switched off or disabled (decision 5).
24. **Instruments are validated at compile time.** `vigil::metrics`' `const` constructors (`new`, `with_unit`, `with_boundaries`, ADR-0004 decision 8) check OpenTelemetry's name rule (first character a letter, then letters, digits, `_`, `.`, `-` or `/`, at most 255), the unit rule (ASCII, at most 63) and the boundaries rule (finite, strictly increasing, which excludes NaN and duplicates), and `assert!` on failure. In a `static`, the documented form, an invalid declaration is a compile error (P18), so no invalid instrument reaches the SDK and there is no uncounted no-op instrument to count. The same `const fn` called at run time (outside a `static`) panics instead; the rustdoc of each constructor has a `# Panics` section saying so (ADR-0004 decision 5's `missing_panics_doc`). The rules are pinned to the SDK's own validation by a test, so a stricter SDK after a bump fails CI instead of silently no-oping.

## Consequences

- **Correct cumulative semantics across processes.** Each process is its own series (`instance="<uuid>"`), so N processes sharing one file sum correctly in PromQL (`sum by (job)`). The cost is series churn: every process start creates new series, which matters for short-lived CLI processes. That is the price of not merging counters across processes, which P3 shows Prometheus cannot do correctly.
- **Loki cardinality.** `service.instance.id` is on logs too, and Loki makes it an index label by default. Deployments with many short-lived processes should move it to structured metadata in Loki's `otlp_config` (Grafana's own recommendation) or drop it in the shipping agent. The shipping ADR ([#39](https://github.com/vig-os/vigil/issues/39)) documents the configuration.
- **Logs format change.** Every logs line gains one resource attribute. It is additive (readers ignore unknown attributes, per ADR-0001's versioning stance), and it lands before any public release (GOAL: no public 0.x).
- **File growth.** Cumulative export rewrites every live series each interval: P1 measured about 1.7 KB per line for 4 instruments, so about 2.5 MB per day per process at 60 s. Rotation and retention bound it; series count and process count scale it.
- **A lost metrics line loses resolution, not totals,** except the final export at shutdown, which has no successor and is flagged `Failed` (decision 23). Otherwise the next cumulative export carries the full count again, unlike logs and spans, where a loss is permanent.
- **No delta, ever, in 1.0.** Backends that prefer delta (some vendors) need a Collector `cumulativetodelta` processor. Adding delta later would be additive API, and it is rejected for now because P2 shows it breaks the primary backend and takes healthy series with it.
- **Errors are visible in traces without duplication.** The trade-off: an ERROR event is processed by the OpenTelemetry layer only to set the status and is then discarded by the span limit. Non-error events cost the OpenTelemetry layer only the filter check.
- **Upstream coupling.** vigil now tracks five upstream crates that must move together, and it can only bump when `tracing-opentelemetry` has caught up (0.34.0 came five days after `opentelemetry_sdk` 0.33). Using an experimental appender feature means vigil may have to carry its own implementation later (decision 20). The 0.34.0 stdout bug shows why the stdout test exists.
- **Prometheus needs `otlp.promote_scope_metadata: true`** (decision 12). Without it, same-named instruments from two crates silently collapse (P17); with it, every series carries scope labels, and a dependency's version bump starts new series.
- **Conflicts are judged by Prometheus names too** (decision 21): within one scope always, across scopes when the kinds or units differ. So pairs that OTLP keeps apart (`app.x` and `app_x`, `app.total.x` and `app.x` in one scope) are dropped together. vigil carries a small copy of Prometheus' default translation, kept honest by the conformance test.
- **A metric name conflict costs both instruments.** Two crates that declare `app.x` differently both lose `app.x` until one is fixed. That is deliberate (decision 21): the alternative is order-dependent or silently merged data. The registry costs one mutex lock per instrument at bind time and one atomic load per record.
- **Lines no longer depend on the consumer's `serde_json` features** (decision 22). The writer cannot rely on `serde_json::to_value` for ordering; that is extra code in the encoder, paid once in #64.
- **Implementation order.** #42 (ADR-0004's surface) first; #64 (key order) before #7/#8 add fingerprint tests; #7 implements decisions 1–3, 5–12, 21–23, the `vigil::metrics` facade and the logs golden change; #8 implements 13–19, decision 4 and `vigil::propagation`; #26 implements 20 and its correlation tests; #9 adds `schemaUrl` on top of the shared resource and scopes. The generalized bounding code lands with whichever of #7/#8 merges first.

## Alternatives considered

- **Delta temporality, or configurable temporality.** Prometheus' OTLP endpoint rejects delta sums with a 500 for the whole request (P2), and its delta-to-cumulative feature is lossy. Exposing a choice whose wrong value silently breaks the reference backend is a trap.
- **Merge counters across processes** (a shared aggregate in the state directory). Needs cross-process aggregation state and its own locking protocol, for a problem the OTel data model already solves with `service.instance.id`.
- **`process.pid` (or `host.name` + pid) as the instance identity.** Prometheus maps only `service.instance.id` to `instance` (P3). PIDs are reused, so two runs could share a series and look like a counter reset. Semconv recommends a UUID.
- **`service.instance.id` on metrics only.** The resource would differ across signals of one process, which breaks resource-based correlation in backends. The Loki cardinality cost has a documented configuration fix.
- **The `uuid` crate.** It would add a crate for 16 random bytes and two bit masks; `getrandom` is already in the tree.
- **Using `tracing-opentelemetry`'s `MetricsLayer`** (metrics from `tracing` events with `monotonic_counter.*` fields). It encodes metric semantics in field-name prefixes, is behind a feature we disable, and doubles the metrics API surface. Applications use `vigil::metrics` (ADR-0004 decision 8; ADR-0004's probe M1 also showed units are lost and log filters silently decide whether a metric exists).
- **Keep span events (no dedup).** Every event is stored and shipped twice (P9); Loki and Tempo both bill for it.
- **Spans-only filter, without the error passthrough.** No duplication, but `error!` inside a span leaves its status Unset (P10), so trace UIs no longer show failed spans.
- **Spans plus ERROR events, without the span limit.** Status is correct, but every error is still duplicated.
- **`with_counting_event_filter`.** The upstream mechanism for exactly this case, but 0.34.0 prints to stdout on every event (P10).
- **Install the OpenTelemetry layer through a `reload` slot, like the logs layer,** Simpler wiring, but `vigil::propagation` relies on the layer's span extensions, which a reload slot hides (P14), so trace context would silently stop crossing processes, a core reason to have traces at all.
- **Strip span events in vigil's span exporter.** Works, but every event's span-event payload is built (location, attributes) only to be discarded, and the exporter cannot tell `tracing` events from user `add_event` calls without sniffing attribute names.
- **Not enabling span fields on logs; correlate by span id only.** Spec-pure, and the span fields are on the span in `traces.jsonl`. Rejected because logs-only builds and log backends (Loki) cannot filter records by an enclosing span's `session.id` without a join, which is #26's request.
- **Exporting still-open spans at shutdown** (ending them early). The registry cannot enumerate live spans, and an artificially ended span would carry a wrong end time. Reporting the count is honest and cheap.
- **Metric conflicts: the first bound declaration wins** (bind-time rejection of the later one). This is what the SDK effectively does, and the winner depends on thread order (P15). Rejected.
- **Metric conflicts: the exporter keeps one stream by a fixed total order** (for example the smallest scope name). Deterministic across scopes, but impossible within one scope: the SDK has already merged both declarations into one stream with the first-bound boundaries (P15), so the exporter cannot separate them. Rejected.
- **Metric conflicts: register every declaration at program start** (link-time collection with a crate such as `inventory`), so conflicts are known before anything records. It closes the window of decision 21, but it needs a declaration macro instead of ADR-0004's `const` statics, link-section tricks per platform, and a new dependency. Rejected for 1.0; decision 21 needs none of it.
- **Metric conflicts: keep both streams** (the SDK's cross-scope behaviour). Two incompatible metrics of one name reach Prometheus. Rejected by ADR-0004 decision 8.
- **Poison same-named instruments across scopes instead of requiring `promote_scope_metadata`.** It would make S1 safe on a default Prometheus, but it contradicts ADR-0004 decision 8 and breaks the semconv case where two crates of one application's workspace (the scope of `vigil::metrics` in 1.0, ADR-0004 decision 8) both record a shared convention name, for example an HTTP crate and an RPC crate both recording `http.server.request.duration`: both would be dropped. Rejected; the backend setting is documented, tested, and pointed out at run time.
- **Compare only OTLP names (decision 21 as of round 2).** P17 shows three silent collisions it misses. Rejected.
- **Validate instruments at bind time or rely on the SDK.** Bind-time validation finds the error only in runs that record the instrument, and has to drop and count; the SDK's validation produces an uncounted no-op. A compile error is earlier and costs nothing at run time. Rejected for decision 24.
- **`lost(Signal::Metrics)` in data points, or split counts.** Data points of cumulative streams are re-sent every interval, so "a data point lost" mostly means lost resolution, not lost measurements; adding them to dropped measurements would mix units. A second count method would add API for a number nobody acts on beyond the `Failed`/`DataLost` kind. Rejected for decision 23.
- **Add decision 18's open-span count to `lost(Signal::Traces)`.** Mixes an upper bound into a lower bound. Rejected; stderr only.
- **Honouring `OTEL_*` environment variables.** Two configuration namespaces for one crate, with precedence rules users must learn; vigil's `VIGIL_*` variables already exist for logs.
- **Using the sdk's `testing` feature for fixtures.** It brings `tokio` into `Cargo.lock`, which the dependency guard forbids (P6); a real meter provider gives the same fixtures.

## Deferred

- **Collector restart behaviour on `metrics.jsonl`:** deferred to [#39](https://github.com/vig-os/vigil/issues/39) (ADR-0006, PR #63), because it is a property of the shipping agent's configuration, not of the file format. ADR-0006 as proposed answers it: without `file_storage` a restart re-sends every line (its probe F1), so its reference config requires storage.
- **A metrics API for libraries** that does not pull in vigil's pipeline: deferred to [#61](https://github.com/vig-os/vigil/issues/61) by ADR-0004 decision 8; decision 21 applies unchanged to it, because conflicts are resolved in the pipeline.
- **`schemaUrl` on resource and scopes:** deferred to [#9](https://github.com/vig-os/vigil/issues/9), which builds on decision 7's shared resource.
