# ADR-0003: Metrics and traces

- **Status:** Proposed
- **Date:** 2026-10-11
- **Issues:** [#38](https://github.com/vig-os/vigil/issues/38) (this decision), [#7](https://github.com/vig-os/vigil/issues/7) (metrics), [#8](https://github.com/vig-os/vigil/issues/8) (traces), [#26](https://github.com/vig-os/vigil/issues/26) (log/span correlation), [#9](https://github.com/vig-os/vigil/issues/9) (`schemaUrl`); depends on [#37](https://github.com/vig-os/vigil/issues/37) (ADR-0004)

## Context

vigil 0.1 writes one signal: logs, through the `tracing` bridge, into `logs.jsonl` ([ADR-0001](0001-on-disk-format.md), [ADR-0002](0002-rotation-and-retention.md)). The 0.2.0 milestone adds `metrics.jsonl` and `traces.jsonl`. The path-to-1.0 pre-mortem (2026-10-10, risks R5, R6, R7) probed the upstream stack and found that it works end to end, with edges that must be decided before #7 and #8 are written.

The load-bearing claims were re-probed for this ADR on 2026-10-11 in a scratch crate (Rust 1.95, `opentelemetry`/`opentelemetry_sdk`/`opentelemetry-proto`/`opentelemetry-appender-tracing` 0.33, `tracing-opentelemetry` 0.34.0, otelcol-contrib 0.151.0 and Prometheus 3.12.0 from the flake's pinned nixpkgs). The probe wrote OTLP/JSON lines with `opentelemetry-proto`'s own transforms (as vigil's exporter does), fed them through the Collector's `otlpjsonfile` receiver and its `otlp_http` exporter into Prometheus' OTLP endpoint (`--web.enable-otlp-receiver`), and queried the result. Findings:

**Metrics.**

- **P1, cumulative works.** One producer, 20 adds over 11 periodic exports: Prometheus returned `vigil_requests_total{route="/x"} 20`, `vigil_latency_milliseconds_{sum,count} 285 / 20`, `vigil_inflight 0`, `vigil_memory_bytes 19456`, and `target_info`. The Collector logged no error. The final value arrived through the export on `shutdown()`.
- **P2, delta is rejected whole.** The same producer with `Temporality::Delta`: 10 of 11 lines failed with `HTTP Status Code 500 … "rejected_items": 4`, which is every metric in the batch, including the gauge and the up-down counter, which are not delta. `vigil_memory_bytes` never arrived. The pre-mortem saw the reason text `invalid temporality and type combination` and that `--enable-feature=otlp-deltatocumulative` accepts delta but loses samples (15/20).
- **P3, missing `service.instance.id` corrupts silently.** Two concurrent processes of one service, with no instance id, appending to one file (ADR-0002's premise): Prometheus kept **one** series and no error was logged anywhere. The samples interleave (`3, 3, 5, 5, 6, 7, …, 12, 12, 14, …, 20`), so the second process's 12 requests disappear from the total and `rate()` is meaningless. The pre-mortem saw a 400 plus 5 out-of-order samples for the same cause when the timestamps interleave the other way. With distinct `service.instance.id` values, the same run gave two exact series (20 and 12), labelled `instance="<id>"`. Prometheus maps `service.name` to `job` and `service.instance.id` to `instance`; other resource attributes (`process.pid`) appear only on `target_info`.
- **P4, a non-finite double drops every metric in the line, silently.** An `f64` gauge recording `NaN` serialized as `"asDouble":null`. The Collector dropped all 4 lines (counter and histogram included) and logged nothing at its default level. The same file with `"asDouble":"NaN"` (the proto3 JSON spelling) arrived complete: `vigil_memory_bytes NaN` and every other series correct. This is ADR-0001 decision 6 again, now for metrics.
- **P5, no runtime.** `PushMetricExporter::export(&self, &ResourceMetrics)` returns a `Send` future; `PeriodicReader` runs on its own thread (`OpenTelemetry.Metrics.PeriodicReader`), as do the batch span processor (`OpenTelemetry.Traces.BatchProcessor`) and the batch log processor. `From<&ResourceMetrics> for ExportMetricsServiceRequest` is public; its JSON is the `{"resourceMetrics":…}` shape of `MetricsData`. The largest line in P1 was 1 743 bytes for 4 instruments.
- **P6, test fixtures.** `ResourceMetrics` fields are `pub(crate)`. The sdk's `testing` feature exposes them but pulls in `tokio`, which `tests/deps.rs` forbids in `Cargo.lock`. The probe built real `ResourceMetrics` without it: a `SdkMeterProvider` with a `PeriodicReader` over the exporter under test, flushed by `shutdown()`.

**Traces.**

- **P7, the pin.** `tracing-opentelemetry` 0.34.0 (MSRV 1.75) is the only release on `opentelemetry` 0.33; `cargo tree -i opentelemetry` shows one copy. With `default-features = false` and the sdk features `logs`, `metrics`, `trace`, the only new crate in the tree is `tracing-opentelemetry` itself: no `tokio`, `tonic`, `hyper`, `tower`, `h2` or `reqwest`.
- **P8, correlation.** Log records emitted inside an entered span carry that span's `traceId`/`spanId`, which match the exported span. The appender reads `Context::current()`, which `tracing-opentelemetry` activates on span entry. Edge (a): `info!(parent: &span, …)` on a span that was never entered gets no trace context (probe: `span=None`).
- **P9, every event is also a span event.** With the layer unfiltered, each `info!`/`warn!`/`error!` inside a span is written twice: as a log record and as a span event (`inner: events=['inside inner', 'warn inner', 'error inner']`).
- **P10, dedup options, measured.**
  - A per-layer filter that lets only spans reach the OpenTelemetry layer removes all span events, but an `error!` inside a span no longer sets the span status: `status.code` stays `0` (Unset). `tracing-opentelemetry` sets `Error` only from ERROR-level events it sees.
  - Letting spans **and ERROR-level events** through keeps `status.code = 2`, but each error is still duplicated as a span event.
  - Spans and ERROR-level events through, **plus** the SDK span limit `max_events_per_span = 0`: no span events at all, `status.code = 2` on the failing span, and `droppedEventsCount = 1` on it, which honestly records that an error event existed.
  - Upstream's own mechanism, `OpenTelemetryLayer::with_counting_event_filter`, **prints `evaluating event with level INFO` to stdout for every event** in the released 0.34.0 (leftover `println!` calls in `FilteredOpenTelemetryLayer::on_event`; probe: 8 stdout lines for 6 events and 2 diagnostics). A library must never write to stdout: it is the protocol channel of an MCP stdio server such as s1-mcp, and the data channel of a CLI.
- **P11, span fields on log records.** With the appender's `experimental_span_attributes` feature and `with_tracing_span_attributes(TracingSpanAttributes::all())`, records inside `info_span!("outer", a = 1, session = "s-1")` and its child `inner` (`b = "x"`) carried `a`, `session` and `b`. It works without the traces signal (it reads the `tracing` registry, not OpenTelemetry). But an event field with the same name as a span field produced **duplicate keys** on one record (`[('a','1'), ('session','s-1'), ('a','2')]`), and the OTLP spec requires attribute keys to be unique. Upstream marks the feature experimental: "the API may change without a major version bump until it is stabilized" (appender CHANGELOG, 0.32.0).
- **P12, open spans at shutdown.** A span still entered when the providers shut down is never exported; `shutdown()` returns `Ok(())`. Its log record (`inside left_open`) points to a `spanId` that does not exist in `traces.jsonl`.
- **P13, default span attributes.** With default settings each span carries `code.file.path`, `code.module.name`, `code.line.number`, `thread.id`, `thread.name`, `target` and the non-semconv `busy_ns`/`idle_ns`. `OpenTelemetryLayer<S, _>` is generic over its subscriber position, so it has to be built for the exact position it is installed in (pre-mortem R7: E0277 when reused elsewhere).

- **P14, span extensions need direct installation.** `tracing_opentelemetry::OpenTelemetrySpanExt` finds the layer through `downcast_raw`. Probe (`src/bin/ext.rs`): with the layer installed as `Filtered` + `Box`, `span.context()` inside an entered span is valid; with the same layer in a `tracing_subscriber::reload` slot (the pattern `src/init.rs` uses for logs), it is invalid, because `reload::Layer` does not forward `downcast_raw` (tracing-subscriber 0.3.23 `reload.rs`).

**Loki.** Loki's OTLP ingestion promotes `service.instance.id` to an index label by default, and Grafana's own documentation says it is "no longer recommended as a default label" because of cardinality, recommending structured metadata instead ([Loki OTel docs](https://grafana.com/docs/loki/latest/send-data/otel/)).

### Assumptions about ADR-0004

ADR-0004 ([#37](https://github.com/vig-os/vigil/issues/37)) is being written in parallel and owns the public surface. This ADR is written against these assumptions; the reviewer reconciles them, and where ADR-0004 decides otherwise, ADR-0004 wins and this ADR is amended:

- **A1, feature names.** Cargo features `metrics` and `traces` gate the two signals. Logs are always built. This ADR works whether or not they are default features; it assumes both are **default-on**, so the default build of `vigil::init` writes all three files.
- **A2, exporter visibility.** No new public exporter type: the metrics and span exporters, and any shared line-bounding code, are crate-private (R1: they would put `opentelemetry_sdk` 0.x traits into vigil's 1.0 promise). Whether the existing `OtlpJsonLogExporter` stays public is ADR-0004's decision.
- **A3, how code gets a `Meter`.** Applications record metrics through the `opentelemetry` API (`opentelemetry::global::meter(..)`), on the global meter provider vigil installs. Whether vigil re-exports `opentelemetry` or wraps the meter is ADR-0004's decision. Whatever it decides must make a version mismatch visible, because an application on a different `opentelemetry` minor gets a different global and records into a no-op provider silently.
- **A4, configuration shape.** The knobs this ADR introduces (metrics interval; per-signal enable) are added in whatever shape ADR-0004 sets for `Config` (builder methods, `#[non_exhaustive]`, environment variables).
- **A5, composition.** If ADR-0004 adds a composable `vigil::layer()`, it includes the OpenTelemetry tracing layer whenever `traces` is enabled, built for that layer's subscriber position (P13).

## Decision

### Shared

1. **One `init`, three signals.** `vigil::init` / `Config::init` sets up logs, plus metrics and traces when their features are compiled in. They share one state directory, one resource and one `RotationConfig`: `logs.jsonl`, `metrics.jsonl` and `traces.jsonl` are separate `RotatingFile`s under the one directory lock (ADR-0002 decisions 3 and 7; a second signal shares the process's lock). `max_bytes` and retention apply to each file separately.
2. **The exporter seam is the logs seam.** Each signal has a crate-private exporter that converts the SDK batch with `opentelemetry-proto`'s public transforms (`From<&ResourceMetrics>`, `group_spans_by_resource_and_scope`), then goes through the same pipeline as logs: deterministic ordering (ADR-0001 decision 5), non-finite sanitizing (decision 6), line bounding (decision 10), and `LineSink::write_line` into the signal's `RotatingFile`. The logs-specific bounding code in `src/logs.rs` is generalized over the three envelopes (`resource{Logs,Metrics,Spans}` → `scope…` → `logRecords` / `metrics` / `spans`). Signal-specific code is limited to: the shrink and drop rules (decisions 11 and 17); the fields that are sanitized for non-finite values (`doubleValue` in log bodies and attributes; `asDouble` and histogram `sum`/`min`/`max` in metrics; double attributes in spans); and the log-record key dedup (decision 20).
3. **Losses are reported, never silent.** Each signal wraps its exporter like `ReportingExporter` in `src/init.rs` today: the first failure goes to stderr, then cumulative rate-limited summaries at most once a minute, and unreported losses at shutdown, naming the signal and its unit: log records, spans, or metric **data points** (`vigil: runtime span export losses; dropped spans: N`, `vigil: runtime metric export losses; dropped data points: N`). A failed metrics export counts every data point in the batch.
4. **Shutdown: concurrent, one 5-second budget.** Dropping the `Guard` (or ADR-0004's fallible shutdown) first sets the existing `stopped` flag, so events and new spans after that point are dropped with the existing one-time stderr warning. It then shuts down the three providers **concurrently**, each on its own scoped thread (`std::thread::scope`) with the same 5-second deadline, and waits for all of them. A sequential order cannot keep one budget: `SdkMeterProvider::shutdown_with_timeout` ignores its argument, and `PeriodicReader::shutdown` waits a fixed 5 s (`opentelemetry_sdk` 0.33 `metrics/meter_provider.rs`, `metrics/periodic_reader.rs`, "TODO: Make this timeout configurable"), so a metrics export blocked on the directory lock (ADR-0002 decision 13) would consume the budget of the signals after it. Concurrently, the worst case stays about 5 s for all three. A signal that misses the deadline gets its own stderr warning naming the signal. The three exporters serialize on the one directory lock, shared in-process through one handle (ADR-0002 decisions 3 and 7), so concurrency costs no correctness. The SDK's own shutdown diagnostics are `opentelemetry*` events, which go to stderr through the diagnostics layer, not into `logs.jsonl`.
5. **Storage failure.** If `metrics.jsonl` or `traces.jsonl` cannot be opened, that signal is disabled with one stderr warning, and the other signals continue. There is no stderr fallback for metrics or spans (unlike logs, they are not human-readable on a console).
6. **No OpenTelemetry environment configuration.** vigil sets every SDK parameter it relies on explicitly (export interval, batch sizes, queue sizes, span limits, sampler), so `OTEL_METRIC_EXPORT_INTERVAL`, `OTEL_BSP_*`, `OTEL_SPAN_*_LIMIT` and `OTEL_TRACES_SAMPLER` have no effect. vigil's configuration surface is `Config` plus `VIGIL_*` variables (A4), as for logs today. One source of truth per knob, and a test can pin the effective values.

### Resource

7. **`service.instance.id` on every signal.** At `init`, vigil generates a random UUID v4 (lowercase, hyphenated, RFC 9562 version and variant bits) and adds it as `service.instance.id` to the one resource shared by logs, metrics and traces. The randomness comes from `getrandom` 0.3, which is already in `Cargo.lock` through `rand_core` (no new crate). The id is not configurable in 0.2.0. Existing attributes (`service.name`, `process.pid`, `host.name`, `service.version`, `vcs.ref.head.revision`) are unchanged. This changes the logs resource, so the logs golden files change with it, in #7.

### Metrics

8. **Cumulative only, and not configurable.** The exporter's `temporality()` always returns `Temporality::Cumulative`. There is no API, environment variable or feature that selects delta or low-memory temporality. A test asserts the temporality on every exported sum and histogram (`aggregationTemporality: 2`).
9. **Periodic reader.** One `PeriodicReader` on the SDK's own thread, export interval **60 s** by default (the OTel default), configurable through `Config` and `VIGIL_METRICS_INTERVAL` in seconds (minimum 1). The final export happens on shutdown. vigil installs the `SdkMeterProvider` as the global meter provider (A3).
10. **Aggregation defaults are upstream's and not exposed.** Explicit-bucket histograms with the SDK default boundaries (instrument code can set boundaries through the `opentelemetry` instrument builder); no views; no exponential histograms; the SDK's cardinality limit of 2 000 series per instrument, beyond which measurements go to one overflow series with `otel.metric.overflow = true`. Exemplars are not produced (the 0.33 SDK emits empty `exemplars` arrays).
11. **Bounding.** A line is split at metric boundaries, and a metric with more data points than fit is split at data-point boundaries, repeating the resource, scope and metric metadata (name, unit, description, temporality, monotonicity). An oversized single data point has its longest attribute string shortened, as for logs. If it still does not fit, the data point is dropped and counted as a loss (decision 3). There is no stub data point, because a fabricated value would be wrong data. Non-finite doubles (`asDouble`, histogram `sum`/`min`/`max`) are written in the spelling the log exporter uses for non-finite values (ADR-0001 decision 6), which P4 shows the Collector and Prometheus accept.
12. **Prometheus name mapping, documented.** The README documents the mapping as observed with Prometheus 3.12's default OTLP translation (and confirmed by the pre-mortem on 3.15): `.` → `_`; monotonic counters get `_total` (`vigil.requests` → `vigil_requests_total`); units become suffixes (`ms` → `_milliseconds`, `By` → `_bytes`, so `vigil.latency` → `vigil_latency_milliseconds_{bucket,sum,count}`); up-down counters and gauges get no `_total`; `service.name` → `job`, `service.instance.id` → `instance`; every other resource attribute is on `target_info` only. Collector configs in docs use the `otlp_http` exporter name (the `otlphttp` alias is deprecated in 0.151.0). #7's conformance test asserts these series names and values through the Collector and Prometheus.

### Traces

13. **Pin and upgrade policy.** `tracing-opentelemetry = { version = "0.34", default-features = false }` (no `metrics` layer, no `tracing-log` normalization). The `opentelemetry` crate family (`opentelemetry`, `opentelemetry_sdk`, `opentelemetry-proto`, `opentelemetry-appender-tracing`) and `tracing-opentelemetry` move together, in one PR, only once a `tracing-opentelemetry` release on the new `opentelemetry` minor exists. That PR passes the Collector conformance tests for all three signals and the stdout test (decision 15). Renovate groups them. How such a bump is versioned for vigil's users is ADR-0004's decision (R1).
14. **Layer configuration.** `OpenTelemetryLayer` with: location on (`code.*`) and threads on (`thread.*`), both semconv; `target` kept; tracked inactivity **off** (no `busy_ns`/`idle_ns`, which are not semconv); context activation on (required for P8); the error-mapping options at their defaults. Consequence of decision 15's span limit: `error_records_to_exceptions` puts `exception.*` on the **span** only for fields recorded as `&dyn Error`; the common `#[instrument(err)]` and `error = %e` forms are mapped by `error_events_to_exceptions` onto the span **event**, which the limit drops, so for them the span keeps `status.code = 2` (and, for a message-less `error = %e` or `#[instrument(err)]`, the status description), while the full error text is in the log record. For `error!(error = %e, "msg")` the field is an ordinary event attribute and the status description is empty. The special fields `otel.name`, `otel.kind`, `otel.status_code` and `otel.status_description` are documented as the way to set them.
15. **Span-event dedup: logs are the only event stream.** The OpenTelemetry layer gets the same gates as the logs layer, plus one of its own: the `RUST_LOG` filter (so `debug_span!`/`trace_span!` from dependencies are not created as OTel spans at the default `info`), the `opentelemetry*` target exclusion, and the shutdown gate (sharing the logs gate's `stopped` and `warned` flags, so there is still one "event after shutdown" warning); then a filter that passes spans and ERROR-level events only. The tracer provider sets `max_events_per_span = 0`. Result (P10): `traces.jsonl` contains no span events; a span with an `error!` inside has `status.code = 2` (Error) and `droppedEventsCount` equal to the number of error events; every event is in `logs.jsonl` exactly once, with that span's ids. **Placement: installed directly, not through a `reload` slot.** `init` installs the subscriber before storage opens and fills the logs layer's `reload` slot afterwards (`src/init.rs`). The OpenTelemetry layer must not use that pattern: `reload::Layer` does not forward `downcast_raw`, so `OpenTelemetrySpanExt` (`context()`, `set_parent`, `set_attribute`, `set_status`, `add_link`) silently does nothing and no `traceparent` can be propagated across a process boundary (P14). Instead, `init` builds the `SdkTracerProvider` before installing the subscriber (after the existing `has_been_set` check, so a refused install is rare; if `set_global_default` still fails, the provider is shut down before `init` returns the error). The span exporter writes to a sink slot (a `OnceLock<RotatingFile>`) that `init` fills once storage opens; if storage fails, the slot stays empty, the exporter discards batches, and decision 5's one warning applies. The layer is wrapped from outside by the filters above, as `Filtered` (which forwards `downcast_raw`). #8 has a test that `Span::current().context()` is valid inside an entered span after `init`. Events added through `OpenTelemetrySpanExt::add_event` are dropped as well; that API is upstream's, outside vigil's promise, and the README says span events are not recorded. `with_counting_event_filter` is not used (P10). A test runs `init` plus events at every level and asserts that **nothing** is written to stdout, so a future upstream stdout leak fails CI.
16. **Sampling and limits.** Sampler `ParentBased(AlwaysOn)`, set explicitly: every span is recorded locally, and shipping decides volume (#8). Batch span processor with the same queue size as logs (`queue_size`, default 65 536), batch size 512, scheduled delay 1 s, and the SDK's other span limits (128 attributes, 128 links). vigil installs the `SdkTracerProvider` as the global tracer provider, as it does the meter provider (decision 9), so crates that use the `opentelemetry` tracing API directly also write to `traces.jsonl`. Those spans bypass `tracing` and therefore `RUST_LOG`; they are subject to the same sampler, limits and loss reporting.
17. **Bounding.** As for logs: split at span boundaries; an oversized span has its longest attribute string shortened (with `vigil.truncated` and `vigil.original_size`); if it still does not fit, the span becomes a stub that keeps `traceId`, `spanId`, `parentSpanId`, `name`, `kind`, timestamps and `status`, with `vigil.dropped = true`. The stub is kept rather than dropped so log records that reference the span still resolve, and it counts as a loss (decision 3).
18. **Open spans at shutdown are reported.** vigil cannot export a span that has not closed: the OpenTelemetry span only ends in `on_close`, and the `tracing` registry has no way to enumerate live spans. vigil counts spans that pass decision 15's filters and have not closed (a vigil layer behind the same filters, with one atomic counter, incremented on new span and decremented on close). It reads the count when the shutdown of decision 4 begins (after the `stopped` gate, so no new spans start). If the count is non-zero it writes `vigil: N spans were still open at shutdown; spans that had not closed before the trace pipeline stopped were not exported, and log records may reference them`. N is exact at that instant. Some of those spans may still close and be exported while shutdown runs, so N is an upper bound on the spans lost; reading the count later instead would miss spans that closed after the trace pipeline stopped. The README documents that root spans should end before the `Guard` is dropped.
19. **Explicit parents (edge a) are a documented limitation.** `info!(parent: &span, …)` on a span that is not entered gets no trace context, because the appender uses the current OpenTelemetry context, which only entering sets. vigil documents "enter the span (`in_scope`, `instrument`, `entered`) for correlation" and has a test pinning today's behaviour, so an upstream change becomes visible at the next bump.

### Logs and spans

20. **Span fields on log records: on, with vigil-owned semantics.** vigil enables the appender's `experimental_span_attributes` feature with `TracingSpanAttributes::all()`, so a log record carries the fields of every enclosing `tracing` span, whether or not `traces` is enabled (#26). Upstream's behaviour is not vigil's contract; vigil's is, and it is pinned by vigil's tests:
    - Fields are collected root to leaf. On a key conflict, the event's own field wins over span fields, and an inner span wins over an outer one. The exporter enforces this on the record, so keys are unique on every record (P11 showed duplicates without it).
    - Values recorded later with `Span::record` are included.
    - Span fields come only from spans that pass the `RUST_LOG` filter: at the default `info`, a `debug_span!(session = ..)` contributes nothing.
    - The dedup relies on the appender adding span fields root to leaf before the event's own fields (`opentelemetry-appender-tracing` 0.33 `layer.rs`, `on_event`). Upstream does not promise that order, so vigil's test asserts the outcome (event wins, inner span wins), not the order.
    - If upstream changes or removes the experimental API, vigil keeps this contract, implementing the span-field visitor itself if needed (the upstream feature is a span-extension visitor of about a hundred lines, with no SDK internals). A bump that changes it fails vigil's tests and is handled in the bump PR (decision 13).
    - There is no allowlist knob in 0.2.0. Adding one later is additive.

## Consequences

- **Correct cumulative semantics across processes.** Each process is its own series (`instance="<uuid>"`), so N processes sharing one file sum correctly in PromQL (`sum by (job)`). The cost is series churn: every process start creates new series, which matters for short-lived CLI processes. That is the price of not merging counters across processes, which P3 shows Prometheus cannot do correctly.
- **Loki cardinality.** `service.instance.id` is on logs too, and Loki makes it an index label by default. Deployments with many short-lived processes should move it to structured metadata in Loki's `otlp_config` (Grafana's own recommendation) or drop it in the shipping agent. The shipping ADR ([#39](https://github.com/vig-os/vigil/issues/39)) documents the configuration.
- **Logs format change.** Every logs line gains one resource attribute. It is additive (readers ignore unknown attributes, per ADR-0001's versioning stance), and it lands before any public release (GOAL: no public 0.x).
- **File growth.** Cumulative export rewrites every live series each interval: P1 measured about 1.7 KB per line for 4 instruments, so about 2.5 MB per day per process at 60 s. Rotation and retention bound it; series count and process count scale it.
- **A lost metrics line loses resolution, not totals.** The next cumulative export carries the full count again, unlike logs and spans, where a loss is permanent.
- **No delta, ever, in 1.0.** Backends that prefer delta (some vendors) need a Collector `cumulativetodelta` processor. Adding delta later would be additive API, and it is rejected for now because P2 shows it breaks the primary backend and takes healthy series with it.
- **Errors are visible in traces without duplication.** The trade-off: an ERROR event is processed by the OpenTelemetry layer only to set the status and is then discarded by the span limit. Non-error events cost the OpenTelemetry layer only the filter check.
- **Upstream coupling.** vigil now tracks five upstream crates that must move together, and it can only bump when `tracing-opentelemetry` has caught up (0.34.0 came five days after `opentelemetry_sdk` 0.33). Using an experimental appender feature means vigil may have to carry its own implementation later (decision 20). The 0.34.0 stdout bug shows why the stdout test exists.
- **Implementation order.** #7 implements decisions 1–3, 5–12 and the logs golden change; #8 implements 13–19 and decision 4; #26 implements 20 and its correlation tests; #9 adds `schemaUrl` on top of the shared resource and scopes. The generalized bounding code lands with whichever of #7/#8 merges first.

## Alternatives considered

- **Delta temporality, or configurable temporality.** Prometheus' OTLP endpoint rejects delta sums with a 500 for the whole request (P2), and its delta-to-cumulative feature is lossy. Exposing a choice whose wrong value silently breaks the reference backend is a trap.
- **Merge counters across processes** (a shared aggregate in the state directory). Needs cross-process aggregation state and its own locking protocol, for a problem the OTel data model already solves with `service.instance.id`.
- **`process.pid` (or `host.name` + pid) as the instance identity.** Prometheus maps only `service.instance.id` to `instance` (P3). PIDs are reused, so two runs could share a series and look like a counter reset. Semconv recommends a UUID.
- **`service.instance.id` on metrics only.** The resource would differ across signals of one process, which breaks resource-based correlation in backends. The Loki cardinality cost has a documented configuration fix.
- **The `uuid` crate.** It would add a crate for 16 random bytes and two bit masks; `getrandom` is already in the tree.
- **Using `tracing-opentelemetry`'s `MetricsLayer`** (metrics from `tracing` events with `monotonic_counter.*` fields). It encodes metric semantics in field-name prefixes, is behind a feature we disable, and doubles the metrics API surface. Applications use the `opentelemetry` metrics API.
- **Keep span events (no dedup).** Every event is stored and shipped twice (P9); Loki and Tempo both bill for it.
- **Spans-only filter, without the error passthrough.** No duplication, but `error!` inside a span leaves its status Unset (P10), so trace UIs no longer show failed spans.
- **Spans plus ERROR events, without the span limit.** Status is correct, but every error is still duplicated.
- **`with_counting_event_filter`.** The upstream mechanism for exactly this case, but 0.34.0 prints to stdout on every event (P10).
- **Install the OpenTelemetry layer through a `reload` slot, like the logs layer, and document `OpenTelemetrySpanExt` as unsupported.** Simpler wiring, but it silently breaks trace-context propagation across processes (P14), which is a core reason to have traces at all.
- **Strip span events in vigil's span exporter.** Works, but every event's span-event payload is built (location, attributes) only to be discarded, and the exporter cannot tell `tracing` events from user `add_event` calls without sniffing attribute names.
- **Not enabling span fields on logs; correlate by span id only.** Spec-pure, and the span fields are on the span in `traces.jsonl`. Rejected because logs-only builds and log backends (Loki) cannot filter records by an enclosing span's `session.id` without a join, which is #26's request.
- **Exporting still-open spans at shutdown** (ending them early). The registry cannot enumerate live spans, and an artificially ended span would carry a wrong end time. Reporting the count is honest and cheap.
- **Honouring `OTEL_*` environment variables.** Two configuration namespaces for one crate, with precedence rules users must learn; vigil's `VIGIL_*` variables already exist for logs.
- **Using the sdk's `testing` feature for fixtures.** It brings `tokio` into `Cargo.lock`, which the dependency guard forbids (P6); a real meter provider gives the same fixtures.
