## Context

vigil goes from version 0.0.0 on `dev` straight to a published 1.0.0; there is no public 0.x (owner decision of 2026-10-10). So the first published surface is the 1.0 promise, and the metrics ([#7](https://github.com/vig-os/vigil/issues/7)) and traces ([#8](https://github.com/vig-os/vigil/issues/8)) work would copy whatever pattern the logs surface has today. The path-to-1.0 pre-mortem (2026-10-10, origin/dev `3cf046d`) found three problems with that surface. Every load-bearing claim below was re-probed for this ADR on 2026-10-11 (Rust 1.95.0, opentelemetry 0.33, cargo-semver-checks 0.47.0, cargo-public-api 0.51.0, all from the flake's pinned nixpkgs) in scratch crates outside the repository.

### R1: 0.x upstream types sit in the surface

The current public surface has 80 items (`cargo public-api` over rustdoc JSON of `3cf046d`). Four of them name `opentelemetry_sdk` types, all through one impl: `impl<S: LineSink + 'static> LogExporter for OtlpJsonLogExporter<S>` (`src/logs.rs:156`) with its `export(LogBatch)`, `set_resource(&Resource)` and `shutdown_with_timeout(..) -> OTelSdkResult`.

- **Upstream churn.** `opentelemetry` and `opentelemetry_sdk` released a breaking minor 14 times between 0.20 (2023-07-29) and 0.33 (2026-09-18), 6 of them since 2025-02 (0.28 2025-02-10, 0.29 03-22, 0.30 05-23, 0.31 09-25, 0.32 2026-05-08, 0.33 09-18; crates.io API). `tracing-opentelemetry` follows in lock step (0.34 on 2026-09-23 is the only release on 0.33).
- **A bump breaks consumers.** Probe: a library exposing `pub fn take(_: opentelemetry::KeyValue)` built against 0.33, used by a consumer on 0.32, fails with `error[E0308]: mismatched types` and `note: there are multiple different versions of crate opentelemetry in the dependency graph` (exit 101).
- **The semver tool cannot see it.** Probe: the same library at 0.1.0 with opentelemetry `=0.32.0` as baseline and `=0.33.0` as current, `cargo semver-checks --baseline-root old --release-type minor` → `196 checks: 196 pass, 56 skip`, `no semver update required`, exit 0. A public-dependency bump passes the gate.

### R2: consumers do not fit `init`

`init` reads only `RUST_LOG` (default `info`, `src/init.rs:193`), owns the global subscriber and has no console output except the storage-failure fallback. flock, the most demanding 0.4.0 consumer ([#16](https://github.com/vig-os/vigil/issues/16)), needs:

- **its own filter variable and default.** The file-logging modes install a global `tracing_subscriber::fmt()` subscriber whose global filter is `EnvFilter::try_from_env("FLOCK_LOG").unwrap_or_else(|_| EnvFilter::new("flk=info,flock=info"))`, writing JSON lines to its own rotating file (`flock/src/logging.rs:30-50`).
- **a different setup per mode.** `flk web` instead installs a separate global human-readable subscriber filtered by `RUST_LOG` (default `info`), writing to stdout, `fmt()`'s default writer (`flock/src/web/mod.rs:154-158`). So flock uses two filter variables, one per mode, and has terminal output in one of them.
- **to read its own log back** (`tail_session_logs`, `merge_log_records`, `flock/src/logging.rs:227-248`). flock knows its directory (`crate::session::data_dir()`), but it must be able to tell whether vigil really writes there or fell back to stderr.
- **room to migrate.** flock owns the global subscriber today. Keeping its own layers next to vigil's during a migration means composing vigil into a `Registry` that flock builds. flock does not do this yet; the probe below tests that shape.

### R10: the surface is not future-proof

- `RotationConfig` has public fields and is not `#[non_exhaustive]`: the pre-mortem planted `pub probe: bool` and cargo-semver-checks reported `constructible_struct_adds_field … semver requires new major version`. It is also `Copy`, so a future non-`Copy` field would be breaking.
- `InitError(String)` cannot be matched: "a subscriber is already set" and "invalid service name" are indistinguishable.
- `Guard` reports loss only on stderr from `Drop`; there is no fallible `shutdown`.
- Retention is `retention_days: u64` on `Config` but `Option<Duration>` on `RotationConfig`.
- `MemorySink` (a test helper) and `NON_FINITE` (a documentation constant) are in the surface.
- There are no feature flags, yet metrics, traces, audit and push are coming.

### R1 also reaches metrics and traces, and fails silently there

The first draft of this ADR only covered the exporter trait. ADR-0003 as proposed in [PR #53](https://github.com/vig-os/vigil/pull/53) (assumption A3, decisions 9 and 16) has applications get a `Meter` from `opentelemetry::global` and lets vigil install the global meter and tracer providers. Spans are customised and propagated with `tracing_opentelemetry::OpenTelemetrySpanExt`. Both give the application's own `opentelemetry` or `tracing-opentelemetry` version an implicit contract with vigil's version:

- **Architect probe (review of PR #54, 2026-10-11):** a stand-in vigil on opentelemetry 0.33 / tracing-opentelemetry 0.34, with an application one minor behind, compiled and ran, but `otel 0.32 global::tracer…span_context().is_valid() = false` and `tracing-opentelemetry 0.33 span.context() valid = false`. Each version has its own globals and its own span extension type, so metrics recorded through the old `global` go to a no-op provider, and `traceparent` propagation stops, with no error at all. That is worse than R1's compile error.
- So a stable API that names `opentelemetry::global`, `Meter` or `OpenTelemetrySpanExt` as the way to use vigil cannot treat an opentelemetry bump as a minor, even though no opentelemetry type appears in vigil's own signatures.

Probes for the replacements, 2026-10-11, scratch crate on opentelemetry/opentelemetry_sdk/opentelemetry-proto 0.33 and tracing-opentelemetry 0.34.0, with a stand-in for vigil's crate-private metrics exporter (`PushMetricExporter`, cumulative, `ExportMetricsServiceRequest::from(&ResourceMetrics)` serialized to JSON):

- **M1, metrics through `tracing` fields (`tracing_opentelemetry::MetricsLayer`).** `info!(monotonic_counter.requests = 1u64, route = "/x")` three times, `info!(histogram.latency_ms = 12.5, route = "/x")`, `info!(gauge.memory_bytes = 100u64)`: the export had `requests` (sum, `aggregationTemporality` 2, `route="/x"`, 3), `latency_ms` (histogram, 12.5) and `memory_bytes` (gauge, 100). But **every `unit` was empty**: field names cannot carry a unit, so the Prometheus unit suffixes ADR-0003 decision 12 documents are lost and the unit leaks into the name. With a consumer's global subscriber-level filter at WARN, as flock's `fmt().with_env_filter(..)` is, the same run exported **nothing**, with no error: metric events are `tracing` events, so log filters decide whether metrics exist. A `debug!` metric event was recorded only because nothing filtered it. Without extra filtering, each metric event also reaches the logs bridge and becomes a log record.
- **M2, a vigil-owned facade.** Statics declared before any initialisation (`static REQUESTS: Counter = Counter::new("app.requests", "{request}")`, `Histogram` in `ms`, `Gauge` in `By`), attributes as `&[(&'static str, Value)]` with a vigil-owned `Value`, bound lazily to the meter provider on the first record after it exists. One record before the provider existed was dropped and counted (`dropped before init: 1`). After binding, the export had `app.requests` (sum, temporality 2, unit `{request}`, `route="/x"` 3 and `route="/y"` 1), `app.latency` (histogram, unit `ms`, 12.5) and `app.memory` (gauge, unit `By`, 100). The signatures name no opentelemetry type, so the application cannot hold a mismatched version.
- **P1, vigil-owned W3C propagation.** `inject(&Span, &mut impl HeaderSet)` and `set_parent(&Span, &impl HeaderGet)` over vigil-owned two-method carrier traits (implemented for `HashMap<String, String>`). Inside, they use vigil's own `tracing-opentelemetry` and `TraceContextPropagator`, against the OTel layer installed as `Filtered` + `Box` in a consumer `Registry` (the shape `Config::layer` returns). The client span injected `traceparent: 00-31a1d341…-b9272e54…-01`, and the server span made its child by `set_parent` had the same trace id (`31a1d34111ff65bbb14c82fa90f937e8`); all three spans were exported with it (`PROBE C OK`). So `Box<dyn Layer>` and `Filtered` both forward `downcast_raw` (tracing-subscriber 0.3.23 `layer/mod.rs:1665-1672`, `:1755`). Two pitfalls came up: `TextMapPropagator::extract` starts from `Context::current()`, so an empty carrier inside an entered span looked valid until the probe switched to `extract_with_context(&Context::new(), ..)`, and an empty `tracestate` was injected as an empty header.
- **Feature-name check.** cargo-semver-checks also skips a feature named `unstable-opentelemetry`: removing an item gated by it passed (196 pass, exit 0). (Round 3 replaced the feature with a cfg, decision 4; the check still shows that semver-checks alone never protected unstable items from unification.)

### Round-3 review findings and probes

A fresh re-review of PR #54 (2026-10-11) found three more ways the promise could break, each probed:

- **Feature unification.** Review probe: an application using only stable vigil, and a library `libx` that enables `unstable-opentelemetry`, so the feature is on for the application too. A vigil minor changes the unstable item, and the **application** fails to build (`E0061` in `libx`, exit 101). A cargo feature cannot keep unstable API out of a stable user's build. Probe of the replacement, a `--cfg vigil_unstable` gate (tokio's `tokio_unstable` pattern), with a stand-in crate `vstub` whose item `unstable` sits under `#[cfg(vigil_unstable)]`:
  - a stable-only application builds (exit 0);
  - `libx` calling the item fails without the cfg (`E0425 … found an item that was configured out`, exit 101) and builds with `RUSTFLAGS="--cfg vigil_unstable"` (exit 0);
  - `libx`'s own `.cargo/config.toml` with `rustflags = ["--cfg", "vigil_unstable"]` lets `libx` build alone, but an application depending on `libx` still fails (exit 101) until the application's top-level build sets the cfg: a dependency cannot opt its users in;
  - cargo-semver-checks over `vstub` 1.0 → 1.0 with the unstable item's signature changed: 196 pass, exit 0 (cfg-gated items are not compiled, so not checked);
  - on this host the environment variable `CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_RUSTFLAGS` (a mold linker flag) silently overrode `build.rustflags` from `.cargo/config.toml`, because Cargo uses only one rustflags source (`RUSTFLAGS`, then `target.<triple>.rustflags`, then `build.rustflags`).
- **Propagation depends on the log filter.** Review probe: with tracing-opentelemetry 0.34 behind an INFO per-layer filter, a `debug_span!("client_call")` inside a recorded `info_span!("outer")` has an invalid context, and `inject` produced `{}`, so the downstream starts a new trace. Probe of the fix (`src/bin/d_ancestor.rs`), with "nearest recorded ancestor" implemented through tracing-opentelemetry's public `get_otel_context(&Id, &Dispatch)` (`otel_context.rs`):
  - **case A**, no layer wants the debug span: the span is disabled outright (no id, no parent link, so the closure of `Span::with_subscriber` never runs). Falling back to `Span::current()`, which is `outer` because entering a disabled span changes nothing, injected `traceparent 00-6236…-dd79145a7856ac6f-01`, which is `outer`'s span id;
  - **case B**, a consumer fmt layer at `debug` makes the span exist in the registry while vigil's OTel layer skips it: walking `Registry::span(id).scope()` to the first ancestor with a valid OTel context injected `outer`'s span id (`f9601443eb8c1149`);
  - in both cases the recorded `info_span!("child_of_debug")` inside the debug span was exported with `parent = outer`, so the injected parent is exactly the parent the local trace shows (`PROBE D OK`).
- **Instrumentation scope and name conflicts.** In `opentelemetry_sdk` 0.33, one provider with meters for scopes `hidden_probe@0.1.0` and `libb@2.0.0` produced: `app.x` sum `ms`, `app.x` histogram `ms` and `app.x` sum `s` in the first scope, and `app.x` sum `ms` in the second, i.e. **four separate streams with the same name and no warning** (only DEBUG `Metrics.InstrumentCreated` events) (`src/bin/e_scope.rs`). The SDK does not stop identity conflicts, so vigil has to.
- A review sketch confirmed the facade on otel 0.33: `const` statics, explicit buckets (counts `[0,1,1,0]`), cumulative temporality, unit kept, record before init dropped.

### Tooling facts the decisions rely on

- **History, no longer relied on: cargo-semver-checks skips `unstable-*` features.** True, but not sufficient, because feature unification still exposes stable users (round 3); decision 4 uses a cfg. Probe: removing a function gated by `#[cfg(feature = "unstable-opentelemetry")]` → 196 pass, exit 0. Control: removing one gated by a plain feature `extra` (not a default feature) → `failure function_missing … semver requires new major version`, exit 1. So by default it checks every feature except the unstable-looking ones.
- **A versioned-feature precedent exists.** `serde_with` 3.24.0 has features `chrono_0_4`, `indexmap_1`, `indexmap_2`, `schemars_0_8`, `schemars_0_9`, `schemars_1`, `time_0_3` to keep 0.x crates out of its own promise.
- **Composition works with a boxed, per-layer-filtered layer.** Probe (scratch crate against `3cf046d`): a generic `fn vigil_layer<S>() -> Box<dyn Layer<S> + Send + Sync + 'static>` with `S: Subscriber + for<'a> LookupSpan<'a> + Send + Sync + 'static`, holding the OTel bridge (over `OtlpJsonLogExporter`) filtered by `FLOCK_LOG`/`flk=info,flock=info` plus an opt-in stderr fmt layer, composed as `registry().with(json_layer.with_filter("flock=debug")).with(vigil)`. Events: `info!(target: "flk::api")` reached vigil's file and the console only; `debug!(target: "flk::api")` reached nobody; `debug!(target: "flock::attach")` reached only flock's JSON layer; `info!(target: "other")` reached nobody. `PROBE OK`, exit 0. The type parameter `S` was inferred from `.with(..)`.
- **The public surface can be snapshotted on the pinned stable toolchain.** `cargo public-api` alone insists on a nightly toolchain (`toolchain 'nightly-…' is not installed`), but `RUSTC_BOOTSTRAP=1 cargo rustdoc --lib -- -Z unstable-options --output-format json` on 1.95.0 followed by `cargo public-api --rustdoc-json target/doc/vigil.json` works (exit 0, 80 items, 4 mention `opentelemetry`).
- **MSRV floors.** Dependencies need at most Rust 1.85 on Linux (`prost` 0.14, `cargo metadata`; `wasip2` 1.87 is wasm-only), and edition 2024 needs 1.85. With `rust-version` lowered to 1.85, `clippy::incompatible_msrv` flags only `File::lock` (stable since 1.89) at `src/rotate.rs:204`, `src/rotate.rs:415` and in `tests/init_review.rs`. `AtomicUsize::try_update` is rejected by 1.93.0 and accepted by 1.95.0, while rustc 1.99.0 deprecates `fetch_update` (used at `src/logs.rs:144`; 1.98.1 does not warn).
- **Feature weight.** Adding `metrics` to `opentelemetry_sdk`/`opentelemetry-proto` adds 0 crates to the normal dependency tree (64 → 64); adding `trace` plus `tracing-opentelemetry` 0.34 adds 1 (→ 65), with a single `opentelemetry` 0.33 in the tree.
- **Queue-overflow losses are not exposed by the SDK.** `opentelemetry_sdk` 0.33 keeps `dropped_logs_count` private (`src/logs/batch_log_processor.rs:158`) and reports it only as the internal `BatchLogProcessor.LogsDropped` warning at shutdown (`:308-316`), which reaches tracing under the default `internal-logs` feature that vigil leaves on. That warning is emitted synchronously on the thread that calls `SdkLoggerProvider::shutdown_with_timeout`, before the shutdown message goes to the worker (`:304-320`, `src/logs/logger_provider.rs:100-111`). Probe: a provider with a batch queue of 1 got 1000 records; the global subscriber filtered everything below ERROR, as a flock-style global filter would. `provider.shutdown()` ran inside `tracing::subscriber::with_default(<capture layer>, ..)`, and the capture read `dropped_logs_count=999` (`PROBE OK`, exit 0). The same `shutdown()` returned `Ok(())`: the SDK reports no loss in its return value.
- **What `cargo public-api` lists depends on its simplification flags.** `-s` omits blanket impls, `-ss` also auto-trait impls, `-sss` also auto-derived impls (`cargo public-api --help`, 0.51.0). The probe count of 80 items used `-sss`. Without `-s`, every vigil type would list foreign blanket impls such as `opentelemetry`'s `impl<T: Sized> FutureExt for T` (`opentelemetry-0.33.0/src/context/future_ext.rs:8`).

## Decision

### 1. OpenTelemetry is hidden from the stable API entirely; the promise covers vigil's own types, std, and the `tracing` family

The architect's direction (hide OpenTelemetry completely, so a bump really is internal) is adopted: probes M2 and P1 show it is feasible for every way an application touches vigil today or under ADR-0003. The alternative policy (an opentelemetry bump is a vigil major, plus a compile-time mismatch guard) is rejected below.

From 1.0.0, the **stable surface** is every public item available with any combination of cargo features, built **without** the `vigil_unstable` cfg (decision 4). Only these external crates may appear in it: `core`, `alloc`, `std`, `tracing`, `tracing_core` and `tracing_subscriber`.

- **No `opentelemetry*` or `tracing_opentelemetry` type, trait, impl or re-export is in the stable surface, and no stable API requires the application to use either crate.** The three ways an application uses telemetry are all vigil-owned:
  - **spans and events:** `tracing` only, as today;
  - **metrics:** the vigil-owned `vigil::metrics` facade (decision 8, probe M2), not `opentelemetry::global` and not `tracing` field conventions (probe M1);
  - **context propagation:** vigil-owned `vigil::propagation` (decision 9, probe P1), not `OpenTelemetrySpanExt`.
- **vigil installs no OpenTelemetry global provider in the stable API**, neither from `init` nor from `layer` (decision 2). The only opt-in is `Config::install_opentelemetry_globals` under `--cfg vigil_unstable` (decision 4).
- Exporters, sinks and re-exports of the exact opentelemetry crates vigil links exist only under `--cfg vigil_unstable` (decision 4).
- **`tracing` 0.1 and `tracing-subscriber` 0.3 are accepted** because the composition API (decision 2) cannot exist without naming `tracing_subscriber::Layer` and the `Subscriber`/`LookupSpan` bounds. They are the crates every consumer already uses (flock, s1-mcp, watcher-s1), and they have not broken in years: `tracing` 0.1.0 shipped 2019-06-28 and `tracing-subscriber` 0.3.0 2021-10-22. If `tracing-subscriber` 0.4 or `tracing` 0.2 ships, moving to it is a vigil **major**.
- **Bumping the internal opentelemetry pin** (0.33 → 0.34, together with `tracing-opentelemetry` per ADR-0003 decision 13) changes nothing in the stable surface and nothing the application links against, so it is a vigil **minor** (patch if upstream only shipped a patch). Upstream behaviour that users write code against is part of vigil's promise and is pinned by vigil's tests, even where `tracing-opentelemetry` or the appender defines it: the special span fields `otel.name`, `otel.kind`, `otel.status_code` and `otel.status_description`; the mapping of ERROR-level events and `#[instrument(err)]` to span status (ADR-0003 decisions 14 and 15); the span-field rules on log records (ADR-0003 decision 20); and the propagation semantics of decision 9. If a bump would change one of these, vigil translates it in its own code so users see no change, or the bump waits for a vigil major. Only numeric defaults that no code names (default histogram boundaries, span and cardinality limits, batch sizes) may change in a minor, with a changelog entry. In every bump PR the Collector conformance tests for all three signals must pass. If the bump changes bytes on disk, ADR-0001's versioning stance decides whether that is a minor or a major ([#50](https://github.com/vig-os/vigil/issues/50) writes the README "Stability" section that combines both). The bump may change `vigil_unstable` items (decision 4).
- **No hidden re-exports.** No feature, stable or unstable, may re-export an opentelemetry crate or item through `#[doc(hidden)]`, a `__private` module or a macro-only path. `cargo public-api` does not list hidden items, so such a re-export would bypass the allowlist check; a vigil macro that needs upstream items expands to vigil-owned functions instead.
- Error `source()` values are type-erased `dyn Error`; their concrete types (including SDK error types) are not part of the promise, so downcasting is unsupported.
- **Enforcement** ([#42](https://github.com/vig-os/vigil/issues/42) part 3/3): CI builds the rustdoc JSON on the pinned toolchain as probed above, with all features and without `vigil_unstable`, and runs `cargo public-api --rustdoc-json … -sss`. It fails if any line of that listing names a crate outside the allowlist. A second rustdoc JSON built with `--document-hidden-items` is checked the same way, so a hidden re-export also fails. This catches what cargo-semver-checks cannot (R1 probe). Blanket impls are omitted on purpose: a foreign blanket impl such as `impl<T> FutureExt for T` is not something vigil promises, and a consumer who imports that trait gets the impl from their own copy of the crate anyway. `-s` omits vigil-written blanket impls as well, which is harmless today: the only vigil traits in the stable surface are the carrier traits of decision 9, which get no blanket impls (`LineSink` exists only under `vigil_unstable`). An ADR that adds a public vigil trait with a blanket impl must extend the check to list it.
- **Extending the allowlist** takes an ADR. It may add a crate only if that crate is at 1.0 or later, or (like `tracing` here) has gone at least three years without a breaking release, and the ADR has to say why the type cannot stay internal. ADR-0005 (audit) and ADR-0006 (push) follow this rule for any type they want to expose.

### 2. Composition: one `Config`, two ways to install, one pipeline per process

`Config` keeps its builder and gains the filter, console and composition options. The sketch, with the semantics #42 must implement:

```rust
let (layer, guard) = vigil::Config::new("flock")
    .version(env!("CARGO_PKG_VERSION"))
    .filter_env("FLOCK_LOG")              // default "RUST_LOG"
    .default_filter("flk=info,flock=info") // default "info"
    .console(vigil::Console::Stderr)       // default Console::Off
    .layer()?;                             // or .init()? for the global subscriber
// flk web: .filter_env("RUST_LOG").default_filter("info").console(Console::Stderr), moving its logs from stdout to stderr
tracing_subscriber::registry()
    .with(flock_json_layer)                // the consumer's own layers and filters
    .with(layer)
    .init();
let dir = guard.dir();                     // Some(state dir) unless storage fell back
```

- **`Config::filter_env(name)`** names the variable vigil reads its filter directives from (default `RUST_LOG`). **`Config::default_filter(directives)`** is used when that variable is unset or empty (default `info`). An empty variable counts as unset, like every `VIGIL_*` variable; this replaces today's surprise that an empty `RUST_LOG` records nothing ([#36](https://github.com/vig-os/vigil/issues/36)). An invalid variable value warns on stderr and falls back to the default filter, as today. An invalid `default_filter` is a programming error: `init`/`layer` return `InitErrorKind::InvalidFilter`.
- **`Config::console(Console)`** adds a human-readable stderr layer with the same filter. The console's text format is not part of the stability promise: it is for people, may change in any release, and must not be parsed (the file is the machine-readable output). `Console` is a `#[non_exhaustive]` enum with `Off` (default) and `Stderr`. ANSI colours are used only when stderr is a terminal. When storage falls back to stderr (decision 3), the console layer is not added twice. There is no JSON console: vigil's file is the structured output. There is no stdout variant either: diagnostics belong on stderr, and stdout stays free for the program's own output. A consumer that logs to stdout today (`flk web`) moves to stderr when it adopts `Console::Stderr`; #16 notes this in flock's migration PR. A consumer who really needs stdout composes its own fmt layer next to `layer()`.
- **`Config::layer::<S>(self) -> Result<(Box<dyn Layer<S> + Send + Sync + 'static>, Guard), InitError>`**, where `S: Subscriber + for<'a> LookupSpan<'a> + Send + Sync + 'static`, builds the same pipeline `init` builds without installing the `tracing` global subscriber or `LogTracer`. The returned layer contains vigil's filter as a **per-layer** filter, the opentelemetry-target exclusion that prevents recursion, the post-shutdown filter, the SDK-diagnostics stderr layer, the optional console layer and, when `traces` is compiled in, the OpenTelemetry tracing layer built for position `S` (ADR-0003 P13), directly in the box with no `reload` slot, so `vigil::propagation` works (probe P1). So it neither filters nor duplicates the consumer's other layers (composition probe). `log` records reach it when the consumer installs `LogTracer`; `tracing_subscriber`'s `SubscriberInitExt::init()` does this by default.
- **`S` must be built on `tracing_subscriber::Registry`** (`Registry` itself or `Layered<_, Registry>`). Per-layer filters need the registry's filter bookkeeping: on any other subscriber, `tracing-subscriber` panics when the layer is added (`register_filter`, tracing-subscriber 0.3.23 `registry/mod.rs:148`). The bound cannot express this, so `layer`'s rustdoc has a `# Panics` section naming it, and the flock-like example in #42 uses `tracing_subscriber::registry()`.
- **`Config::init(self)`** and **`vigil::init(service)`** keep their meaning: install the global subscriber and `LogTracer`, using the same options.
- **What each installs:**

  | Effect | `init` | `layer` |
  |---|---|---|
  | `tracing` global default subscriber | yes | no (the consumer installs its `Registry`) |
  | `log` → `tracing` (`LogTracer`) | yes | no (`SubscriberInitExt::init()` does it) |
  | vigil's process-wide pipeline slot (binds `vigil::metrics` instruments, decision 8) | yes | yes |
  | OpenTelemetry global meter and tracer providers | no; only with `--cfg vigil_unstable` and `Config::install_opentelemetry_globals` | same as `init` |

- **One vigil pipeline per process, and a second attempt fails loudly.** The pipeline slot is reserved atomically when `init` or `layer` starts, and kept by the first call that succeeds. A call that finds the slot taken, or reserved by a concurrent call, returns `InitErrorKind::AlreadyRunning` before it creates any provider, file handle or thread. A call that fails for another reason (`InvalidServiceName`, `InvalidFilter`, or `init` refused with `ForeignSubscriber`) releases its reservation, so a failed attempt does not use up the slot. A taken slot stays taken even after the first `Guard` was shut down (the `tracing` global cannot be uninstalled either, and instruments bound to the first pipeline stay bound). There is no second pipeline to fight over a global, no duplicate diagnostics, and no ambiguity about where `vigil::metrics` records go. Different roles in different processes each have their own pipeline (decision 10).
- **Testing under this rule.** Under `cargo test` all tests in one binary share a process, so they share at most one pipeline. Dropping a test's `Guard` stops that pipeline for the rest of the binary, and a guard kept in a `static` is never dropped, so it never flushes. The documented testing story, used by vigil's own suite and #42's flock-like example test, has two supported shapes:
  1. **one process per test** with `cargo nextest` (vigil's flake already runs nextest): each test calls `Config::new(..).dir(<temp dir>).init()`, does its work, calls `guard.shutdown()` and reads the files with `rotate::read_since`;
  2. **one shared pipeline per binary** under `cargo test`: a `static GUARD: LazyLock<Guard>` initialised once with a temp dir; each test records, calls `GUARD.flush()` (decision 3), and reads back only its own records, filtered by a field unique to the test. Nothing calls `shutdown`; data is on disk after each `flush`.

  The rustdoc of `init`, `layer` and `Guard::flush` and the README testing section show both.
- **`Config::retention(Option<Duration>)`** replaces `retention_days(u64)`; `None` keeps everything and `Some(Duration::ZERO)` deletes rotated segments at the next prune. The environment variable stays `VIGIL_RETENTION_DAYS` (whole days, `0` keeps everything), because a human sets it. The two "zeros" mean opposite things, and the rustdoc of `Config::retention` and of the variable say so side by side. An explicit `retention(None)` beats the environment variable, like every builder value, so `Config` stores "not set" separately from "set to `None`".
- **`Guard::dir(&self) -> Option<&Path>`** returns the state directory vigil writes to, or `None` when it fell back to stderr. A consumer that reads its log back (flock, with `vigil::rotate::read_since`) learns from it whether there is a file to read. A consumer that left the directory to vigil's XDG resolution learns where the file is without repeating that resolution.

### 3. Errors are for the caller's mistakes; the environment degrades

The rule: `InitError` is returned only for a mistake the caller can fix in code. Anything the environment causes (unwritable storage, a bad environment variable, a subscriber that cannot be reconfigured) degrades with one stderr warning and still returns a `Guard`, because telemetry must never stop the application (as `init` already does for storage, #5).

- **`InitError`** is a struct with `kind(&self) -> InitErrorKind`, `Display`, `Error` (with `source()` where there is one), `Send + Sync + 'static`. **`InitErrorKind`** is `#[non_exhaustive]`, `Copy + Eq + Debug`, with:
  - `AlreadyRunning`: vigil's pipeline already exists in this process (decision 2). The reaction is to do nothing: the existing pipeline already receives this code's `tracing` events and `vigil::metrics` records.
  - `ForeignSubscriber` (`init` only): another crate already installed the global `tracing` subscriber. `init` checks `tracing::dispatcher::has_been_set()` before it reserves the slot or creates any provider, file handle or thread (as `src/init.rs` does today); if another thread wins the race between that check and `set_global_default`, `init` shuts down the providers it built and closes its files before returning this kind. The reaction is to switch to `Config::layer` and add the layer to that subscriber's `Registry`, or to remove the other initialisation.
  - `InvalidServiceName`: the name breaks the rule in `Config::new`.
  - `InvalidFilter`: `default_filter` does not parse.
- The `reload` failure path in `Config::init` (`cannot configure tracing subscriber`) only happens if the reloadable layer has been dropped, which cannot happen to the global default subscriber. It becomes a degradation (stderr warning, `Guard::dir()` is `None`), not an error kind.
- **`Guard::flush(&self) -> Result<(), FlushError>`** exports everything queued so far on every signal (force-flush of the log and span processors, a collect-and-export of the metrics reader) and waits up to 5 seconds, without stopping anything. It exists for long-lived processes that want a durable point (before a risky operation, at a checkpoint) and for the shared-pipeline test shape (decision 2), where the guard is never dropped.
- **`Guard::shutdown(self) -> Result<(), FlushError>`** flushes and shuts down with the default 5-second timeout; **`Guard::shutdown_with_timeout(self, Duration)`** takes an explicit one (a CLI wants a short wait, a daemon under lock contention a longer one). `Drop` keeps today's behaviour (stderr warning, no error), and after `shutdown` it does nothing. A guard that fell back to stderr returns `Ok(())`.
- **`FlushError`** (returned by `flush` and `shutdown`): `kind()`, `lost(&self, signal: Signal) -> u64`, `Display`, `Error`, `Send + Sync + 'static`. `Signal` is a `#[non_exhaustive]` enum `Logs`, `Metrics`, `Traces`. Units are log records, measurements and spans (ADR-0003 decision 23); data-point problems set the kind and are reported on stderr without a measurement count. Counts cover losses since the previous flush or startup. **`FlushErrorKind`** is `#[non_exhaustive]`: `Timeout` (did not finish; more than counted may be lost), `Failed` (SDK or sink error), `DataLost` (drained but lost data), in that precedence order. More than 64 simultaneous flush requests can fill the SDK's control channel and return `Failed`.
- **Decision 3 amendment, 2026-10-11 ([#42](https://github.com/vig-os/vigil/issues/42), [PR #72](https://github.com/vig-os/vigil/pull/72)): count overflow at vigil's boundary on every flush.** This supersedes the original shutdown-only overflow count and count-free flush flag. The SDK emits `LogDroppingStarted` only once over its lifetime, so later lossy flush periods were silent, and consumer filters could hide even the first flag. `ReportingProcessor` counts accepted records, incrementing acceptance only after SDK `emit` completes; `ReportingExporter` counts records reaching it before export. Each drain snapshots acceptance before its request. On successful completion, accepted-at-request minus total reaching the exporter bounds cumulative overflow; subtracting overflow already reported assigns only new losses to the period. Successful drains cover all records accepted before the request, so queued/in-flight records cannot be mistaken for losses. Later concurrent arrivals can reach the exporter too, deliberately reducing this lower bound; a later drain can recover it. Failed or timed-out drains do not infer overflow from outstanding records, which may still export. Export failures and diagnostic stubs are added separately. Counts are exact with quiescent producers and successful drains, independent of SDK diagnostics, static max levels and consumer filters, including shared pipelines that never shut down.
- Shutdown still captures `BatchLogProcessor.LogsDropped` (`dropped_logs_count`) on the calling shutdown thread, independently of consumer filters, and reconciles its since-start total against overflow already counted. Only this event is consumed; every other event is forwarded to the dispatch cloned before spawning. A unit test pins the SDK event name, field and forwarding. If creating the scoped shutdown thread fails, shutdown runs inline with the same capture and timeout, including during Drop. The lower-bound gaps are concurrent arrivals after shutdown's acceptance watermark/SDK counter read or worker disconnection; WARN compiled out removes only the supplemental SDK reconciliation, not boundary counting. `lost` documents these gaps. Drop prints only losses not yet printed by runtime summaries and names the actual kind; explicit shutdown returns countable losses without printing them again. Once metrics and traces exist, lifecycle methods cover each provider under its own `Signal`.


### 4. `--cfg vigil_unstable`: direct OpenTelemetry access, outside the promise

Unstable API is gated by the **compiler cfg `vigil_unstable`**, not by a cargo feature. Cargo unifies features across the dependency graph, so a library enabling an unstable feature would expose every application in its graph to unstable changes, and an application using only stable vigil would break on a vigil minor (review probe). A cfg is set only by the top-level build (`RUSTFLAGS`, or the application's own `.cargo/config.toml`), never by a dependency (round-3 probe). This is tokio's `tokio_unstable` pattern. With `--cfg vigil_unstable`, and only then:

- **Exporters and sinks** are public: `vigil::logs::OtlpJsonLogExporter` (`new`, `with_max_line_bytes`, `sink`, and its `LogExporter` impl), the metrics and span exporters from #7/#8, and the `vigil::sink` module (`LineSink`, `AppendFile`, `MemorySink`, and the `LineSink` impls for `Arc<T>` and `RotatingFile`). Without the cfg they are crate-private.
- **The exact crates vigil links are re-exported**, visibly: `vigil::unstable::{opentelemetry, opentelemetry_sdk, tracing_opentelemetry}`. Code that must use the OpenTelemetry API directly uses these paths, never its own dependency on those crates. That turns the silent mismatch of the architect's probe into a guarantee: the re-exported crate is, by construction, the version vigil's pipeline uses.
- **`Config::install_opentelemetry_globals(self) -> Self`** makes `init` and `layer` also install vigil's meter and tracer providers as the OpenTelemetry globals, so crates that instrument with `opentelemetry::global` directly write into vigil's files. Those crates must be on vigil's opentelemetry minor, or they record into a no-op provider silently; the rustdoc says so in its first sentence. Because there is one pipeline per process (decision 2), the globals are installed at most once and never contested.
- **These items are exempt from semver.** Any vigil minor may change them, including when vigil moves to a new opentelemetry release. Such a change gets a changelog entry naming `vigil_unstable`. The rustdoc of each item and the README say to pin vigil with `~1.N` when the cfg is set. Only applications should pin like that: Cargo allows one semver-compatible vigil 1.x per dependency graph, so a library that pins `~1.N` holds every other dependent in the graph at 1.N. A library that uses unstable items forces every application that depends on it to set the cfg, and its README must say so; without the cfg the application fails to compile, loudly, instead of breaking later.
- **How users enable it:** `RUSTFLAGS="--cfg vigil_unstable" cargo build`, or in the application's `.cargo/config.toml`: `[build] rustflags = ["--cfg", "vigil_unstable"]`. The README warns that Cargo uses only one rustflags source, in this order: `CARGO_ENCODED_RUSTFLAGS`, then `RUSTFLAGS`, then all matching `target.<triple>.rustflags` and `target.<cfg>.rustflags` joined together (including `CARGO_TARGET_<TRIPLE>_RUSTFLAGS`), then `build.rustflags`. An earlier source silently replaces the later ones, so the cfg has to go into whichever source the build already uses (round-3 probe). Setting `RUSTFLAGS` rebuilds the whole dependency graph once.
- **Tooling:** `Cargo.toml` declares the cfg with `[lints.rust] unexpected_cfgs = { level = "warn", check-cfg = ['cfg(vigil_unstable)'] }`, so a typo is warned about. cargo-semver-checks never sees cfg-gated items, because they are not compiled without the cfg (round-3 probe: 196 pass after a signature change), and the public-api allowlist check (decision 1) runs without it, so unstable items never enter either gate. CI adds one `cargo check --all-features` with `RUSTFLAGS="--cfg vigil_unstable"` so the unstable code keeps compiling. docs.rs documents unstable items, labelled: `[package.metadata.docs.rs] rustdoc-args = ["--cfg", "docsrs", "--cfg", "vigil_unstable"]` and `rustc-args = ["--cfg", "vigil_unstable"]`, with `#[cfg_attr(docsrs, doc(cfg(vigil_unstable)))]` on each gated item.
- `LineSink` stays unsealed: its purpose is custom storage. New methods get default implementations.
- **Graduation trigger:** these items can join the stable surface only after `opentelemetry_sdk` publishes 1.0 for the traits they implement (and, for the re-exports and globals, `opentelemetry` 1.0), and only through a new ADR. Until then a consumer who wants vigil's files from their own SDK pipeline, or third-party `opentelemetry::global` instrumentation, uses the cfg, knowing it is unstable.
- `NON_FINITE` becomes crate-private. The spelling it names is documented in the `logs` module and ADR-0001 decision 6.

### 5. No public fields, every public enum non-exhaustive

- No public struct has a public field. Structs that callers configure (`Config`, `RotationConfig`) are built with methods; the others (`Guard`, `InitError`, `FlushError`, `PropagationError`, `RotatingFile`, the `vigil::metrics` instruments) are opaque. This makes `#[non_exhaustive]` unnecessary on structs, because nobody outside can construct them with a literal.
- **`RotationConfig`** gets private fields and builder methods in the `Config` style: `RotationConfig::default().max_bytes(u64).retention(Option<Duration>)`. `max_bytes` clamps 0 to 1, like `Config::max_bytes`. It derives `Debug + Clone + PartialEq + Eq + Default` and **drops `Copy`**, so adding a non-`Copy` field later is not breaking.
- Every public enum (`Console`, `InitErrorKind`, `FlushErrorKind`, `Signal`, `PropagationErrorKind`, `metrics::Value`, and later ones) is `#[non_exhaustive]`.
- Auto traits are part of the promise: `Config`, `Guard`, `RotationConfig`, `RotatingFile`, `InitError`, `FlushError`, `PropagationError` and the `vigil::metrics` instruments are `Send + Sync` (cargo-semver-checks catches losing them). Builder methods and `Guard` stay `#[must_use]`.
- `missing_docs`, `clippy::missing_errors_doc` and `clippy::missing_panics_doc` become denied ([#44](https://github.com/vig-os/vigil/issues/44)).

Name and default are decided here. What a feature's code does is deferred to the ADR named in the last column.

| Feature | Default | Adds | Behaviour deferred to |
|---|---|---|---|
| `metrics` | on | `opentelemetry_sdk`/`opentelemetry-proto` `metrics` features; 0 new crates (probe) | ADR-0003 ([#38](https://github.com/vig-os/vigil/issues/38)) |
| `traces` | on | `trace` features plus `tracing-opentelemetry` 0.34; 1 new crate (probe) | ADR-0003 ([#38](https://github.com/vig-os/vigil/issues/38)) |

- Logs are not a feature: they are the crate's core and always compiled.
- `metrics` and `traces` are on by default because the crate's promise is "logs, metrics and traces" and they cost at most one crate. "On" means compiled in; what `init` does with each signal is ADR-0003's decision.
- `audit` is off because it adds cryptographic dependencies only audit users need. `push` exists only once ADR-0006 supersedes ADR-0001 decision 9 ("vigil writes files only… No network exporter"), which the owner has asked for (owner decision v2, 2026-10-11: an optional `push` feature, with files staying the durable copy). This ADR reserves the name and fixes it as off by default, so the default build never contains network code.
- **There is no unstable feature**; unstable API uses the `vigil_unstable` cfg (decision 4).
- **There is no `test-util` feature.** Its only candidate, `MemorySink`, serves exporter tests and is under `vigil_unstable`. Code that records `vigil::metrics` in a test without a pipeline only increments the dropped-before-init counter (decision 8), so tests need no stub. Consumers test vigil's output in the two shapes of decision 2.
- Rules: every optional dependency is enabled with `dep:` syntax, so no implicit feature names leak into the surface. Features are additive: enabling one never removes or changes an item. Removing a feature, or changing the default set, is a major. To label gated items with their feature, #42 sets `[package.metadata.docs.rs] all-features = true` and the `rustdoc-args`/`rustc-args` of decision 4 in `Cargo.toml` and adds `#![cfg_attr(docsrs, feature(doc_cfg))]` to `lib.rs` (docs.rs builds only default features unless told otherwise).

### 8. Metrics: a vigil-owned facade

With feature `metrics`, `vigil::metrics` is the stable way to record metrics. Sketch, with the semantics #7 implements:

```rust
use vigil::metrics::{Counter, CounterF64, Histogram, Gauge, UpDownCounter};
static REQUESTS: Counter = Counter::new(vigil::scope!(), "app.requests").with_unit("{request}").with_description("Handled requests");
static CPU: CounterF64 = CounterF64::new(vigil::scope!(), "process.cpu.time").with_unit("s");
static LATENCY: Histogram = Histogram::new(vigil::scope!(), "app.latency").with_unit("ms").with_boundaries(&[5.0, 10.0, 50.0]);
static INFLIGHT: UpDownCounter = UpDownCounter::new(vigil::scope!(), "app.inflight");
static MEMORY: Gauge = Gauge::new(vigil::scope!(), "app.memory").with_unit("By");

REQUESTS.add(1, &[("route", "/x".into())]);
LATENCY.record(12.5, &[("route", "/x".into())]);
```

- **Five instruments, fixed value types:** `Counter` (monotonic, `u64`), `CounterF64` (monotonic, `f64`, for semconv quantities such as `process.cpu.time` in seconds), `UpDownCounter` (`i64`), `Histogram` (`f64`, explicit buckets), `Gauge` (`f64`, last value). They map one-to-one onto the SDK's instruments, so ADR-0003's aggregation, temporality and Prometheus mapping hold unchanged (probe M2: sum with temporality 2 and units preserved, histogram, gauge). Asynchronous (callback) instruments are not in 1.0; adding them is additive.
- **Construction is `const`** (`new`, `with_unit`, `with_description`, `with_boundaries(&'static [f64])`), so instruments are `static`s, declared once like `tracing` callsites. Names, units and descriptions are `&'static str`.
- **Scope = the declaring crate.** OpenTelemetry defines the instrumentation scope as the instrumentation library, and it reaches disk (`scopeMetrics[].scope`) and Prometheus (`otel_scope_name`, `otel_scope_version`). `vigil::scope!()` expands, in the calling crate, to `Scope::new(env!("CARGO_PKG_NAME"), env!("CARGO_PKG_VERSION"))`, so the scope is the crate that declares the instrument, not vigil and not the application. `Scope::new` is public and `const` for the rare caller that needs another scope (generated code); the macro is the documented way. The macro is plain public API; it expands only to vigil-owned items, so no hidden path exists (decision 1).
- **Attributes** are `&[(&'static str, Value)]`. `Value` is a `#[non_exhaustive]` vigil enum (`Bool`, `I64`, `F64`, `Str(Cow<'static, str>)`) with `From` impls for `bool`, `i8`/`i16`/`i32`/`i64`, `u8`/`u16`/`u32` (losslessly into `I64`), `isize` and `usize` (a `len()` as a label is common; `usize` follows the `u64` rule), `u64` (into `I64` when it fits, otherwise into `Str` with its exact decimal value, since OTLP has no unsigned 64-bit attribute; the rustdoc warns that such an attribute changes type above `i64::MAX`, which splits its series), `f32`/`f64`, `&'static str` and `String`. Static keys keep label sets small; the SDK's cardinality limit (ADR-0003 decision 10) still applies.
- **Identity conflicts are handled deterministically and loudly.** Instrument identity conflicts (the same name, compared case-insensitively as OpenTelemetry specifies, with a different kind, unit or histogram boundaries) are handled **deterministically and loudly**: the outcome must not depend on which thread records first, and a stderr diagnostic names both declarations. The same name with the same kind, unit and boundaries in another scope is not a conflict; it is a separate stream told apart by `otel_scope_name`. The mechanism is decided in **ADR-0003** (metrics exporter), and must be proven against the pinned `opentelemetry_sdk`. *(Amended by ADR-0003 decision 21: a conflict poisons the name for every declaration; within one scope, spelling and description are also identity; Prometheus series names are part of identity too, within one scope always and across scopes for pairs of different kind or unit; same-named instruments in different scopes need Prometheus' `otlp.promote_scope_metadata: true`, ADR-0003 decision 12.)* vigil has to provide it because the SDK does not: the round-3 probe exported four same-named streams with no warning, and the final review showed that a losing cumulative stream cannot simply be unbound on 0.33 (it keeps exporting) and that histograms differing only in boundaries are not treated as a conflict by the SDK at all.
- **Late binding.** An instrument binds to the process's pipeline (decision 2) on its first record after the pipeline exists, then records directly. A record before the pipeline exists is dropped and counted in a process-wide counter, **silently**. When a pipeline of the same vigil major starts, it reports the count once (`vigil: 12 metric records before vigil::init were dropped`) and adds it to `FlushError::lost(Signal::Metrics)`. So the message appears only in an application that runs vigil: an application without vigil, or one whose pipeline is a different vigil major (a separate static counter), never sees stderr output from `vigil::metrics`. Every record checks the pipeline's `stopped` flag (ADR-0003 decision 4), because a bound SDK instrument outlives its provider: a record after shutdown began is dropped and reported once on stderr (`vigil: metric recorded after vigil shutdown; dropped`), but not counted, because `shutdown` has already returned its counts.
- **Libraries record through `tracing` only in 1.0.** A library depending on vigil would force the SDK, rotation and the exporters onto every application using it, including applications that do not use vigil. So `vigil::metrics` is for applications (and for libraries that are part of one application's workspace). A library that wants metrics without that cost waits for a separate API-only crate with no SDK dependency, which `vigil::metrics` would then re-export with identical paths and API, an additive change. That is deferred to [#61](https://github.com/vig-os/vigil/issues/61), post-1.0, because 1.0's known consumers are applications. A process without `metrics` compiled in has no `vigil::metrics` module, so misuse is a compile error. With `metrics` compiled in but the signal switched off (ADR-0003 A4's per-signal enable) or its storage failed (ADR-0003 decision 5), records are dropped without further reports.
- **Why not `tracing` fields (`MetricsLayer`):** probe M1. Units are lost, and log-level filters, including a consumer's global filter vigil cannot see, decide silently whether a metric exists.
- **Why not `opentelemetry::global`:** the architect's probe; a version mismatch records into a no-op provider silently. It remains available, unstable, through decision 4.

### 9. Context propagation: vigil-owned `inject` / `set_parent`

With feature `traces`, `vigil::propagation` carries W3C trace context across process boundaries without any opentelemetry type in its signatures (probe P1):

- `pub trait HeaderSet { fn set(&mut self, key: &str, value: String); }` and `pub trait HeaderGet { fn get(&self, key: &str) -> Option<&str>; }` are the carrier traits, implemented by vigil for `HashMap<String, String>` and `BTreeMap<String, String>`. A consumer adapts `http::HeaderMap` or an MCP `_meta` map with a two-line impl, so no HTTP crate enters the surface.
- **Errors are typed, because the cases need different reactions.** `PropagationError` is a struct with `kind() -> PropagationErrorKind`, `Display`, `Error`, `Send + Sync + 'static`; `PropagationErrorKind` is `#[non_exhaustive]` with `Missing` (no `traceparent` in the carrier: the normal case for an untraced request), `Invalid` (a `traceparent` that does not parse or has an all-zero id), `AlreadyStarted` (the span's OpenTelemetry span was already built, see below) and `NotRecorded` (the span has no OpenTelemetry span: no `traces` pipeline in this process, or the span was filtered out by vigil's filter). Only `Missing` is expected in normal operation; the rustdoc says the others point at a bug or a misconfiguration.
- **Nearest recorded ancestor (stable behaviour).** `inject` and `trace_id` use the context of the given span if vigil's OpenTelemetry layer recorded it; otherwise that of its **nearest recorded ancestor**: if the span exists in the registry, the first span in `Registry::span(id).scope()` with a valid OpenTelemetry context; if the span is disabled outright (no id, so no parent link), `Span::current()` and its ancestors. This is the parent that a recorded child span of the unrecorded span gets in-process, so the downstream service's spans attach exactly where the local trace says (round-3 probe, cases A and B). For a disabled span (case A) that holds only when `inject` runs in the context where the span is, or would be, entered: a disabled span keeps no parent, so `inject` called elsewhere (the span moved into a spawned task, or created with an explicit `parent:`) uses whatever is current there, or returns `NotRecorded`. `inject`'s rustdoc says so; a span that crosses tasks should be one vigil's filter records. Spans are not recorded unfiltered with export filtered instead: that would create OpenTelemetry spans for every `debug_span!` of every dependency, which ADR-0003 decision 15 avoids on purpose, and an export-side filter would leave recorded children pointing at unexported parents. Implementation note for #8: `get_otel_context` locks the span's extensions, so the `scope()` walk must not hold an `ExtensionsMut` of any span while calling it (upstream's documented deadlock). The rule is testable: #8 asserts the injected parent span id equals the recorded ancestor's in both cases, and that a recorded child's exported parent is the same span.
- `inject(span: &tracing::Span, carrier: &mut impl HeaderSet) -> Result<(), PropagationError>` writes `traceparent` (and `tracestate` only when non-empty; probe P1 saw an empty header otherwise). It returns `NotRecorded`, writing nothing, only when neither the span nor any ancestor (nor the current span, for a disabled one) is recorded.
- `set_parent(span: &tracing::Span, carrier: &impl HeaderGet) -> Result<(), PropagationError>` makes `span` a child of the remote context. It extracts against an **empty** root context, never `Context::current()` (probe P1: otherwise an empty carrier inside an entered span looks valid).
- **Ordering rule:** `set_parent` must come before anything that builds the span's OpenTelemetry span: entering the span, passing it to `inject` or `trace_id`, or passing **any descendant** to `inject` or `trace_id`, because the ancestor rule builds the ancestor whose context it reads (`get_otel_context` activates the span it is asked about). `tracing-opentelemetry` 0.34 builds the span on its first `context()` call (`span_ext.rs:342`), and `set_parent` on a built span fails (`span_ext.rs:280-294`). vigil maps that to `AlreadyStarted` instead of silently keeping the local parent. #8 has a test for each kind.
- `trace_id(span: &tracing::Span) -> Option<String>` returns the 32-hex-digit trace id under the same ancestor rule, for correlation ids in responses and error messages, or `None` when nothing is recorded. Calling it builds the span, so the ordering rule applies.
- `set_parent` on a span that is not recorded returns `NotRecorded`: a span without an OpenTelemetry span cannot take a parent, and the ancestor rule does not apply to it. Server-side spans that receive context should therefore be at a level vigil's filter records (`info_span!` at the default filter).
- **The working server pattern, shown in the rustdoc:** create a fresh span, call `set_parent` on it, then run the handler inside it with `.instrument(span)` or `span.in_scope(..)`:

  ```rust
  let span = tracing::info_span!("handle", otel.kind = "server");
  let _ = vigil::propagation::set_parent(&span, &headers); // Missing is fine
  handle(req).instrument(span).await
  ```

  The pattern that does not work, also shown: inside a function with `#[instrument]`, `set_parent(&Span::current(), ..)` returns `AlreadyStarted`, because the attribute entered the span, which built its OpenTelemetry span, before the body ran.
- Only W3C Trace Context; no baggage and no other propagation formats in 1.0 (additive later). Span status and name are set with the `otel.*` special fields ADR-0003 decision 14 documents; links and `add_event` are not in 1.0.
- The rustdoc of `vigil::propagation` says not to use `tracing_opentelemetry::OpenTelemetrySpanExt` from an application's own dependency: on a different minor it silently returns invalid contexts (architect's probe). Under `--cfg vigil_unstable` the matching `vigil::unstable::tracing_opentelemetry` is available.

### 10. Multi-role consumers

A consumer with several roles (flock: `flock.log`, `flock-client.log`, `flock-server.log`, plus per-process `flock-mcp-<pid>.log`, `flock/src/logging.rs:53-75`) runs one pipeline per process (decision 2), and maps roles in one of two ways, both supported by the 1.0 surface:

- **service name per role** (`Config::new("flock-server")`): separate state directories and files, and a separate `service.name`, hence a separate Prometheus `job`; or
- **one service, one directory** (`Config::new("flock")`, the same `dir`): every role appends to the same files, which is ADR-0002's multi-process premise; processes are told apart by `service.instance.id` and `process.pid` (ADR-0003 decision 7).

vigil 1.0 adds no API for custom resource attributes. Which mapping flock uses, and whether a role attribute is needed (an additive `Config` option through an ADR), is deferred to [#16](https://github.com/vig-os/vigil/issues/16), because it depends on how flock's log tail and dashboards want to query roles.

### 11. MSRV policy

- **`rust-version` stays `1.95` for 1.0.0.** The measured floor is lower (1.89, set by `File::lock`; dependencies need 1.85), but every known consumer builds with the devkit-pinned toolchain, which is 1.95.0. Rust 1.95 was released 2026-04-16, so it turns six months old on 2026-10-16, before any realistic 1.0 date; the six-month rule below governs raises after 1.0. A lower MSRV would buy no known user and would rule out `AtomicUsize::try_update`, the replacement for `fetch_update`, which rustc 1.99 deprecates (probe).
- **Raising the MSRV** happens only in a minor release, never a patch, with a changelog entry. The new MSRV must be a stable release at least six months old on the vigil release date. The devkit toolchain pin and the MSRV move independently.
- **CI tests it** ([#45](https://github.com/vig-os/vigil/issues/45)): one job builds and tests with all features on exactly the `rust-version` toolchain, separate from the dev pin, and also runs `cargo check --all-features --target aarch64-apple-darwin` with that toolchain, so macOS-only code paths (`renameatx_np` through rustix, ADR-0002) are held to the MSRV too. A second job builds and tests on the latest stable release without `-D warnings`, so a deprecation (like `fetch_update` on 1.99) shows up as a warning before it becomes an error; a build or test failure there blocks. Both jobs run on Linux; the macOS lane ([#46](https://github.com/vig-os/vigil/issues/46)) runs the dev pin. **Today the MSRV equals the devkit pin (1.95.0)**, so the MSRV job tests the same toolchain as `nix flake check` and adds only the apple-target check. It starts testing something distinct the moment devkit moves the pin past 1.95, which is exactly when an accidental use of a newer std API becomes possible; the job exists before that so the first such PR fails. Switching `src/logs.rs:144` to `try_update` is part of #42.

### 12. Semver baseline before and after the first publish

- **Until 1.0.0 is published** (version stays 0.0.0 on `dev`): the semver job ([#43](https://github.com/vig-os/vigil/issues/43)) compares each PR with the full SHA of its merge base with `dev`, passes an explicit `--release-type minor` (without it, 0.0.0 → 0.0.0 runs 0 checks and passes, pre-mortem R9), and fails unless it reports more than 0 checks. It runs inside the dev shell with the toolchain and cargo-semver-checks from the flake's pinned nixpkgs: verified in review, it runs 222 checks there and a planted break fails, while outside the dev shell it fails with `unsupported rustdoc format v61` (the host rustdoc's JSON format is newer than the tool knows). A PR labelled `semver:major` (such as #42) may fail this job only if its body cites the ADR decision that requires the break; the architect checks that citation before merging. The public-api allowlist check (decision 1) has no exception.
- **When #42 lands**, a `cargo public-api` snapshot of the stable surface is committed (#42 picks the path). From then on every surface change shows up as a diff of that file in the PR that makes it.
- **From 1.0.0 on:** the baseline is the latest published version on crates.io (cargo-semver-checks' default). Feature PRs don't bump the version, so CI keeps passing `--release-type minor`: every PR must be minor-compatible. The release-preparation PR sets the new version and the job runs with the release type that version implies. The `semver:major` exception ends: a breaking change needs a superseding ADR and a 2.0.0.

## Consequences

- Consumers who use `init`/`layer`, `tracing`, `vigil::metrics` and `vigil::propagation` never see an opentelemetry bump, and cannot hold a mismatched opentelemetry version, because they never name one. vigil can track upstream's roughly two breaking releases a year in minor releases.
- vigil now owns a small metrics API (five instruments, a scope, one value enum) and a propagation API (two traits, three functions, one error type). They are thin over the SDK, but vigil is responsible for their semantics across upstream bumps. New instrument kinds, callbacks, baggage or links are additive work, each needing a decision.
- Crates that instrument with `opentelemetry::global` directly are not captured by default. Capturing them needs `--cfg vigil_unstable` plus `install_opentelemetry_globals`, and those crates must match vigil's opentelemetry minor.
- One pipeline per process also constrains tests: under `cargo test`, tests in one binary share one pipeline, kept in a `static` and flushed with `Guard::flush`, or run one process per test with nextest (decision 2). That is a real cost for consumers used to independent `cargo test` tests, accepted because a per-test pipeline would bring back contested globals.
- Libraries cannot record metrics through vigil in 1.0 without imposing vigil on their users (decision 8); they use `tracing` until #61.
- Unstable API needs a compiler flag, which is clumsier than a feature and rebuilds the whole graph once, but it can never reach an application that did not ask for it.
- Metric name conflicts must be resolved inside vigil's metrics exporter (ADR-0003), since the SDK neither prevents nor reports them; until ADR-0003 decides the mechanism, #7 cannot be implemented.
- One pipeline per process: a library cannot set up its own vigil pipeline inside an application that already has one. It records through `tracing`, which the application's pipeline receives.
- flock-shaped consumers compose vigil into their own `Registry` with their own filter, console and other layers. #42's acceptance includes a flock-like example with a test.
- `shutdown` makes loss visible as a value. The price is coupling to the SDK's `BatchLogProcessor.LogsDropped` event, its name, its field and the fact that it is emitted on the calling thread, all guarded by a test. If upstream changes any of these, vigil cannot take that bump until it finds another source for the count. The count stays a lower bound (decision 3).
- Users of `vigil_unstable` get no semver protection: `cargo update` can pull in a minor that breaks their build unless they pin `~1.N`, and such a pin in a library holds every other dependent in the graph back. Today no consumer is known to need the exporters.
- vigil's own `init`/`layer` must provide everything consumers need, because the exporters are no longer a stable escape hatch. Every new consumer need becomes a `Config` option (a minor) or an ADR.
- A `tracing-subscriber` 0.4 or `tracing` 0.2 forces a vigil major (the composition bound and `propagation`'s `&tracing::Span` name them). Since every consumer would have to migrate anyway, this is accepted.
- Every callback through the boxed layer is one dynamic dispatch, which is negligible next to the file I/O behind it.
- #42 breaks the logs surface on `dev` (`retention_days`, `RotationConfig` fields, `InitError`, the exporter module). Nothing is published, so no user is affected; this is the last cheap moment.
- CI grows by a rustdoc-JSON build on the pinned toolchain (#43) and two toolchain lanes (#45).

## Alternatives considered

- **Expose opentelemetry for metrics and propagation, make every opentelemetry bump a vigil major, and add a mismatch guard** (the architect's fallback). A guard that is a compile error, not a silent no-op, would need vigil's signatures to name the application's opentelemetry types, which brings back R1's E0308 on every bump, or a build-time version check, which cannot see crates that use `opentelemetry::global` without depending on vigil. And it would cost 14 majors since mid-2023 (keeping only the exporters stable has the same cost), each forced on `init`-only consumers who never touch OpenTelemetry. Rejected, because probes M2 and P1 show the fully hidden design works.
- **Metrics through `tracing` fields (`tracing_opentelemetry::MetricsLayer`).** No external types at all, but probe M1: no units, and metrics silently vanish under log filters, including a consumer's global filter. Rejected for the facade.
- **Install the OpenTelemetry globals by default, as ADR-0003 as proposed does.** Convenient for crates that use `opentelemetry::global`, but each such call site on a different minor is a silent no-op (architect's probe), and with `layer()` the globals have no single owner. Rejected; kept as an unstable opt-in.
- **An `unstable-opentelemetry` cargo feature** (this ADR's previous revision). Feature unification lets any library turn it on for the whole graph, so a stable-only application breaks on a vigil minor (review probe, `E0061`). Rejected for the cfg.
- **Propagation: record every span unfiltered and filter at export.** Keeps every span's own context valid, but creates OpenTelemetry spans for every dependency's `debug_span!` (ADR-0003 decision 15) and leaves recorded children with unexported parents. Rejected for the nearest-recorded-ancestor rule.
- **Metrics scope = vigil, or the application.** Simpler, but hides which library an instrument comes from and breaks the OpenTelemetry meaning of scope. Rejected for the declaring crate.
- **Let the SDK keep conflicting instruments as separate streams.** That is the 0.33 behaviour (round-3 probe), and it puts a counter and a histogram of one name into Prometheus at once. Rejected: conflicts are handled deterministically and loudly (decision 8), by a mechanism ADR-0003 decides.
- **A `vigil-api` crate for libraries in 1.0.** Right long term, but a second crate to publish and freeze before 1.0, for no known 1.0 consumer. Deferred to #61 with an additive path.
- **Allow several pipelines per process.** Two `layer()` calls would contest any process-wide state (the metrics binding, OpenTelemetry globals, if opted in) and duplicate diagnostics. Rejected for one pipeline per process with a loud second-call error.
- **Versioned features (`opentelemetry_0_33`, as in `serde_with`).** Honest semver, but staying minor-only means compiling the exporters against several SDK versions at once (one renamed dependency and one code path per version); dropping an old one is a major anyway. That cost buys nothing for zero known users. Rejected; a new ADR can adopt it if users appear.
- **Wrap the SDK traits in vigil-owned types.** A provider accepts only the SDK's `LogExporter`, so a wrapper cannot plug in without exposing the trait it wraps. Rejected.
- **A separate 0.x crate for the exporters.** Gives cargo-visible semver for the exporters, but needs a second published crate and turns vigil's line encoder into a public API of one of the two crates. Rejected for 1.0. It is the natural move if the exporters gain real users before upstream reaches 1.0.
- **Make the exporters fully private.** Almost the same as decision 4, but it would take away the only way for an existing SDK pipeline to write vigil's files. The cfg costs only attributes. Rejected.
- **A concrete `vigil::Layer` type implementing `Layer<S>` for every `S`.** Per-layer filters (`Filtered<L, F, S>`) are generic over `S`, so a non-generic type would have to reimplement tracing-subscriber's filter plumbing. Rejected for the probed `Box<dyn Layer<S>>`.
- **Return `impl Layer<S>` instead of a box.** Works too, but a consumer cannot name the type to store it in a struct. Rejected; the box costs one indirection.
- **Accept a `tracing_subscriber::EnvFilter` in `Config`.** Puts one more upstream type in the surface where a string works. Rejected.
- **A registry callback (`Config::with_layer(..)`).** Inverts control and multiplies generic bounds. Rejected; `layer()` hands control to the consumer.
- **`InitError` as a `#[non_exhaustive]` enum.** Workable, but data in variants freezes their fields. A struct with `kind()` (the `std::io::Error` shape users already know) can carry message and source freely. Rejected.
- **`RotationConfig` with `#[non_exhaustive]` and public fields.** Allows reading and mutating fields, but skips the `max_bytes ≥ 1` validation and keeps the `Copy` commitment. Rejected.
- **A `test-util` feature.** Nothing for consumers would go in it (decision 7). Rejected.
- **MSRV N-2 rolling, or MSRV = the measured 1.89.** N-2 would follow upstream every six weeks with no consumer asking for it; 1.89 buys no known user and rules out `try_update`. Rejected for the six-month rule.

## Reconciliation with ADR-0003

ADR-0003 ([PR #53](https://github.com/vig-os/vigil/pull/53)) was written against assumptions about this ADR. Where they differ, this ADR wins (ADR-0003's own rule), and ADR-0003 changes as follows:

- **A1 (feature names):** confirmed. `metrics` and `traces`, both on by default (decision 7).
- **A2 (exporter visibility):** confirmed for stable builds: the metrics and span exporters are crate-private. With `--cfg vigil_unstable` (a compiler cfg, not a feature) they become public alongside `OtlpJsonLogExporter` (decision 4). ADR-0003 decision 2's "crate-private exporter" stays true without that cfg.
- **A3 (how code gets a `Meter`):** replaced. Applications record through `vigil::metrics` (decision 8), not `opentelemetry::global`; nothing is re-exported in the stable surface. Each instrument's scope is its declaring crate (`vigil::scope!()`); same-name conflicts are handled deterministically and loudly by a mechanism ADR-0003 decides (see the last items of this list); libraries use `tracing` only until #61. Decision 10's "instrument code can set boundaries through the `opentelemetry` instrument builder" becomes `Histogram::with_boundaries`. ADR-0003's rejection of `MetricsLayer` stands, now with probe M1 as evidence.
- **A4 (configuration shape):** builder methods with private fields, environment variables `VIGIL_*` (decisions 5 and 6). `Config::metrics_interval(Duration)` with `VIGIL_METRICS_INTERVAL` in seconds, and per-signal enable as builder methods.
- **A5 (composition):** yes. `layer()` contains the OpenTelemetry tracing layer whenever `traces` is compiled in, built for position `S`, as `Filtered` inside the box and never in a `reload` slot (decision 2; probe P1 shows propagation works there).
- **d9 (periodic reader, global meter provider):** drop "vigil installs the `SdkMeterProvider` as the global meter provider". The provider binds vigil's pipeline slot for `vigil::metrics` (decisions 2 and 8). The global is installed only under `--cfg vigil_unstable` with `install_opentelemetry_globals`.
- **d16 (global tracer provider):** drop the default install. "Crates that use the `opentelemetry` tracing API directly also write to `traces.jsonl`" holds only with that unstable opt-in, and only for crates on vigil's opentelemetry minor.
- **d15 and d19 (span extensions, parents):** `vigil::propagation`'s nearest-recorded-ancestor rule (decision 9) is stable behaviour; d15's filter stays as is, and #8 tests that the injected parent equals the exported parent of a recorded child. User-facing references to `OpenTelemetrySpanExt` (`context()`, `set_parent`, `set_attribute`, `set_status`, `add_link`) become `vigil::propagation` (decision 9) for context; attributes and status are set through `tracing` fields and the `otel.*` special fields; links are not in 1.0. "The global tracer provider is installed only after `set_global_default` succeeds" applies only with the unstable opt-in. #8's test that `Span::current().context()` is valid after `init` becomes a test that `vigil::propagation::inject` writes a `traceparent` after both `init` and `layer`. The installation constraints (no `reload` slot, provider built before the subscriber) stay, because `propagation` relies on them internally. The README warning about `add_event` remains; links are not in 1.0.
- **d3 and d4 (losses, shutdown):** losses are returned per signal in its own unit by `FlushError::lost(Signal)` from `Guard::flush` and `Guard::shutdown` (decision 3); `vigil::metrics` records dropped before the pipeline are reported once when the pipeline starts and counted under `Signal::Metrics`. d4's one-time "after shutdown" warning extends to metric records (not counted). d4's concurrent scoped shutdown threads each install the `LogsDropped` capture themselves (decision 3).
- **`InitError` kinds:** `AlreadyInitialized` is split into `AlreadyRunning` and `ForeignSubscriber` (decision 3); d15's "if `set_global_default` still fails" path returns `ForeignSubscriber`.
- **d14 and d20 (special fields, error mapping, span fields on logs):** these become stable behaviour pinned by vigil's tests across bumps (decision 1): vigil translates or waits for a major, never changes them in a minor.
- **"`RUST_LOG` filter" in d15, d16 and d20** becomes vigil's configured filter (`filter_env` / `default_filter`, decision 2).
- **The `MetricsLayer` alternative:** its last sentence ("Applications use the `opentelemetry` metrics API") becomes "Applications use `vigil::metrics` (ADR-0004 decision 8)".
- **d13 (bump policy):** the coordinated opentelemetry/`tracing-opentelemetry` bump is a vigil minor unless it changes the on-disk format (decision 1 here, ADR-0001's stance).
- **One pipeline per process:** ADR-0003 decision 1 ("one `init`, three signals") gains that `layer()` builds the same three-signal pipeline, that a second `init`/`layer` returns `AlreadyRunning`, and that `init`'s "refused install" path covers both.
- **Metric identity conflicts (new decision required):** the mechanism behind decision 8's requirement. Either the exporter removes losing streams from every export, or the loser is rejected at bind time. Histogram boundaries are part of identity. The outcome must be independent of thread order, including the case where the winner never records. Proven on `opentelemetry_sdk` 0.33: the final review showed a losing cumulative histogram keeps exporting (`flush3 ["crate-a:app.x:ms","crate-b:app.x:ms"]`), so unbinding alone does not work.
- **Unit of `lost(Signal::Metrics)`:** do not mix data points (failed or bounded exports, d3, d11) with measurements (`vigil::metrics` records dropped before init or in a conflict). Pick one unit, or split the counts, and say how `FlushError` exposes it.
- **d18 vs `lost(Signal::Traces)`:** d18's open-span count is an upper bound and `lost` is a lower bound. Say which is reported where (stderr, `FlushError`, both), and whether d3's stderr summary still prints when `shutdown()` already returns the losses.
- **Deferred section:** the "exporter visibility, how applications obtain a `Meter`, and the versioning of a coordinated upstream bump" item is resolved by this ADR and can be removed.
