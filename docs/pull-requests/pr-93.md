# [PR 93](https://github.com/vig-os/vigil/pull/93) feat(metrics): add cumulative exports through shared envelopes

## Description

Add the cumulative metrics data path through shared OTLP envelope ordering, sanitizing and bounding. Oversized metric points are dropped and reported without fabricating series identity; data-point failures set lifecycle outcomes without counting measurements.

Log scope order on attribute ties now follows the documented total order. Log records retain their batch order within each scope, and existing golden checks pass. The exporter and shared bounding API remain crate-private by default and labelled unstable under `vigil_unstable`. Reader/file wiring, the metrics facade, identity filtering and final shutdown summaries remain in 7b; resource identity and log batch environment pins already landed in #88.

## Changes Made

Logs and metrics both use the generic envelope pipeline, normalization step, attribute helpers and signal/unit reporting machinery. Ordering compares decoded name/version/schema URL, then sorted attributes using a fixed typed-value order. Equal primary keys compare child structure recursively, excluding every time field: metrics by name, description, unit, then points by attributes and typed values; log records keep their existing order and compare non-time fields. Only equal non-time structure compares timestamps, oldest first. Keys are built once per element only within tied groups. SDK HashMap traversal must not leak into scope ordering through per-scope collection timestamps. Metrics split at metric and point boundaries with repeated metadata. Log shortening and diagnostic stubs retain their existing rules.

### Manual Testing Details

R6: `cargo test --all-features` and `just precommit` exit 0. The tied-scope timestamp regression exhausts both permutations of (50,60) and (100,1), expecting first-point times ["100","50"]. Removing `times.sort();` makes it fail by assertion (exit 101); the corrected implementation passes.

Previous-round acceptance commands exited 0: `just precommit`, `nix flake check -L`, `cargo test --lib --features test-preserve-order` (118 passed, two ignored timing probes), `python3 scripts/conformance.py`, and `nix develop -c python3 scripts/check_public_api.py`. Both exact CI ordering configurations also pass: `RUSTFLAGS="--cfg vigil_unstable" cargo test --locked --no-default-features --lib ordered`, and the same command with `--features audit,test-preserve-order`. Collector semantic round trips retain 40 metric points and 1,306 log records; the stable API snapshot is unchanged.

Log and metric scope tests exhaust all 24 permutations in four four-element families (96 per signal), including NaN, signed zero, infinities, escaped strings and attribute-count variants. Their children have distinct timestamps opposed to the structural order, and assertions verify that children decide before time. Additional fixtures pin metric name/description/unit, numeric values, recursive AnyValue type ranks and array/list prefixes, record sequences, empty versus populated point attributes, every `*TimeUnixNano` field, and numeric oldest-first ordering when only timestamps differ. Log record order is retained.

The real SDK regression uses `OtlpJsonMetricExporter`, `SdkMeterProvider` and `PeriodicReader`: 24 fresh providers with four counters carrying NaN scope attributes, collected twice each in-process without timestamp normalization (48 collections), produce exactly one order. Against the `234faec` sorter the same probe produces six distinct orders and exits 101. The timestamp-bearing log and metric permutation tests and all three structural fixture tests also fail by assertion with that sorter (exit 101); all pass with the correction.

Earlier regression proofs remain: individually reverting temporality, point dropping, time-first keys, period flags, non-finite attributes, split commas, exact-limit comparisons, shared log ordering, shutdown gating or returned sink errors produced assertion failures and exit 101. Exact-limit packing tests kill both `>` to `>=` mutations. Loss tests cover metrics-only and mixed periods, precedence/reset and failed split writes; stderr reporting tests cover first failures and rate-limited summaries.
