# [PR 35](https://github.com/vig-os/vigil/pull/35) fix(logs): bound JSON lines for Collector ingestion

## Description

Prevent the default Collector receiver from silently discarding large log batches. Every emitted JSON line stays within a configurable byte budget (1,000,000 by default).

## Type of Change

- [x] `fix` -- Bug fix
- [x] `test` -- Adding or updating tests
- [x] `docs` -- Documentation

### Modifiers

- [ ] Breaking change (`!`)

## Changes Made

- #30 item 1: split batches deterministically at record boundaries, pack multiple scopes per line, and copy only resource/scope metadata. `with_max_line_bytes` configures the budget and clamps it below 1 MiB.
- #30 item 2: shorten the largest body/attribute strings by the exact escaped-byte overflow, while keeping attribute keys, eventName, scope and resource fields immutable; preserve UTF-8, base64 and non-finite spellings. Replace unshrinkable records with explicit dropped stubs, preserving identity and healthy neighbors; a bounded `vigil.dropped_reason` retains small original messages. Set `vigil.truncated` and `vigil.original_size` (original single-record line bytes including envelope).
- #30 item 3: emit 1024 ~4 KB records and one 3 MiB body through `vigil::init` and the tracing bridge. Include one 60,000-integer-attribute record and verify its dropped stub survives the pinned Collector alongside every healthy record.
- #30 item 4: record the size-limit evidence and accepted non-finite reader deviation in ADR-0001.
- Serialize nextest cases to keep multiprocess regressions within the shared host's eight-process limit. No dependency changes. No items were marked unverified in the issue.

## Changelog Entry

### Fixed

- Keep attribute keys and event names immutable when bounding log lines; replace structurally oversized records with counted stubs that preserve small original messages ([#30](https://github.com/vig-os/vigil/issues/30))

- Bound OTLP/JSON log lines to the Collector limit, split large batches, and mark truncated oversized records; exercise large tracing records in Collector conformance ([#30](https://github.com/vig-os/vigil/issues/30))

## Additional Notes

Immutable keys, eventName, attribute count, or other unshrinkable record data becomes a diagnostic stub with the original timestamps, severity, trace/span IDs and scope. Its body explains the original single-record line size and cap, and its attributes include `vigil.truncated`, `vigil.dropped` and `vigil.original_size`. A bounded `vigil.dropped_reason` retains the original string body within the remaining line budget. Healthy neighbors export normally with an Ok result. The latest dev adds runtime-loss diagnostics. Dropped stubs enter that same cumulative, rate-limited summary, including shutdown reporting, with a regression that fails before the counter integration (exit 101). An impossibly small budget for the resource/scope envelope and preserved diagnostic identity still returns an explicit error; no oversized line is emitted.

Golden fixtures remain byte-identical: batches already within the cap retain their existing encoding, so no blessing was needed. Large batches use the new packed layout; regressions verify record counts, scope identity, order, deterministic bytes and byte budgets. The runtime-summary integration makes a narrow change to the newly merged reporting wrapper in `src/init.rs`; `src/rotate.rs` is unchanged.
