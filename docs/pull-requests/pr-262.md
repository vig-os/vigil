# [PR 262](https://github.com/vig-os/vigil/pull/262) feat(audit): confirm resume gaps by an accept Resumed line

## What changed

ADR-0005 decision 11 says an `accept Resumed` line "also confirms that resume's gap". The confirmation set `engine::check` built from matched receipts (ruling 13-V7-d1 point 8) gains matched, in-range `accept Resumed` pins, computed in one place before `build_gaps` runs; every downstream consumer (`LostRecord` for receipts/waivers/`from`/accept lines inside the gap, `lost_records=<n>` in the `Resumed` detail carried under the `Accepted` finding's `was:` tail, genesis `SeqGap` suppression, and anchor/`through=` pin demotion only when the opening is itself anchored per ruling 13-V7-d1 point 8) reads it unchanged. The shared match rule is reused: a mismatched, set-aside, forked, non-Resumed-kind or untrusted-opening `accept Resumed` confirms nothing.

No new public API: the rule plugs into `Verifier::accept` (#261).

### Equivalent mutant note

A narrower variant of the keyed-by-`seq`-only mutant that changes **only the lookup** in `build_gaps` from `confirmations.contains(&(c.resume_seq, c.resume_hash))` to `confirmations.iter().any(|&(s, _)| s == c.resume_seq)` is equivalent on these rows. The shared `receipts::matches` rule guards the insert path: a `(seq, hash)` reaches `confirmations` only when exactly one unforked record at `seq` has that hash, which is the resume record's own hash. A forked `seq` is rejected by `receipts::matches`, so two distinct candidates sharing a `seq` cannot both land in `confirmations` with each other's hash. The seq-only lookup therefore matches `(resume_seq, resume_hash)` iff the `(seq, hash)` lookup does. The measured variant that strips the hash at insert time (above) kills the rule outright.
