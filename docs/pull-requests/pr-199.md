# [PR 199](https://github.com/vig-os/vigil/pull/199) test(audit): pin every reader CorruptTrail detail per path (#197 R0a)

## Summary

Pins the reader `CorruptTrail` detail strings for the paths that stay in R0a per the 197-d1 addendum (point 6). R0a's trimmed scope here is `scan_inner` called directly as `scan(.., opening, ..)` plus the `apply_checked` sites it reaches, with a coverage gate that classifies every `corrupt(..)` call site in `src/audit/storage.rs` as asserted, deferred to R0b, or proven unreachable with a reason. The paths pinned here are:

- `scan` → `scan_inner` live-path first-record and loop-body guards (`scan_closing`/`scan_staged` are R0b, per 197-d1 addendum 6)
- `apply_checked` reached through `scan(.., opening=false, state=None)` on empty, fragment-only and entry-only files
- `history_segment` strict-pass through its fallback body (via a direct `history_segment` call on the fallback-eligible layouts)
- the two `existing()` guards on `TrailReader::open`'s file-type check

## What moves to R0b (addendum point 6)

- `scan_staged` and `scan_closing` driven via their public callers, and the `TrailReader::open` live path on a real reader, including the path-dependent archived-base case (`scan` Ok vs `scan_staged` `initial checkpoint does not link genesis`).
- The named run layouts R0b owns: `boundary_resume` after a run segment, the opening MMR mismatch, and the genesis closer after a fragment-only first segment.
- The `history_segment` fallback rescan, the `refresh` path (`opening=false` with cached `State`) and `resume`.

## Mutants, not labels, are the proof

The site occurrence indices in `UNREACHABLE` / `PENDING_R0B` / `assert_corrupt(.., site)` are documentation labels; nothing about the gate depends on `occurrence==N` matching any particular code line. What proves the pins are load-bearing is the mutant table below: changing a detail string, or swapping two check order on one path, must make the named pin exit 101 at runtime (not fail to compile).

## Coverage gate

`coverage_gate_pins_every_corrupt_site` reads `storage.rs` and `storage_tests.rs` with `include_str!`, extracts every `corrupt("...")` call site (skipping `fn corrupt(`) and every `assert_corrupt(result, "<detail>", site)` pin, and fails if a site has no assertion and is not listed in `PENDING_R0B` or `UNREACHABLE`. The occurrence indices in those tables and in the `assert_corrupt` calls are labels for a reader; the mutants below are what proves the pins catch the behaviours they claim.

## Mutant proofs

- 23 detail-string mutants on R0a's asserted sites (every shared-detail site plus 10 representative per path kind) each make the named pin exit 101 at runtime; reverting restores exit 0.
- `coverage_gate_pins_every_corrupt_site` fails exit 101 when a new uncovered `corrupt("x")` site is added inside `initial`; reverting restores exit 0.
- Round 2 adds two mutants on the paths this round pins:
  - Changing `corrupt("missing head")` at the post-loop site (`scan_inner`) to any other string makes `pin_sc_missing_head_opening_false_empty` and `pin_sc_missing_head_opening_false_fragment_only` exit 101 (both fail with "detail mismatch"); reverting restores exit 0.
  - Swapping the two first-record guards on `scan_inner`'s live path (`opening checkpoint duplicates predecessor` and `missing opening checkpoint`) makes `pin_sc_opening_duplicates_predecessor_non_checkpoint` exit 101 (120 passed, 1 failed on the full `audit::storage::tests` filter); reverting restores exit 0 at 121 passed.
