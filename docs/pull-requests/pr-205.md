# [PR 205](https://github.com/vig-os/vigil/pull/205) refactor(audit): move history_segment's tolerant walk onto the shared runs::Classifier (#197 R2b S2)

## Summary

#197 R2b Slice 2: move `history_segment`'s tolerant-mode walk (including the fallback rescan from the saved segment-start state) onto `runs::Classifier`. The reader's `history_segment` becomes a thin shim that drives the strict `scan_inner` shim first (unchanged) and, on `CorruptTrail`, drives the tolerant classifier (`new_tolerant` / `feed_fragment_tolerant` / `feed_unparsable_tolerant` / `feed_record_err_tolerant` / `feed_record_prepare_tolerant` + reader-side `check_attestation` + `feed_record_apply_tolerant` / `finish_tolerant`) restored from a snapshot of the pre-pass `RunState`. Every `CorruptTrail` detail is byte-identical on every path; the writer-only `(checkpoint_time, since_checkpoint)` fold now flows through one shared private helper (`next_cp_fields`) used by `scan_inner`, `apply_checked` and the fallback rebuild, so the three sites cannot drift. Also fixes the carried stale `scan_inner` header comment (the strict `Classifier::feed_record` itself calls `runs::check_attestation`; the shim hands it `gap_digest` via `take_gap`).

Ruling 197-d1 addenda 6-15 (12: reader's per-path order binds on every path including the tolerant fallback walk; 13: S2 scope; 14: single atomic PR; 15: `next_cp_fields` saturates at `u64::MAX`). Owner decision 13-V4-d4 (one shared pure classifier). ADR-0005 amendment 6, B3d1-d1/d3/d4, 107-d1. S3 (classify iterator, every-violation collector, typed `Violation` enum consumed by V4a, caveat rewrite) remains out of scope (addendum 13).

## Single intended deviation from base

`next_cp_fields` increments `since_checkpoint` with **`saturating_add(1)`** on every path (per ruling 197-d1 addendum 15). Base was inconsistent: `scan_inner` used `saturating_add(1).max(1)` (the `.max(1)` a no-op), while `storage::apply_checked` (and the reader's pre-S2 fallback that routed through it) used plain `+ 1`, which panics in debug and wraps to `0` in release at `u64::MAX`. A wrap to `0` would falsely signal "just checkpointed" to the writer's cadence. The refactor unifies the three sites behind one helper (DRY), and the helper must match base's strict-path semantics on every realistic input while fixing the `apply_checked`/fallback bound. The bound counts records since a checkpoint, so it is unreachable in practice; the semantics must still be correct on every path.

Everywhere else head and base produce byte-identical outputs (error strings and every Ok-state field), apart from the unobservable `*run`-on-`Err` value described below. The final fresh review's 311,025-row differential found the only other differing rows (4,874) all in `since_checkpoint = u64::MAX` contexts, where base panics and head saturates.

## Second, unobservable difference (introduced by this PR)

On an `Err` from the fallback body, base had already set `*run = inherited` before its fallback loop, while this head leaves `*run` at the value the caller passed in. **This PR introduces that difference; it is not pre-existing.** It is unobservable: all five callers of `history_segment` (in `sink.rs` and `storage.rs`) propagate the `Err` with `?` and drop `run`, so no output differs. The final fresh review normalised exactly this field on `Err` rows (8,155 raw rows differ only in it).
