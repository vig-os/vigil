# [PR 111](https://github.com/vig-os/vigil/pull/111) feat(audit): reader rule for segment runs sealed by resume (B3d1)

## Description

A trail sealed by an operator resume could not reopen when a sealed segment had lost its opening checkpoint or ended in an Unparsable crash outcome. The reader now accepts such runs only when the successor checkpoint links the last present head, its immediate resume names that head and loss bound, and its MMR matches the cumulative fold of all present records.

## Changes Made

- Record accepted ADR-0005 amendment 6 and rulings B3d1-d1/d2/d3/d4, including the leaf-index, archiving, and permanent verifier findings.
- Seed the fold from the first present complete checkpoint's size and peaks, push that checkpoint and every later complete record once, and never reset state at a damaged boundary. A genesis-linked resume without a predecessor uses the existing creation-leaf base (size 1); the reader enforces size 1 in both the amendment-4 and amendment-6 paths; constructor/decoder checkpoint counts stay unchanged.
- Permit sequence gaps at broken segment starts inside sealed runs; require consecutive sequences and intact hash links after each segment's first record. Restore ordinary resume-gap and MMR checks once a run closes. Preserve cached-head, staging, repair, and pending-resume checks.
- Share the same predecessor fold and pending-run boundary with B2b staging settlement, including hand-built resume and normal rotation staging fixtures. A record-free first run can close at its own base only through a genesis link.
- Cover one/two-segment runs, fragment-only segments, Unparsable tails, honest periodic checkpoints, overlapping successive runs, a second loss, and creation-checkpoint loss followed by hand-built staging settlement. Check prefix/middle deletion, wrong heads, missing/delayed/duplicate declarations, and internal sequence gaps.
- Compare every checkpoint before the current run’s first broken record hash link, using the existing fold validator. Carry the loss point across run segments and clear it at closure. Preserve the periodic-checkpoint exception at/after actual loss and always compare the closing opening checkpoint.
- Preserve decision 8’s immediate-resume requirement after an unsealed predecessor even when the successor has an Unparsable suffix. The shared scanner enforces it for open, cached refresh and staging settlement.
- Reject the first linking-checkpoint successor if its fold or immediate resume is invalid, rather than extending the run to a later closing segment. Preserve ordinary duplicate-line and repair rules within runs; reject interior non-fragment lines.
- No public API, disk format, dependencies, operator resume implementation, README, or verifier changes. The pre-existing first-present-prefix residual (#107) remains out of scope.

### Architect ruling B3d1-d4

The wider property in d3 conflicted with the original checkpoint exception: a wrong-MMR linking checkpoint was rejected, but appending `junk` made its segment a run member and caused its fields to be ignored. A concrete property probe reproduced that acceptance (runtime exit 101). The architect resolved it by narrowing the exception: no loss point means no checkpoint-MMR exemption. Amendment 6 (iii) now states that rule explicitly, while retaining the d3 property and fixing the lowercase sentence start under Run boundaries.

Pre-mortem before implementing d4: checked crash/resume, torn-fragment repair (`audit.repaired`), rotation, settlement/staging promotion, creation recovery, genesis resume, archived bases, and identical duplicate lines. No honest path writes a checkpoint with a mismatched present-record fold before a hash-link loss. Fragments and duplicates add no leaves; repair attestation is part of the next record’s hash. Archiving seeds the retained base’s size/peaks; genesis resume retains its one creation leaf. The comparison reuses the normal scanner’s `apply_checked` helper.

Each d4 fixture checks open, cached refresh and staging settlement: wrong-MMR linking checkpoints reject both with and without `junk`; correct fields plus `junk` and closing resume open; a headless run’s honest periodic checkpoint still opens even when the actual loss occurred in an earlier segment whose successor’s first hash link is intact.

## [Comment #1](https://github.com/vig-os/vigil/pull/111#issuecomment-6125987665) by [@gerchowl](https://github.com/gerchowl)

_Posted on October 12, 2026 at 02:10 PM_

Architect ruling B3d1-d4 (answers the r3 BLOCKED: the B3d1-d3 property conflicted with amendment 6 (iii)'s exception for in-run checkpoints). The exception is narrowed, not the property. Inside a run, every checkpoint before the run's first **loss point** (the first complete record that does not hash-link to its predecessor) has its MMR fields compared to the fold, as outside a run. Only checkpoints at or after a loss point (honest periodic checkpoints in a headless file) stay uncompared. Unparsable lines add no leaf and break no link, so appending them can never make a rejected trail acceptable. ADR-0005 amendment 6 (iii) is updated in this PR; the block was architect-caused and the round is not counted.
