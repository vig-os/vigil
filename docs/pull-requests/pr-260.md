# [PR 260](https://github.com/vig-os/vigil/pull/260) feat(audit): set aside anchors and pins in a confirmed gap with an anchored opening

## Summary

Anchors and ``through=<b>:<h>`` revocation pins inside a confirmed resume gap whose opening checkpoint is itself anchored (an input anchor on the verified trail with the opening's full ``(trail, seq, hash)``) are set aside as one unlocated ``LostRecord`` (info) at the input's ``seq``. Only the pin's hash check is replaced: the bound still limits the key (``UntrustedKey`` above the bound still fires) and the confirmation check still runs. Another trail's anchor is never set aside, and a receipt or ``accept`` line never anchors an opening on its own, closing the stolen-key cut over anchored checkpoints (ADR-0005 decision 5 "Receipts lost with a resume"; ruling 13-V7-d1 point 8).

Implementation: one shared helper ``Classifier::lost_record_anchored`` next to ``Classifier::set_aside`` builds the ``LostRecord`` through one finding constructor; ``anchors::evaluate`` and ``revocation::check`` call it after the ``set_aside`` step. ``opening_anchored`` on the classifier's gap entry runs the shared ``anchors::match_only`` (ruling 13-V6-d1 point 2), so a forked opening is never anchored even when an input anchor equals its ``(trail, seq, hash)``.

Correction: M6 (another trail's anchor is set aside) kills only A6, not A5b + A6; the trail-differs check runs ahead of ``lost_record_anchored`` for A5b whose anchor sits above the gap.

Equivalence arguments:
- N1 ``match_only`` ignores trail: the anchor's hash commits over its own trail, so a cross-trail match on identical ``(seq, hash)`` with a different trail is cryptographically infeasible; no row in the suite distinguishes it.
- N4 pin ``lost_record_anchored`` branch skips the ``confirmation`` call: the demoted pin lives inside a confirmed gap whose opening is a trusted-signed checkpoint strictly above the bound, so ``confirmation`` always returns early without emitting; both paths produce the same findings on every row.
- "candidate gap confirmed+anchored with seqs strictly above ``last_line_seq``" cannot exist: confirmation requires the resume receipt ``(resume_seq, resume_hash)`` to pass ``bare_position.set_aside``, i.e. ``resume_seq <= last_line_seq``; but ``resume_seq = opening_seq + 1 = lost_through + 2 > high``, so a gap seq strictly above ``last_line_seq`` forces ``resume_seq`` above too, and confirmation fails. A10 and A10b therefore pin the order through an unconfirmed candidate gap above ``E``, with ``N10`` as the kill.
