# [PR 63](https://github.com/vig-os/vigil/pull/63) docs(adr): ADR-0006 shipping via the Collector file shipper and an optional push feature

## Description

Proposes ADR-0006 (Status: Proposed): how vigil's OTLP/JSON Lines files reach Loki and Prometheus. It follows the owner decision of 2026-10-11, supersedes ADR-0001 decision 9 for the optional `push` feature, and extends ADR-0001 decision 5 with a promised time-first JSON key order.

## Type of Change

- [x] `docs` -- Documentation only

### Modifiers

- [ ] Breaking change (`!`) -- This change breaks backward compatibility

## Changes Made

- `docs/adr/0006-shipping.md` (new):
  - **The reference file shipper is the Collector-contrib `otlpjsonfile` receiver,** with a config whose rules were each shown necessary by restart/rotation probes:
    - `file_storage` (without it: 100 duplicates per restart);
    - `start_at: beginning` (with `end`: 100 of 150 records lost);
    - live file plus `<signal>-*.jsonl` segments (live file only: 82 of 150 lost);
    - `include_file_name: false`;
    - no `batch` processor below contrib 0.162.
  - **A time-first JSON key order keeps every segment's fingerprint unique.** The receiver identifies files by their first 1000 bytes. With a 700-byte metric description, today's alphabetical order delivered 3 of 150 points silently; time-first delivered 150 of 150.
  - **The `push` feature** sends the same bytes as OTLP/HTTP JSON (accepted by the Collector and by Alloy 1.16, equal by meaning) to a loopback IP-literal agent, over `ureq` 3 without TLS (+6 crates):
    - a bounded drop-oldest queue, OTLP retry rules, and a shutdown deadline that is honoured (prototype);
    - `VIGIL_PUSH_*` configuration;
    - `VIGIL_PUSH=off` as the operator kill switch.
  - **Why Alloy has no OTLP-file receiver:**
    - Alloy bundles a curated subset under an inclusion policy.
    - The receiver is alpha, its codeowners are seeking new maintainers, and it had a race until contrib 0.162.
    - Nobody has requested it upstream.
    - The smaller ask is the `otlpjson` connector ([grafana/alloy#6752](https://github.com/grafana/alloy/issues/6752)); `filelog` + `otlpjson` was probed working. Nothing was filed upstream; that is the owner's decision.
  - **The Loki `otlp_config` that keeps `service.instance.id` out of index labels.** The obvious override is a no-op; `ignore_defaults: true` works, as probed on Loki 3.7.8.
- `docs/adr/0001-on-disk-format.md`: marks decisions 5 and 9 and the versioning stance as amended by ADR-0006, effective when it is accepted.
- `docs/adr/README.md`: index row for 0006.
- Filed [#60](https://github.com/vig-os/vigil/issues/60) (0.2.0) to own the reference config and its exactly-once and fingerprint conformance tests.

## [Comment #1](https://github.com/vig-os/vigil/pull/63#issuecomment-6103710528) by [@gerchowl](https://github.com/gerchowl)

_Posted on October 11, 2026 at 12:22 AM_

Cross-ADR coordination from ADR-0003 (PR #53, head 4a0db5f, decisions 12 and 23). Two changes ADR-0006 needs to stay consistent:

**1. Decision 4, "Tee order", failed file writes.** ADR-0006 currently says:

> It still counts as lost in `FlushError::lost(Signal::…)` (ADR-0004 decision 3, in the signal's own unit), because the durable copy is missing.

ADR-0003 decision 23 (which amends ADR-0004 decision 3) counts `lost(Signal::Metrics)` in **measurements**. A failed metrics *line* is a data-point problem, and it sets the error kind without a count. Proposed replacement:

> A failed file write of a **log or span** line still counts its records or spans in `FlushError::lost(Signal::Logs | Signal::Traces)`, even if the push copy is delivered, because the durable copy is missing. A failed write of a **metrics** line sets `FlushErrorKind::Failed` and is reported on stderr in data points, and is not added to `lost(Signal::Metrics)` (ADR-0003 decision 23): the next cumulative export carries the totals again.

**2. Reference shipping config / README (Prometheus side).** ADR-0003 decision 12 now requires Prometheus `otlp.promote_scope_metadata: true`. Probe P17 used otelcol-contrib 0.151.0 → Prometheus 3.12.0 with defaults. `crate-a` and `crate-b` both recorded counter `app.x` (+5 and +7 per round). The result was `app_x_total {} ['5','10','10']`: crate-b's data was dropped with 0 errors. With the setting there were two series, labelled by `otel_scope_name`. ADR-0006's Prometheus guidance and #60's conformance config should include:

```yaml
otlp:
  promote_scope_metadata: true
```

Please mention in the README that a dependency's version bump then starts new series (`otel_scope_version` label).
