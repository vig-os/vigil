# [PR 92](https://github.com/vig-os/vigil/pull/92) feat(audit): durable writer core (B2b1)

## Description

Implement the crate-internal durable audit writer on the existing locked reader. A successful record returns its head after the data flush; the handle retains its known written state before releasing the directory lock. Creation, checkpointing, sealing, recovery and consuming close share the existing OTLP projection, scanner, single-write helper and no-replace rename machinery.

## Changes Made

- Explicit `create` draws 16 random bytes, writes the `0400` marker, flushes the marker and directory, and publishes the creation checkpoint through staging. `open` settles recovery without signing or writing record bytes and checks structural loss before the expected head. See [ADR-0005 lines 535–574](https://github.com/vig-os/vigil/blob/feature/11-audit-writer/docs/adr/0005-audit-trail.md#L535-L574). The marker encoding ruling is recorded in the ADR: exactly 32 lowercase hex characters plus one LF; malformed spellings are `CorruptTrail`.
- Records validate through the existing mapping, reject reserved actions and excessive payloads, take time under the lock, combine a due checkpoint into one write, roll partial writes back, and acknowledge after `sync_data`. One internal constructor/path supports every reserved action. See [time at line 196](https://github.com/vig-os/vigil/blob/feature/11-audit-writer/docs/adr/0005-audit-trail.md#L196), [lines 427–449](https://github.com/vig-os/vigil/blob/feature/11-audit-writer/docs/adr/0005-audit-trail.md#L427-L449) and [line 582](https://github.com/vig-os/vigil/blob/feature/11-audit-writer/docs/adr/0005-audit-trail.md#L582).
- The first line after a gap attests exactly its bytes and repair LF, including closing and close checkpoints. Complete JSON without LF remains a record, and its missing LF counts toward the rotation budget. See [lines 410–421](https://github.com/vig-os/vigil/blob/feature/11-audit-writer/docs/adr/0005-audit-trail.md#L410-L421).
- Checkpoint cadence follows the latest checkpoint in the trail across processes. The ADR records the ruling for count, wall-clock baseline after open/refresh, and immediate checkpointing after a clock step back. Signer failures acknowledge records, retry on the next append, report once and increment the internal unsigned counter; rotation can grow the segment during an outage. Explicit checkpoints return the signer error, consuming close writes nothing on signer failure, and Drop tries best effort. See [lines 489–493](https://github.com/vig-os/vigil/blob/feature/11-audit-writer/docs/adr/0005-audit-trail.md#L489-L493), [513–521](https://github.com/vig-os/vigil/blob/feature/11-audit-writer/docs/adr/0005-audit-trail.md#L513-L521) and [613](https://github.com/vig-os/vigil/blob/feature/11-audit-writer/docs/adr/0005-audit-trail.md#L613).
- Sealing follows the staged steps and directory flush order. Both staging names are settled at open and every operation, including complete interrupted creation and resume promotion over a live opening checkpoint. See [lines 524–554](https://github.com/vig-os/vigil/blob/feature/11-audit-writer/docs/adr/0005-audit-trail.md#L524-L554). Settlement shares the scanner’s genesis-link and resume-head checks: with no predecessor, a genesis-linked resume must name `head=0:<genesis digest>`; self-contained archived prefixes remain supported. Shared no-replace publication reuses ADR-0002's link/unlink fallback and inode-link check to finish an interrupted fallback without scanning or sealing the same inode twice.
- Any failed operation fsync returns `Io` and poisons subsequent records on the handle. Live appends truncate to their pre-write length; failed rollback creates the `0600` shared poison marker under the lock. See [lines 447–449](https://github.com/vig-os/vigil/blob/feature/11-audit-writer/docs/adr/0005-audit-trail.md#L447-L449).

- **Rule 1:** truncate an unpromoted staging file to zero after a failed staging write, staging-file fsync, or directory fsync of its name. Failed writes return `Io` without poisoning; failed fsyncs poison an existing handle, and a failed rollback then creates `audit.poison` naming the staging file. - **Rule 2:** create `audit.poison` under the lock after a failed directory fsync following a rename into or out of the live name, including sealing, settlement promotion during a running operation or `open`, and final `create`/future `resume` promotion. Record the cause (`directory fsync after rename`) and affected names; cover failed poison-file creation and the restart/remount → verify → remove clearing procedure. B2b1 currently returns `Io` and poisons an existing handle, but creates no shared barrier at these sites.
- **Rule 5:** make `checkpoint` and consuming `close` reject an in-memory-poisoned handle before taking the lock, reading, signing or settling; make `Drop` of that handle inert and silent. B2b1 already does the early check for `record`, but its checkpoint/close/Drop paths can still settle and sign.
- **Rules 5–6 / all write paths:** report one stderr line for a new failure of Drop's best-effort checkpoint (including `Io`, signer failure, or a shared `audit.poison` barrier), while writing nothing when the shared barrier exists and printing nothing for a handle already poisoned in memory. B2b1 currently discards Drop's checkpoint error.
