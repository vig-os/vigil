# [PR 249](https://github.com/vig-os/vigil/pull/249) feat(audit): link records across seq jumps and pin the end of an archive batch

## What changed

- The chain loop in `src/audit/verify/engine.rs` compares every record (except the record at the lowest `seq`) with the record at the **highest present `seq` below it**, not only `seq - 1`. The expected set is the hashes at that `seq` (forks included). The record at the lowest `seq` keeps the existing genesis / prefix-`SeqGap` / accepted-start rules. No special case for resume openings or end-record lines.
- `src/audit/verify/end_before.rs` holds exactly one end-specific link finding: `no_record_precedes` emits one unlocated `ChainBroken` at `e` with `end_before seq <e>: no record precedes the end` when the files hold no record below `e` and `e > 0`; at `e = 0` nothing is checked.
- `FindingKind::ChainBroken` rustdoc covers both the chain-rule form (now across jumps) and the end-specific form.
- One CHANGELOG `Unreleased` sentence.

ADR: decision 2 step 6, decision 11 `accept-run` item 2, the prefix-deletion and tail-cut bullets. Ruling: 13-V6-d6.

## Rows (`src/audit/verify/end_link_tests.rs`)

Every row asserts the full sorted `Vec<Finding>` through `assert_findings`. Hashes, MMR roots and digests that appear in a detail string are `const` hex literals pinned by `fixture_hashes_match_literals`. The writer stamps every record with a wall-clock time stamp through a time hook that is `pub(super)` inside `sink` and is not reachable from this module, so the writer's record hashes drift per run and these rows are hand-built; they use the fixture `TRAIL` and `signed_cp` / `entry_rec`, which construct records through the same `Record::checkpoint` / `CheckpointFields` call the writer's `sink::signed` uses (`sink.rs` ~765..=781) and the same fixture signer, so each record is byte-for-byte what the writer would emit at the fixture clock.

L4 is built as the prefix-deletion layout of ADR-0005 l.942..=943: six sealed segments `S0..=S5`, each starting with its own opening checkpoint `cpN`; `S0..=S4` were archived at writer-style segment ids 0..=4 and `S5` kept, then `S3` and `S4` were deleted from the archive, so the archive is `[cp0, cp1, cp2]`. `S5 = [cp5]` lives in the live directory as a sealed segment at segment id 5, and the writer's live file `audit.jsonl` follows it with a fresh opening checkpoint `cp6 = signed_cp(6, cp5.hash(), fold through cp5)`. The start for form (c) is `cp5`.
