# [PR 244](https://github.com/vig-os/vigil/pull/244) feat(audit): set aside anchors and pins below an accepted start

## Summary

An anchor or a `through=<b>:<h>` pin whose `seq` is strictly below an **accepted** `Verifier::start_from` start no longer runs its ordinary `AnchorMismatch`/`RevocationMismatch` check. The check is replaced by one unlocated finding of kind `OutOfRange` (info) when the start is anchored, or `UnanchoredStart` (error) otherwise. Another trail's anchor still gives `AnchorMismatch … trail differs`; the pin's confirmation check runs unchanged. With no accepted start, every `seq` is in range as before. This closes the stolen-key cut above an anchor (ADR-0005 decision 11 "A signature alone never demotes anything", ~l.753-757; ruling 13-V6-d3).

## Details

- `anchor seq <a> hash blake3:<64 hex>: below start seq <s>` (anchor)
- `key <64 hex> through=<b>: below start seq <s>` (pin)

Implementation: one crate-private module, `src/audit/verify/position.rs`, holds the two-case classifier `InRange` / `BelowStart { start_seq, anchored }` plus the shared `Classifier::set_aside(seq, subject)` helper. The classifier is built once per verify call from the accepted start and the anchors; "anchored" matches the start's full `(trail, seq, hash)` against the anchor list (ruling 13-V6-d3 point 3); acceptance (ruling 13-V6-d1 point 2) guarantees that anchor matches. Both call sites (`anchors::check` and `revocation::check`) consume the helper so the `OutOfRange`/`UnanchoredStart` choice and the detail suffix live in one place; the trail-differs precedence still runs first (ruling 13-V6-d3 point 4). The reader, `end=`, `max_age` and the signature/trust predicates are untouched. The full rule lives on `Verifier::start_from`.

| give the below-start finding a location | P1, P2, P3, P4, P6, P11, P12 |
| skip the confirmation check for a pin below the start | — (equivalent) |

**Equivalence argument (skip confirmation below the start).** A key is unique per section (`trust.rs::validate`), so the accepted start's key is never the bounded key of a `through=` entry in that same section. A bound below an accepted start therefore has the start's own trusted checkpoint, signed by another key, strictly above the bound — the start always confirms the bound. `confirmation` returns without emitting in the below-start case either way, so skipping it changes nothing observable. The `RevocationUnconfirmed` half of ADR-0005 d11 l.939 is covered by P9 (`b = s`): that bound is in range, so the ordinary confirmation runs and fires `RevocationUnconfirmed` when no other-key trusted checkpoint sits above it.
