# [PR 204](https://github.com/vig-os/vigil/pull/204) refactor(audit): push-API classifier for scan_inner family (#197 R2b1)

## Description

#197 R2b Slice 1: move `scan_inner`'s strict-mode per-segment checks
into a crate-private push-API `runs::Classifier`. `scan_inner`/`scan`/
`scan_staged`/`scan_closing` keep their shape and become thin shims that
drive the classifier, with the reader still owning byte-level I/O and
the writer-only `checkpoint_time`/`since_checkpoint` counters. Every
`CorruptTrail` detail is byte-identical on every path; the
`apply`/`apply_checked` wrappers, `State::after`, `refresh`,
`history_segment`, `resumes_after`, `resume_header`, `segments_after`
and the public API are untouched.

See `docs/adr/0005-audit-trail.md` §19.9 (one sentence appended after
R2a's). R2b S2 moves `history_segment`'s fallback walk and adds the
tolerant mode; R2b S3 adds the every-violation collector with typed
violations and the `classify` iterator V4a consumes (ruling 197-d1
addendum 13).

## Type of Change

- [x] `refactor` -- Code restructuring (no behavior change)

## Changes Made

- `src/audit/runs.rs`: add the strict-mode push-API `Classifier`
  (`SegmentContext`, `Mode`, `Advance`, `FinishOutcome`, the
  `invalid_opening_line` helper, and the `Classifier::{new, state,
  take_gap, feed_record, feed_fragment, feed_unparsable, finish}`
  methods). Owns `multiple records`, `trail identity`,
  `opening checkpoint duplicates predecessor`,
  `missing opening checkpoint`, `check_attestation`,
  `unclosed segment lacks matching immediate resume`, `apply_checked`,
  plus the `finish` epilogue. Attestation runs **inside**
  `feed_record` at base's per-path position (ruling 197-d1 addendum 12:
  after `missing opening checkpoint`, before the immediate-resume
  guard). On `Advance::Duplicate` `run_loss` is cleared and the shim
  does **not** bump `since_checkpoint`.
- `src/audit/storage.rs`: `scan_inner` becomes a thin shim over
  `runs::Classifier`; the local `SegmentContext` struct is deleted
  (the reader imports `runs::SegmentContext`).
- `src/audit/storage_tests.rs`: gate comment extended with the R2b S1
  paragraph, `sites.len()` goes 49 to 48 (the drop is the UNREACHABLE
  `missing head` row for scan_inner's `apply Ok leaves state=Some`,
  which becomes a classifier invariant with no inline
  `corrupt("missing head")` call; see the correction note below), the
  two `pin_sc_missing_head_opening_false_*` tests re-key `(..., 2)` to
  `(..., 1)`, the stale `scan_inner: apply Ok leaves state=Some`
  UNREACHABLE row drops, and four new acceptance pins land:
  `pin_sc_trail_identity_after_pending_fragment`,
  `pin_sc_multiple_records_fails_apply_checked_first`,
  `pin_sc_duplicate_does_not_bump_since_checkpoint`,
  `pin_sc_attestation_between_missing_opening_and_apply`.
- `docs/adr/0005-audit-trail.md`: one sentence appended to §19.9 after
  R2a's.

### Correction on earlier "merge" wording

The first commit's message and some rustdoc said the
`invalid_opening_line` helper "merges" the strict-mode
fragment-at-opening and unparsable arms. That is wrong: base `95f8bcf`
already had a **single** `scan_inner` site for both arms. The move
into `runs::invalid_opening_line` is a rename/reorganisation, not a
merge. The 49 → 48 gate-count drop comes entirely from the dropped
UNREACHABLE `missing head` row for `scan_inner: apply Ok leaves
state=Some` becoming a classifier invariant. Fix-round commit updates
the rustdoc on `invalid_opening_line`, `feed_fragment` and
`feed_unparsable`, and the coverage-gate comment, to say so.

### Proof: unfixed `S1.patch` vs fixed

Applied `r2b-proto/S1.patch` to base `95f8bcf` and injected the four
acceptance pins. Behaviour:

| Pin | base `95f8bcf` | unfixed `S1.patch` | this PR | catches |
|---|---|---|---|---|
| `pin_sc_trail_identity_after_pending_fragment` | ok | **FAILED exit 101** | ok | `S1.patch` defect 1 |
| `pin_sc_duplicate_does_not_bump_since_checkpoint` | ok | **FAILED exit 101** | ok | `S1.patch` defect 2 |
| `pin_sc_multiple_records_fails_apply_checked_first` | ok | ok | ok | M2 (mutant), not an `S1.patch` bug |
| `pin_sc_attestation_between_missing_opening_and_apply` | ok | ok | ok | M4 (mutant), not an `S1.patch` bug |

So two of the four acceptance pins (`pin_sc_multiple_records_fails_apply_checked_first`
and `pin_sc_attestation_between_missing_opening_and_apply`) catch
mutants (M2 and M4 respectively), not regressions in unfixed
`S1.patch`; the other two catch the two `S1.patch` behaviour defects.

Defect 1 = attestation ran **ahead of** trail-identity in unfixed S1
(regresses addendum 12). Defect 2 = unfixed S1's reader shim bumped
`since_checkpoint` on `Advance::Duplicate` (base's `apply_checked`
wrapper leaves writer-only fields on a duplicate). Both are corrected
here.

Note on attestation order: moving the `check_attestation` call one
step **earlier** (before `missing opening checkpoint`) or one step
**later** (after the immediate-resume guard) is an equivalent mutant:
a gap digest only exists once `feed_fragment` has accepted a line,
which itself requires `!self.first && !self.boundary_resume`. By the
time that holds, the `missing opening checkpoint` and immediate-resume
guards no longer trip, so re-ordering across those neighbours is
unobservable. M4 catches the real violation of addendum 12 (moving
attestation **after** `apply_checked`), which does change observed
details.

### Base-vs-head differential (independent 545,385-case sweep)

The fresh reviewer ran an **independent base-vs-head differential**
over strict `scan` (opening true/false, from empty and from a prefix
state), `scan_staged`, `scan_closing`, live `TrailReader::open`,
`refresh(opening=false)`, and `history_segment` × 4, comparing both
`Err` detail strings and the full set of observable `State` fields
(including `since_checkpoint`, `run_loss`, `checkpoint_time`, offset,
length, newline, gap): **545,385 cases, byte-identical on every
case**. The 156 passing pins (152 originals + the 4 new acceptance
pins) specifically assert `since_checkpoint` and the exact
detail-string order across the attestation site. No pin asserts
`run_loss`: the duplicate-branch clear is not observable on strict
paths (see the comment in `pin_sc_duplicate_does_not_bump_since_checkpoint`),
so only the independent differential above covers it. The
`invalid_opening_line` helper preserves the single reader-side site
that `pin_sc_invalid_audit_line_or_opening_checkpoint` targets.
