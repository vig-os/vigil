# Comments (1)

## [Comment #1](https://github.com/vig-os/vigil/pull/172#issuecomment-6570168722) by [@gerchowl](https://github.com/gerchowl)

_Posted on November 2, 2026 at 05:53 AM_

Architect ruling 164-d1: fix round 1 for head `51a1ff9`.

A fresh reviewer confirmed that the format is unchanged (24 input orders give one details byte string), the durability claims, the slices, and that no consumer identity appears. It found two blockers.

**Blocker 1. §20.7 overstates integrity** ("any change … produces `HashMismatch`/`ChainBroken`/a signature finding"). Decision 5 lets an attacker with write access recompute the unsigned tail after the last checkpoint, and roll back to an earlier checkpoint. Ruling: every post-erasure guarantee is scoped to what backs it:
- checkpoint-signed coverage (records through the last signed checkpoint);
- external receipts and anchors (#57);
- verified archive ranges (amendment 10).

The section must say plainly that the unsigned tail after the last checkpoint is not protected against an attacker with write access, with or without an erasure. Erasure itself weakens nothing. Recommend that consumers checkpoint before erasure-relevant retention events, and say whether that is advice or a rule.

**Blocker 2. §20.5 calls the proposal entirely additive,** but OQ5 refuses an input that 0.1.0 accepts. Ruling:
- CP1 is a breaking behaviour change under ADR-0004.
- CP1's PR carries `semver:major` (in 0.x it ships as a minor bump, per the stability policy) and a CHANGELOG entry under a breaking/changed heading that names the refused input.
- This docs-only PR is unchanged in that respect; remove the "no `semver:major` is needed" text.

**Open questions:** all accepted as recommended.
- OQ1: the id alphabet `[A-Za-z0-9._:-]`, 1–128 bytes.
- OQ2: the existing `InvalidEntry`.
- OQ3: no `seq` bounds yet.
- OQ4: a separate inclusion-proof issue, filed by the architect; cited as "to be filed".
- OQ5: reserve `vigil.attrs.` on every trail, with blocker 2's bookkeeping.

Each OQ is marked **Decided (ruling 164-d1)**. Status stays Proposed until CP1 merges.

**Gap analysis note:** the directory lock serialises writers across processes; it does not enforce one writer process per trail. One writer process per trail is the consumer's deployment choice, which vigil supports but does not require.
