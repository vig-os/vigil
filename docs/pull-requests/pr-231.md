# [PR 231](https://github.com/vig-os/vigil/pull/231) feat(audit): check checkpoint signatures and key trust in the verifier

## What changed

The offline verifier now checks each distinct `(seq, hash)` checkpoint
in the verified set for a valid Ed25519 signature over the 58-byte
checkpoint signing message and a signing key listed and trusted at its
`seq` on the verified trail (ADR-0005 decisions 8 and 9; ruling
13-V5-d1 points 1-3). Native and shipped-only copies are checked, inside
runs and outside; a byte-identical duplicate yields one finding at its
first occurrence (the `(path, line)` the engine's merge keeps). Each
distinct candidate is checked at its own `(path, line)`.

The two new findings are independent (ruling 13-V5-d1 point 2):

- `BadSignature` — `verify_strict` over `checkpoint_message` fails;
  includes an undecodable key, a small-order key and a non-canonical
  signature. Detail: `key <64 lowercase hex>`.
- `UntrustedKey` — the signing key is not listed for the trail's section
  (`key <64 lowercase hex> not listed for trail <32 hex>`) or the
  checkpoint's `seq` exceeds the key's `through=` bound
  (`key <64 lowercase hex> bounded through seq <n>`).

A checkpoint can carry both; neither suppresses the other. A
crate-private `trusted` predicate exposes the "signature verifies **and**
key is trusted at `seq`" fact for later work (coverage, revocation,
`end=`, `max_age`). The pass never feeds the shared classifier and
never demotes, excuses or empties a run.

The verifier's per-checkpoint summary retains the `CheckpointFields`
and the signing message together in one `SignedCheckpoint`, so the
"signing message is present iff it is a checkpoint" invariant is
structural rather than a parallel pair of `Option`s joined by an
`.expect`.

## Rows table (`src/audit/verify/signature_tests.rs`)

Every acceptance row asserts the FULL sorted finding list as whole
`Finding` values (every field: kind, file, line, seq, detail,
`accepted_kind`, `run_digest`). The comparison helper `assert_findings`
is a thin `assert_eq!` on `Vec<Finding>`; no projection drops a field,
and every digest / hash / key that appears in an expected detail is a
written-out hex constant (`CP2_HONEST_DIGEST` ..., the A1 / A3 run
digest bytes), never computed from the fixture or from the code under
test. A separate `fixture_hashes_match_literals` test pins each
literal to the record the fixtures produce.

Predicate rows (`A4b`, `A8b`, `Y1b` and the two `trusted_predicate_...`
rows) exercise the new crate-private `trusted` predicate and cannot
compile on base; they are labelled predicate tests, not acceptance.
Regression row `R2` compiles and passes on the stubbed base (`check`
stubbed to a no-op; the honest A1 list is base-identical) and is
killed by M2 and M8 through its two predicate pin assertions.

## Existing tests changed (shared keyless-policy builders, fixture churn)

- `src/audit/verify/rule2_tests.rs:policy_trail()` and
  `src/audit/verify/runs_tests.rs:policy_trail()` now list
  `runs_v4a_fixtures::fixture_pubkey()` — the public key derived from
  the shared fixture signing seed `0x27` used by every signed
  checkpoint these fixtures produce. Without this change every V4a
  verifier row would also emit `UntrustedKey` for cp0/cp2/cp5/cp6.
- `tests/audit_verify.rs::Written` and
  `no_crash_mark_absent_when_only_successor_is_a_shipped_copy`'s
  inline fixture: list the writer's own public key via
  `signer.public_key()`, so every writer-produced checkpoint is
  trusted at verify time.
- `src/audit/verify/engine_tests.rs::ctx::checkpoint`: fabricated
  checkpoints now carry a real `signing_message` paired with their
  fields in `SignedCheckpoint`, signed by the shared fixture key, and
  the file's `trust_trail()` lists that key. Historical rows filter
  findings by kind, so no finding list changed.
- `src/audit/verify/engine_tests.rs::record` and
  `src/audit/verify/mod_tests.rs::located`: the parallel
  `signing_message: None` field is gone — `Summary::checkpoint` is now
  one `Option<SignedCheckpoint>`.
- `src/audit/runs_v4a_fixtures.rs::fixture_pubkey()`: new helper
  returning the fixture key's public bytes, reused by every verifier
  test file.

No existing finding list changed: every expected list is byte-identical
with its base counterpart.

A1-A8, R1 and R1b are single-sealed-segment layouts without a run, so
they do NOT kill M7 / M7′; only A9 and A10 place a bad signature on a
checkpoint whose segment classifies as a run member (first record not
a checkpoint). F1 and F2 both order the "bad" candidate strictly after
the honest one in BTreeMap-by-hash order, so dropping `candidates[1..]`
under X3 deterministically loses the signature finding. Z1 is caught
only because the row standard compares whole `Finding` values: a
projection on `(kind, file, line, seq, detail)` would miss it.
