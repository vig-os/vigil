## Changes Made

- `docs/adr/0005-audit-trail.md`:
  - **Tessera answer.** The coupling came from shared vocabulary, not a shared problem. Tessera seals finished data products; vigil's audit trail is a live, multi-writer log. vigil adopts tessera-core's MMR construction bit for bit (probed: identical roots for every size 0..=2048, and tessera verifies proofs against vigil roots), uses its `blake3:<hex>` spelling and its key-file format, and defers export to `.tsra` to #59. It does not adopt tessera's seal-once model or its `ed25519-env-v1` envelope.
  - **Decisions:**
    1. Feature `audit`, with a synchronous, fail-closed API separate from `tracing`.
    2. The trail lives in its own `audit/` directory and lock, reusing ADR-0002's machinery. Retention is off.
    3. Records are OTLP log records with `audit.*` attributes covering who, what, when, why, before and after.
    4. The record hash is a frozen, length-prefixed encoding of attribute **values**, so it survives re-serialisation and Collector round trips.
    5. The hash chain starts from a per-trail genesis value.
    6. Each record is fsynced before `Ok`. A failed fsync poisons the handle. There is no queue, no drop and no truncation. A signer outage does not fail records.
    7. One MMR spans the whole trail.
    8. Ed25519 checkpoints run every N records or T seconds (evaluated at append time), plus closing and opening checkpoints at rotation.
    9. Key custody uses a `Signer` trait and `KeyFileSigner`; a key is rotated by reopening with a new signer and revoked through the trust file.
    10. Anchoring is optional, done by exporting checkpoint lines.
    11. The verify API and the `vigil-audit` CLI contract are fixed, including exit codes.
    12. The v1 format is frozen, with golden vectors and fixtures that CI pins to the 1.0.0 tag.
    13. The public surface follows ADR-0004's rules.
    14. Dependencies: `blake3` (pure), `ed25519-dalek`, `getrandom` (already in the tree).
    15. The tessera adoption path.
  - **Deferred,** each to an issue filed for this ADR: group commit and a batch API (#56); RFC 3161 and transparency-log anchoring plus a consistency-proof API (#57); hardware signers (#58); tessera export and MMR swap (#59).
- `docs/adr/README.md`: adds ADR-0005 to the index. It also replaces the stale sentence saying ADR-0003 is the audit trail with the list of reserved numbers, worded as in PR #54.

**New dependencies:** none in this PR. The ADR chooses `blake3` 1 and `ed25519-dalek` 2 for the `audit` feature (crates.io; justified in decision 14).

### Manual Testing Details

Probes ran in scratch crates outside the repository, on Rust 1.95.0 from the dev shell:

- **MMR equivalence with tessera-core** (vig-os/tessera@f08255d as a dev-dependency):
  - roots are equal for sizes 0..=2048;
  - `verify_inclusion` and `verify_consistency` accept proofs against vigil roots, including a proof built from stored checkpoint peaks;
  - `cargo test --release`: 2 passed. A mutation (bagging left to right) fails both tests.
- **Cost per record:**
  - encoding + blake3 + chain link + line: 1.26 µs (SIMD blake3), 2.67 µs (`pure`);
  - MMR push: 0.34 µs;
  - Ed25519 sign: 11.1 µs; `verify_strict`: 24.1 µs.
- **fsync on vm-dev ext4:**
  - `sync_data` per record: p50 23–34 ms, about 30–37 records/s;
  - one `sync_data` per 64 records: about 1 970 records/s;
  - tmpfs: effectively free.
- **Platform fsync:** in Rust 1.95 std, `sync_data` is `fdatasync` on Linux and `F_FULLFSYNC` on Apple (`std/src/sys/fs/unix.rs:1381-1430`).
- **crane/Nix:** a scratch clone of vigil with both crates added and a BLAKE3/RFC 8032 known-answer test. `nix build .#checks.x86_64-linux.clippy .#checks.x86_64-linux.nextest`: exit 0, 127 tests passed. The normal tree goes from 64 to 81 crates; licences are MIT/Apache-2.0, BSD-3-Clause and CC0-1.0.
- **tessera-core's weight:** 41 normal dependencies, against 23 for `blake3` plus `ed25519-dalek`.

## Additional Notes

- **Pre-PR review.** A fresh-context review found 4 blockers, all fixed in this PR:
  - The threat model is restated: without a key, an attacker can rewrite the uncovered tail or roll the trail back to an earlier checkpoint. Anchors, receipts and `--max-age`/`StaleHead` detect that.
  - Trails are created explicitly (`create` plus a marker file) instead of silently on `open`.
  - The writer applies the verifier's `TornWrite` rule, including after a torn opening checkpoint.
  - Revocation uses `through=<seq>` bounds, so the documented procedure verifies cleanly.

  Smaller fixes from the same review: duplicate and foreign attributes and `body` are rejected, peaks are absent at size 0, `audit.poison` is written when a rollback fails, Collector duplicates are reported as warnings, and the `pure` crane build was re-probed.
- **#12's title** still says "on tessera-core". This ADR supersedes that plan (owner decision 2026-10-11), so the title and body should be updated when #12 is briefed.
- **Conflict with PR #54.** This PR and #54 both edit `docs/adr/README.md`; whichever merges second rebases. ADR-0004 is cited as Proposed in PR #54.
