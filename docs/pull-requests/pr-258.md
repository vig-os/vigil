# [PR 258](https://github.com/vig-os/vigil/pull/258) feat(audit): confirm resume gaps by receipt and report lost inputs

## Summary

Confirm resume gaps by receipt and emit `LostRecord` for inputs inside them (ADR-0005 decision 5 "Resume gaps" / "Receipts lost with a resume"; ruling 13-V7-d1 points 7-9). An honest `AuditConfig::resume` after a lost live file now passes plain verification: a trusted, fold-matched opening checkpoint makes the jump a resume gap and the `SeqGap` is suppressed (point 7, with the genesis exception requiring confirmation); a receipt matching the resume record's `(seq, hash)` under the shared match rule AND passing `Classifier::set_aside` confirms the gap (point 8), so a receipt above `end_before`'s last-line `seq` or below an accepted start never confirms; inside a confirmed gap every receipt, waiver and `receipts_from` becomes one `LostRecord` (info) with the `<subject>: lost in gap <a>..=<b>` grammar; the `Resumed` detail now carries `lost_records=<n>` counted per-gap, keyed on each gap's own resume `(seq, hash)`.

Gap confirmation re-applies `Classifier::set_aside` plus `receipts::matches` — the same Matched decision `match_one` returns — and deriving confirmation directly from `match_one`'s outcome is tracked as a follow-up issue the maintainers will file.

A shipped-only opening is never a fold-matched candidate (owner ruling 13-V4-d10 point 5; spike #224), so a Collector copy cannot confirm a gap.

## What changed

- `verify/position.rs`: `Gap` gains `resume_seq` / `resume_hash` so the per-gap `lost_records` count keys on the gap's own resume identity, never on the pending-candidate list's shape.
- `verify/engine.rs`: the receipt confirmation pre-pass runs the shared match rule through `Classifier::set_aside` on a bare-gaps classifier, so an above-end or below-start receipt fails confirmation on the same path the real receipts loop uses; `build_gaps` now reads `confirmed_receipts` (not the receipts bundle) and pairs hash equality with the trusted predicate on the same copy; `count_lost_records` iterates the gap list and reads bounds + key from each `Gap`, never zipping with the kept candidates.
- `verify/receipts.rs`: `matches` rustdoc describes its real caller set (resume-gap confirmation pre-pass in `engine::check`).
- `verify/resume.rs`: `ResumeCandidate` rustdoc drops the inaccurate `head_hash` low-bound claim and states the field's purpose.

Non-test diff: **299 net lines added** in `src` (measured by `git diff --stat origin/dev -- <non-test files>` as `385 insertions(+), 86 deletions(-)`).

## X1 equivalence

X1 ("match a gap by `high` only") is equivalent to the shipped fix. The classifier's per-gap `(low, high)` is produced by S2a / S2b, which force `low == next` (the `h+1` immediately after the trusted head) for a non-genesis gap, and by S3b, which forces `low = 0` for a genesis gap. In both branches `low` is determined by the gap's structural neighbor, so matching a gap by `high` alone cannot differ from matching by `(low, high)` on any producible fixture — no row can uniquely kill X1 beyond the existing H/Q coverage.
