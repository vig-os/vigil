## Unreleased

### Added

- Add `Verifier::receipts(impl IntoIterator<Item = (u64, [u8; 32])>) -> Self` so a stopped-trail verifier reconciles the application's stored receipts against the verified history (ADR-0005 decision 5 "Receipt reconciliation"; ruling 13-V7-d1 points 2-5). The call turns reconciliation on so `.receipts([])` still reports every in-range `audit.record` as `NoReceipt` (error) at the record's first copy in the engine's merge order, with detail `no receipt for seq <s> hash blake3:<64 hex>`; a second call adds to the receipt set; identical receipts collapse, and two receipts for one `seq` are each evaluated independently. Operator `vigil.audit.*` records are included; checkpoints are not. The reconciled range runs from `seq 0` or the accepted `Verifier::start_from` start through the last record in the files, so the end record of a `Verifier::end_before` batch is never `NoReceipt`'d, and a receipt whose `seq` is strictly below an accepted start or strictly above the end record's last line's `seq` is set aside through the shared position classifier as `OutOfRange` (info) when the start or end is anchored and `UnanchoredStart` / `UnanchoredEnd` (error) otherwise, with subject `receipt seq <s> hash blake3:<64 hex>`. A receipt matches when the verified set holds exactly one distinct record at its `seq` and that record carries its hash; otherwise `ReceiptMismatch` (error) at the receipt's `seq` with no location, with detail taken from the first failing step in this order: `receipt seq <s> hash blake3:<64 hex>: no record`, `receipt seq <s> hash blake3:<64 hex>: seq is forked`, `receipt seq <s> hash blake3:<64 hex>: hash differs (record blake3:<64 hex>)`. `waive`, `receipts_from`, `receipts_live` and resume-gap confirmation (`LostRecord`, `Unreconciled`) land in later #13 work. Refs #13.
- Set aside an anchor, a `through=<b>:<h>` pin or a trust-file `end=<s>` whose `seq` is strictly above the end record's last line's `seq` under `Verifier::end_before` as one unlocated `OutOfRange` (info) or `UnanchoredEnd` (error) finding at the input's `seq`, and skip `RevocationUnconfirmed` in an end-bounded verification because the confirming checkpoint may lie above the end (ADR-0005 decision 11 "It ends the range"; ruling 13-V6-d7; see `Verifier::end_before` for the detail grammars and the rule). Refs #13.
- Compare every record of the verified set with the record at the highest present `seq` below it, not only the one immediately before, so a `ChainBroken` fires together with `SeqGap` wherever records are missing between the two; the end record (`Verifier::end_before`) is checked by the same rule, and the one end-specific case fires an unlocated `ChainBroken` at `e` with the detail `end_before seq <e>: no record precedes the end` when the files hold no record below `e` and `e > 0` (ADR-0005 decision 2 step 6, decision 11 `accept-run` item 2, the prefix-deletion and tail-cut bullets; ruling 13-V6-d6; see `FindingKind::ChainBroken` for the grammars). Refs #13.
- Add `Verifier::end_before(&str, Option<Checkpoint>) -> Result<Self, AuditError>` so one archive batch is verified against its end record and the batch-start anchor entry that pins it, with the record's lines walked by the shared classifier as the segment that follows the files (ADR-0005 decision 11 `.end_before`; ruling 13-V6-d4; see `Verifier::end_before` for the full record grammar, finding details and the conflict with `max_age`; #13).

Refs #13.
- Add `Verifier::start_from(Checkpoint) -> Self`, which accepts the first record of an archived trail as the start when the acceptance rule holds and emits a single `StartMismatch` (error) with the first failing condition's detail otherwise, so the prefix `SeqGap` for `0..s−1` is suppressed only on an accepted start while everything else runs unchanged (ADR-0005 decision 11 `.start_from`; ruling 13-V6-d2; see `Verifier::start_from` for the acceptance rule and the seven-step detail precedence). Refs #13.
- Add `Verifier::anchor(Checkpoint) -> Self` and emit `AnchorMismatch` per failing anchor on the verified trail (ADR-0005 decision 10; ruling 13-V6-d1 points 1-2). An anchor pins one `(trail, seq, hash)` triple built from a `Checkpoint` outside the trail directory; it matches only when its `trail` is the verified trail, the verified set holds exactly one distinct record at its `seq` (byte-identical duplicates count as one record), and that record carries the anchor's hash. Shipped-only copies count as records in the trail (ruling 13-V5-d4); a forked `seq` (ruling 13-V5-d2) is never matched, even when one copy carries the anchor's hash. Each distinct `(trail, seq, hash)` is checked once; duplicate anchors collapse. A failing anchor yields one `AnchorMismatch` (error) at `seq` `s` with the detail taken from the first failing condition in this order: `anchor seq <s> hash blake3:<64 hex>: trail differs`, `anchor seq <s> hash blake3:<64 hex>: no record`, `anchor seq <s> hash blake3:<64 hex>: seq is forked`, and `anchor seq <s> hash blake3:<64 hex>: hash differs (record blake3:<64 hex>)`. Every finding locates at the first copy of the record at `seq` in the engine's merge order (the same copy `DuplicateRecord` reports as the original), including the `trail differs` case when the verified trail holds that `seq`; the `no record` case has no record to locate against and so no location. Anchors are not signature-checked: supplying one is the operator's statement that this checkpoint was observed on the verified trail at its `seq`. `Checkpoint` gains a private trail field, filled by `Checkpoint::parse` from the line's `audit.trail`; every in-process constructor (`AuditTrail::checkpoint`, `AuditTrail::close`, `AuditConfig::resume`, `checkpoints`) delegates to `parse`, so an anchor taken in process matches its own trail. Refs #13.
- Add `Verifier::max_age(Duration) -> Result<Self, AuditError>` and emit `StaleHead` when the newest trusted checkpoint on the verified trail is older than `max_age`, or when `max_age` is set and no trusted checkpoint exists (ADR-0005 decision 5; rulings 13-V5-d1 point 7 and 13-V5-d6). The newest trusted checkpoint is the trusted (ruling 13-V5-d1 point 3) checkpoint with the highest `seq`, including shipped-only copies; at a forked `seq` (ruling 13-V5-d2), the highest unforked trusted one below it. "Now" is read once per verify call from the system clock through a crate-private seam, and age is `now - time` in nanoseconds on the checkpoint's signed `time` with checked arithmetic (a future `time` saturates to age 0 and is not stale; clock problems are the business of `ClockWentBackwards`). Detail grammars are `newest trusted checkpoint seq <n> time <t> is older than max_age <d> at <now>` at the checkpoint's first copy for the stale case, and `no trusted checkpoint (max_age <d>)` with no location for the no-trusted case. At most one `StaleHead` fires per verify call. `max_age` is always `Ok` at this head; combining it with `end_before` yields `InvalidConfig` from whichever call comes second (ADR-0005 §19.2; #13 V6). `Duration::ZERO` is accepted, and calling `max_age` a second time replaces the earlier value. Refs #13.
- Check `end=` and grant a matching `end=` its three exemptions in the verifier (ADR-0005 decision 9; rulings 13-V5-d1 point 5 and 13-V5-d5). Evaluate two independent conditions once against the merged records per `seq` on the verified trail and the shared fork set: at `s`, the verified set must hold exactly one distinct record with hash `h` (byte-identical copies count once), and above `s`, no record of the verified trail may carry a `seq` strictly above `s`. Each condition yields at most one `TrailEnded`. The "at `s`" detail follows the first failing check in this order: `seq <s> is forked` (no location), `no record at seq <s>` (no location), `record at seq <s> has hash blake3:<64 hex>` (at the first copy in the engine's merge order, the one `DuplicateRecord` treats as the original). The "above `s`" detail is `records seq <a>..=<b> above the end`, with `a` and `b` the lowest and highest such `seq`, located at the first such record in merge order. Every detail starts with `end=<s>:blake3:<64 hex>:`. A matching `end=` (neither condition fails) grants exactly three things, and a mismatch grants none: the report's tail exemption (`UncoveredTail` stays an info but `--strict` does not fail on it), confirmation of every `through=` bound in the section whose `seq` is at or below `s` (the pin itself still runs), and promotion of a 13-V5-d2 attester at or below `s` to `TornWriteRepaired`. No `end=` in the section checks nothing and grants nothing. Refs #13.
- Check revocation pins and confirmation in the verifier (ADR-0005 decision 9 and amendment 8; rulings 13-V5-d1 point 4, 13-V5-d3 and 13-V5-d4). For each key in the verified trail's section carrying a `through=<s>:<h>` bound, in key-byte order (scope: ruling 13-V5-d3 point 3), the verifier emits `RevocationMismatch` when the pin fails and `RevocationUnconfirmed` when the bound is not confirmed; the two checks are independent so one bound can carry both findings. A bound on key `K` is pinned when exactly one distinct record exists at `s`, its hash is `h`, it is a checkpoint, and its `audit.key_id` is `K` (amendment 8: a bound names a checkpoint `K` itself signed). Byte-identical duplicates count as one record; a `SeqConflict` fork is not pinned (fail-closed per ruling 13-V5-d2). Exactly one `RevocationMismatch` detail is emitted per bound, chosen by the first failing condition in this order (ruling 13-V5-d4 point 3): `no record at seq <s>` (no location), `seq <s> is forked` (no location), `record at seq <s> has hash blake3:<64 hex>` (at the first copy in the engine's merge order), `record at seq <s> is not a checkpoint` (at the record), or `record at seq <s> is signed by key <64 hex>` (at the record). A bound is confirmed by a trusted checkpoint (ruling 13-V5-d1 point 3: signature verifies under `verify_strict` AND key trusted at its `seq` for the verified trail) strictly above `s` (ruling 13-V5-d4 point 2) signed by a key other than the bounded one; a shipped-only trusted checkpoint confirms (ruling 13-V5-d4 point 5). Otherwise `RevocationUnconfirmed` fires with detail `key <64 hex> through=<s>: no trusted checkpoint by another key above the bound`, located at `s` like the pin finding. The module reads only what the engine already has from the one snapshot (ruling 13-V4-d5): the merged records per `seq`, the fork set, and the crate-private trusted predicate. Ruling 13-V5-d5 point 2.2: a matching `end=` in the section confirms every `through=` bound in the section whose `seq` is at or below the matched end `seq`, so no `RevocationUnconfirmed` fires there; the pin itself still runs. Refs #13.
- Report trusted-checkpoint coverage in the verifier (ADR-0005 decision 5 and decision 11; rulings 13-V5-d1 point 6 and 13-V5-d2). `Report::covered_through` is the highest `seq` of a checkpoint whose signature verifies under `verify_strict` AND whose key is trusted at that `seq`, or `None` when no candidate is trusted; native and shipped-only candidates count equally. `UncoveredTail` now lists exactly the records strictly above `covered_through` (or every record when `None`), with detail `records seq {a}..={last}` where `a = covered_through + 1` (or the first verified `seq`); the last record being itself covered yields no `UncoveredTail`. A native gap is reported as `TornWriteRepaired` (info) with the same `lines {first}..={last} ({N} bytes), attested at line {L} seq {S}` grammar only when the attesting record is itself a record of the verified trail AND the only record at its `seq` (not one side of a `SeqConflict` fork) AND its `seq <= covered_through`; otherwise it stays `TornWrite`. `RepairMismatch`, a trailing gap with no attesting record, and a `fragment not present` detail (native or shipped) are never promoted. Refs #13.
- Check every distinct `(seq, hash)` checkpoint in the verified set for a valid signature over the 58-byte checkpoint signing message and a signing key listed and trusted at its `seq` for the verified trail (ADR-0005 decisions 8 and 9; ruling 13-V5-d1 points 1-3). Native and shipped-only copies are checked, inside runs and outside; a byte-identical duplicate yields one finding at its first occurrence, the same one the engine's merge keeps. `BadSignature` fires when `verify_strict` over `checkpoint_message` fails (an undecodable key, a small-order key and a non-canonical signature are included), detail `key <64 lowercase hex>`. `UntrustedKey` fires when the signing key is not listed for the trail's section (detail `key <64 lowercase hex> not listed for trail <32 hex>`) or when the checkpoint's `seq` exceeds the key's `through=` bound (detail `key <64 lowercase hex> bounded through seq <n>`). The two findings are independent: a checkpoint can carry both; neither suppresses the other. Signature and trust checks never feed the shared classifier and never demote, excuse or empty a run. A crate-private `trusted` predicate exposes the "signature verifies **and** key trusted at seq" fact to later `#13 V5` work (coverage, revocation, `end=`, `max_age`). Refs #13.
- Report ADR-0005 decision 5 rule 2 and amendment 6 (iii) refined by decision 11 `accept-run` item 3 as `MmrMismatch` findings from the shared classifier's one fold, and filter the private resume candidate list fail-closed to openings the fold compared and matched. Every native opening checkpoint and native in-run checkpoint before the run's first loss point whose declared `mmr_size`/root/peaks differ from the fold is reported as `MmrMismatch` and pairs with a `CheckpointMmrDiffers` violation (which empties every run, 13-V4-d8 point 3); every native in-run checkpoint at or after the first loss point whose declared fields differ from the fold is reported as `MmrMismatch` without a violation (amendment 6 (iii): the reader does not compare it and runs stay). Shipped-only openings are out of scope for rule 2 at this head (owner decision 13-V4-d7; spike #224 decides whether run boundaries and rule 2 can be recovered from a Collector record stream). A self-base that is self-consistent against its own peaks (ADR amendment 6 "Base", `Mmr::from_peaks`) is recorded as never-compared and dropped by the fail-closed filter, like any other never-compared opening; a self-base whose declared fields disagree with the fold loaded from its own peaks is a compare that fired and failed, so it lands under the differing outcome and emits `MmrMismatch`. The genesis base of amendment 9 part 1 stays a real compare against the computable 1-leaf fold. The resume-candidate filter keeps only candidates whose `(opening_seq, opening_hash)` the classifier positively recorded as compared-and-matched, so a forged opening whose hash collides on `seq` with an honest Matched opening on the same trail is also dropped; shipped-only openings (#224) and openings the walk did not reach after an earlier violation in the same segment are therefore never confirmed. One classifier pass per verify call, no second fold (ruling 13-V4-d10 point 1). The classifier records every checkpoint the fold compares in every segment of the single classification (including sealed segments walked by the strict-Stop closure inside `storage::history_segment` on the verifier's outer Collect path); `runs::classify` and reader-only paths set `record_fold_entries = false` so no per-checkpoint blake3 hash runs on the reader's Stop path. Detail grammar: `expected size <n> root <digest>, found size <n> root <digest>`. Ruling 13-V4-d10. Refs #13, #224.
- Add verifier run detection through one shared classifier pass under `Reaction::Collect` over the verifier's confirmed snapshot bytes (never a second read, no file open), emitting one `SegmentStructure` finding per closed run with its run digest per ADR-0005 decision 11 "accept-run". The run's `(file, line, seq)` are the run's first segment and its first record on the verified trail; the detail lists each loss point in `seq` order, then each span in segment-and-byte order (with `after start` at a segment's first byte), then `digest blake3:<hex>`. A run's spans come from the run's own segments only, `first_segment..last_segment` exclusive, so the closing segment never contributes to the run digest (ruling 13-V4-d9, #226). Shipped (Collector) inputs get no run finding at this head (owner decision 13-V4-d7; spike #224). Rulings 13-V4-d3, 13-V4-d4, 13-V4-d5, 13-V4-d6, 13-V4-d8, 13-V4-d9. Refs #13, #226.

## [0.2.0](https://github.com/vig-os/vigil/releases/tag/0.2.0) - 2026-11-02

### Added

- Optional rotated-segment count and directory-wide telemetry byte caps, with per-signal size, count and age rotation overrides and environment equivalents ([#163](https://github.com/vig-os/vigil/issues/163), #176, #178). Zero caps are honoured. Pruning runs at open and after rotation in age, count, then total-byte order, deleting oldest segments first; the total pass also runs before an oversized write into an empty live file. Live files and audit files are never pruned. Total-byte pressure can erase a quiet signal's entire rotated history. Failed deletions remain counted, later segments are tried, and an unmet cap warns. Live-file and pending-write reservations and retained writer handles are included in the documented logical-byte bound.
- Audit `FieldKind`, `AttrValue` and `Entry::attr`, with a canonical typed attribute block; `RecordSchema`, `RecordSchemaBuilder` and `ActionFields`, with canonical schema text and a domain-separated BLAKE3 digest (#164, #175, #177).
- Schema-checked audit writers through `AuditConfig::schema`, with fail-closed record and operator validation and personal-data and erasure guidance (#164, #165, #179). The v1 byte encoding is unchanged.
- `vigil-audit schema <file>` prints a canonical schema digest; optional `--schema <file>` on `rotate` and `resume` enforces opaque operator and reference ids (#164, #165, #180).

### Changed

- **Breaking:** audit record construction refuses caller-supplied `Entry::details` starting with the reserved `vigil.attrs.` prefix (`InvalidEntry`), with or without a schema; decoding existing records is unchanged (#164, #175).

SDK warnings go to stderr, failed stderr writes are tolerated, and events after shutdown produce at most one warning.
  - Invalid directory, filter and numeric overrides warn; empty overrides are ignored and relative HOME paths are rejected. An existing global subscriber is rejected before storage side effects; an existing `log` logger does not prevent tracing initialization. Initialize after fork, as documented.
- **Multi-process-safe size rotation and age retention** on local Unix filesystems ([#4](https://github.com/vig-os/vigil/issues/4), [#25](https://github.com/vig-os/vigil/issues/25), [#31](https://github.com/vig-os/vigil/issues/31)).
  - `vigil::rotate::RotatingFile` appends whole lines to `<dir>/<signal>.jsonl` under a blocking `flock` on the state directory, refreshes replaced or missing directory locks, and reopens the live file after another writer rotates. Operations use the locked directory descriptor; waits over ten seconds produce one warning per process.
  - Rotation uses atomic no-replace rename, with directory-relative link/unlink only when unsupported. Both unlink and undo failures are reported; the next lock acquisition recovers live files sharing an inode with a matching signal segment while preserving external backup links.
  - Signal names are `[a-z0-9_]+` and segment matching is exact. Segments order by timestamp and integer counter, including counters wider than six digits and backwards clock changes. Directories and files are created with modes 0700 and 0600, and looser existing permissions are tightened on open. Each line uses one `write(2)`; partial writes roll back and killed-writer fragments are separated from the next record.
  - `segments`, `segments_since`, `read_since` and `find_newest` read segments back without locking writers. Reads retry across rotation with a bounded best-effort result; newest-first searches stop at the first matching file. Files must be read separately to avoid joining unterminated fragments across file boundaries.
- `vigil::logs::OtlpJsonLogExporter` (requires `--cfg vigil_unstable`), an `opentelemetry_sdk` `LogExporter`, writes batches as bounded OTLP/JSON `LogsData` lines to a `vigil::sink::LineSink`, with deterministic ordering, missing `timeUnixNano` backfilled from observed time, and non-finite doubles spelled `"NaN"`/`"Infinity"`/`"-Infinity"` ([#3](https://github.com/vig-os/vigil/issues/3), [#30](https://github.com/vig-os/vigil/issues/30)).
  - Lines default to at most 1,000,000 JSON payload bytes excluding the newline; the configurable cap is clamped to 1..=1,048,575 for the Collector's 1 MiB limit. Batches split at record boundaries and pack scopes while copying only resource/scope metadata. Oversized records shorten their largest strings by the escaped-byte overflow, preserving UTF-8 and base64 boundaries, and carry `vigil.truncated` and `vigil.original_size`.
  - Attribute keys, event names and resource/scope fields remain immutable. Unshrinkable records become counted diagnostic stubs preserving identity and small original messages when space permits; healthy neighbors remain intact. A cap too small for the envelope and diagnostic identity returns an explicit error.
- `vigil::sink::{LineSink, AppendFile, MemorySink}` (requires `--cfg vigil_unstable`): the line-sink seam, an `O_APPEND` single-`write(2)` file sink (mode 0600) and an in-memory test sink ([#3](https://github.com/vig-os/vigil/issues/3)).
- **ADR-0001 (on-disk format) and ADR-0002 (rotation and retention)** record the OTLP/JSON Lines format, versioning stance and multi-process rotation design, including directory locks, no-replace rotation and bounded reader retries ([#1](https://github.com/vig-os/vigil/issues/1)).
